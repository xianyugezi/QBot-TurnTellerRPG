## 二、核心架构改造（决定批次划分）

### 2.1 pages_crud PAGE_MODULE 硬编码 → editor_registry 动态驱动（关键前置）
现状：`PAGE_MODULE` 写死六页（已注释「批 4 扩张页时替换」）——**这就是硬编码点**。改造：
- pages_crud 增 `page_registry` 注入/读取 editor_registry 页表（page_id → module_file 映射）
- 移除 `PAGE_MODULE` 六页死映射（或降级为缺省兜底），PAGE_FILE/PAGE_ID_PREFIX 同步动态化
- 扩展页（npc/checkin/ai/hidden/env_event/log_card）+ 新页全部经 editor.json 登记即得 CRUD
- 风险：既有测试大量引用 PAGE_MODULE 常量 → 保留模块级常量但内容改为「动态读取 + 兜底」或测试改注入

### 2.2 field_meta 空表模块注入（专项全权冲突处理）
C 类模块（dungeon/achievements/fishing/forge）+ E 类（stats/formula）字段表空是**防泛型误拦**（专项校验器全权深结构）。注入字段表必须走 M12 4A 的**宽松登记原则**（仅 id required + 宽 obj 容器 + soft_label 多形态 + 闭合枚举），注入后跑内容包加载**零新增红拦**（test_demo 实测把关）。
- dungeon：9 顶层（id/name/type/entry_item/entry_limit/maps/subquests/safe_zone/drops）
- achievements：7 顶层（id/name/desc/conditions/trigger/once/reward）
- fishing：obj 3 段（schema_version/species/king）——**species 数组深层由 fishing_editor_service 提供 schema**
- forge：obj 5 段（schema_version/trees/sets/augments/settings）
- stats：map 键空间（11 键）→ 页面形态 = 键值编辑器（entry_type=map 特化渲染）
- formula：map 键空间 → 键值编辑器 + formula 校验（长度/AST）
- settings：obj 段编辑器（default_map/world_name/currencies/death_penalty/alchemy/forge/fishing + slot_defs/env_event/log_card）

### 2.3 前端侧边栏全页清单
editor.html 已读 /api/editor/pages 渲染侧边栏 → **登记即出现**（无需前端改）；但 map 型页（stats/formula/settings）和 obj 型页（fishing/forge）需要**非 list 条目形态的表单渲染**（现表单假设 list 条目：列表+点开+保存）。map/obj 页特殊渲染：单对象表单（无列表）或键列表编辑。

### 2.4 钓鱼页特殊（fishing_editor_service 现成）
`editor/fishing_editor_service.py`（495 行，纯函数零 IO）：fish_card_schema()/fish_csv_export/import/validate/crown_preview/simulate_catches——钓鱼表单直接复用（卡片式：species 逐条编辑 + CSV 导入导出 + 冠级预览）。这是 M12 启动包 L108「UI 归 M12」的真缺口补交。

## 三、硬编码清理（用户点名重点，贯穿各批）

### 3.1 事件硬编码（EVENT KEY 散落 → 内容包可配置）
现状（已摸底）：
- `bump_event(ctx, "[事件:签到]")` checkin.py L877 / `[事件:副本通关]` dungeon L556 / `[事件:等级提升]` levelup L203 / `[事件:图鉴新增]` codex L387 + fishing_codex L172 / `[事件:任务完成]` quest（_EVENT_PREFIX 常量 L119）/ `[事件:怪物击杀]` battle / `[事件:成就达成]` achievements L370 / `[事件:首杀]` adventure_log L129 / `[事件:环境事件]` environment_events L79（有 ENV_EVENT_KEY_BASE 常量）/ NPC 对话动态键 dialog L269
- **无事件键注册中心**：各模块写死键名，条件引擎/成就/任务以 `[事件:X]` 为条件键读取（quest.py L458 `"[事件:" + name + "]"`）——改键名会断条件 → **必须谨慎**
- 目标：**事件键集中到 settings.json 可配置段（events 段）**，模块从 ctx/settings 读键名，缺省回退现键（向后兼容零破坏）；条件引擎读取侧同步收口
- 风险：event_bus 是唯一写入器但键名散落消费方；改动必须全仓 grep `[事件:` 对齐

### 3.2 功能硬编码（编辑器层 + 引擎层）
已登记的编辑器硬编码（pages_crud 注释 + m12_记录）：
- PAGE_MODULE 六页死映射（本里程碑 2.1 解决）
- PAGE_ID_PREFIX 页名前缀绑定（内容包自定义 ID 风格无入口）→ editor.json 页条目加 id_prefix
- 版本簿挂 ctx 内存键（跨进程失效）→ SV-08 语义可接受但登记
- quest.json 单复数契约笔误（已修正登记）
- field_meta meta_source 映射在 api.py meta_page 的 dict（新增模块要同步加映射）→ 改 editor_registry 驱动
引擎层功能硬编码候选（审计面，遇则登记/处理）：
- 事件键（3.1）、木桩特判（EV-06 tier:training 不计——battle 已有？）、货币 id（veinborn coins 教训）、settings 段默认值、NPC/商店/任务键空间

### 3.3 处理纪律（用户铁律）
- **只建议不限制**：硬编码改可配置必须有缺省回退（内容包不声明 → 现行为不变）
- 涉及引擎消费语义（事件键/条件）→ 先出方案给用户审核再改（2026-09-03 用户拍板：复杂验证派子 agent 模拟玩家；硬编码记录让用户决定——但本次用户已授权「统一处理」）
- 处理范围以「编辑器可达性」为准：页面要编辑的内容若消费方硬编码 → 一并收口；纯引擎内部常量不硬改

## 二、🔴 P0 清单

### P0-1（重复触发）印记条件 C-1/C-2/C-4/C-5 在 battle 注入 marks_lookup 后「静默恒真」，旧 P0 复发
- **位置**：battle.py `_resolve_combo_action` 内 `_marks_lookup` L1150-1156（注入）＋ combo.py `_eval_marks` L372-399 / `evaluate_condition` marks 槽 L468-472。
- **实际**：`_eval_marks` 只识别 `sub["has"]` 与顶层 `eq/min/max`，用 `marks_lookup(which, None)` 取 **该侧总层数** 兜底。而 1d §3.1 与 印记定稿 §5.1 的**规范语法**是：
  - C-1 `{"self_marks": {"fire_mark": {"min": 3}}}`（指定印记层数）
  - C-2 `{"target_marks": {"curse_mark": {"max": 1}}}`
  - C-4 `{"marks_set": {"all": ["地","水","火","风"]}}`（齐备）
  - C-5 `{"marks_any": {"min": 3}}`（**种类数**）
  对上述输入：`sub.get("has")` 为 None → 跳过 ids 分支；`sub` 顶层无 eq/min/max → **直接 `return True`**。即：battle 注入 lookup 后（现在必注入），C-1/C-2/C-4 恒满足、C-5 用「总层数」冒充「种类数」。含印记条件的派生步**无条件触发**——与本批要修的旧 P0（1c3 TC-13「未注册字段/求值异常 → 默认不满足、安全失败」被攻穿）行为等价，只是失败形态从「未知键忽略」换成「已知键恒真」。
- **应有**：combo 侧转发 `marks.py` `MarksManager.evaluate`（L366-406）——该实现已正确覆盖 C-1..C-5（指定印记 count_by_name / marks_total 层数 / marks_set has_all / marks_any distinct），或至少按 1d §3.1 规范语法重写 `_eval_marks`；未解析/异常一律 `False`（安全失败，TC-13）。
- **证据**：细化_1d §3.1 C-1..C-5（L146-150）语法示例；marks.py `evaluate` L366-406 为正确参考实现但全库**零调用方**（grep `evaluate(` 仅定义与 eval_condition 转接，无 battle/combo 消费）；battle L1152 `side = attacker if which=="self" else target` 只提供侧映射，无法弥补语义缺失。
- **影响**：1d §3.1 五原语中 4 项已运行路径失效且**反向安全**（静默放行不报错）；AT-14/TC-13 不可达成。**必须先修再加测。**

## 三、🟡 P1 清单

### P1-a 霸体 armor_active 生命周期过早清位 → 同回合对手打断（TC-INT-03/TC-ARM-01/TC-36）不免疫
- **位置**：battle.py L1192-1205（`result.armor` → `_armor_active[attacker]=True` L1193；L1205 `=False` 在伤害结算前即清）。
- **实际**：`player_act` 顺序 = do_action(玩家) → enemy_act()（后手）→ end_turn。玩家（先手）使用 armor 技能时，L1205 在**本次行动结束**就把 `_armor_active["player"]` 清 False；随后敌方同回合盾击（后手）调 `combo_engine().apply_interrupt(..., target="player")` 时 `is_armored("player")` 已为 False → **打断成功**。「玩家用大追斩·霸体、对手同回合盾击 → 打断失败」（1c2 TC-ARM-01 / TC-36 / TC-INT-03）在标准流程中无法成立。
- **应有**：霸体「使用期间」按 1c2 §2.1「双方回合开始声明、结算按行动顺序」与 §2.2 窗口，应至少**保持到当轮对手行动结算完**（回合末 tick 前），而非本行动半径内。battle 注释 L337 自述「行动开始 → 本次结算完成」仅覆盖单行动半径，与验收用例冲突。
- **影响**：霸体核心功能（免疫打断）在 1v1 实战流程零生效。静态推导：需把清位延后到 end_turn（对手行动后），并保留被拒/中途异常路径一致。

### P1-b interrupt「唯一实现走 effects.json」未归口 · 双实现 · 免疫源分裂
- **位置**：battle.py L1187-1191（`combo_engine().apply_interrupt`）＋ L1201-1203（同一技能 effects 又经 `execute_action` 跑 effects.py L1581-1592 L0 interrupt）；combo.py `is_armored` L947-956。
- **实际**：①一个 interrupt 技能结算时会**同时**执行两套打断逻辑：combo 引擎 apply_interrupt（三条件+真正清零连段）与 effects L0 interrupt（只 `combo_state[target]["interrupted"]=True` 置标、**不清连段**，见 effects.py L1588-1591）；②effects 置的 `interrupted` 标记全库**零生产消费方**（grep 仅 effects/combo 注释、test_effects_runtime L360 断言），是写死标志的残桩；③免疫源分裂——combo.is_armored 只查 `armor_active`（L954），effects L0 查 `immune_to_interrupt`（effects L417-420，来自 defenses.immune + 状态 `immune_vs:interrupt`）：同一目标的霸体在两条路径判定不一致；④`is_armored` docstring 声称「 armor_active + 免疫矩阵 immune_vs:interrupt 任一为真即霸体」（combo.py L949-952），代码只实现了第一源。
- **应有**：1c2 §1.3 字段 24「interrupt 唯一实现走 effects.json」/ 1c3 TC-39「tag 仅派生语义标记，打断效果由效果系统 L0 interrupt 唯一实现」——打断的**效果执行**应与攻击窗口判定分离：窗口三条件为 battle 级门禁，清零动作应统一走 effects L0（并把 L0 补成「真清零」），删除 combo 侧重复清零实现；免疫源统一（armor_active 与 immune_vs 归一）。
- **影响**：interrupt 存在两套语义、免疫判定口径不一；`interrupted` 残留标注与 1g1c combo_zeroed_at 审计并存，易被误读为已清零。

### P1-c 技能 effects 仅消费 action 内联，不从 skills.json 解析合并 → 标准 skill 指令与派生形态的 effect 仍不执行
- **位置**：battle.py L1186（`eff_list = action.get("effects") or []`）、L1192（tag 仅 `action.get("tag")`）、L1205 的 armor 也仅 `result.armor`；`_normalize_action` L1549-1551（`skill:xxx` 只产出 `{"type":"skill","skill_id":...,"mult":...}`，**无 effects/tag**）。
- **实际**：全库 grep 无任何调用方在 action dict 里注入 `effects`（commands/router.py 为 M4 签名桩）；`skills.json[skill_id].effects` 的唯一解析源在 combo `resolve_skill`（L769-774），但 battle 从把已解析的技能定义 effects 合入 `eff_list`。即：标准 `player_act('skill:火球')` 路径——tag/interrupt/armor/effects 全部不消费，mark_add/打断/aoe 等**依旧只走伤害通道**；派生形态（form_id 覆写后）也不取 `step.to` 技能定义 effects。
- **应有**：P1-3/P1-4 注解「印记施加/消除、打断等 L0 动作经 execute_action 真实进战斗」（battle L1184）应成立的前提是**先按 skill_id（含派生形)解析 skills.json 并合并 effects/tag/armor 到结算动作**；目前只把"消费端"接上了，解析/装配端断线，注解言过其实。
- **影响**：技能 effects 消费在引擎内实际路径不可达（静态推导），需由调用方手工补 effects 才生效；与「1c2 §1.3 字段 24（skills.json effects → 效果系统）」目标不符。建议 battle 在 `_resolve_combo_action` 内用 `self.combo_engine().resolve_skill(form_id)` 合并 `effects/tag/armor`，或登记为 F-24/M5 递延并在注解注明。

### P1-d 互杀 G4 误删「先手击杀生效→先手胜」分支（定稿 L61 + 1g1c TC-11 被违反）；且 定稿 L62 与 TC-11 存在内部冲突应上报
- **位置**：battle.py `_resolve_battle_end` L664-691（order 分支 L666-674：真互杀一律 `p_dead,e_dead=True,True` → 平局）；`_mark_dead` L621-622 仍置 `player_killed_enemy` 但从此不再参与胜负。
- **实际**：order 基准下双方死亡标记并存 → **无条件平局**（可配 player_loss），`player_killed_enemy` 成为死标记。
- **应有**：战斗数值层定稿 L61「order：…**先手击杀生效 → 先手胜**」与细化_1g1c TC-11（L197）「反伤致双方同轮死亡 | 按 mutual_kill_basis=order：**先手击杀生效→先手胜**；否则 draw」——玩家行动直击杀敌（player_killed_enemy=True）且双方同轮死时**应判玩家胜**；仅「反伤/同归于尽、先手未落直击」才走平局。当前实现把先手胜分支整体删除。
- **定稿内部冲突（需上报不裁决）**：战斗数值层 L62「先手反伤/同归于尽致死且后手亦死 → 平局」与 1g1c TC-11「反伤致双方同轮死亡+先手击杀生效→先手胜」在「反伤双死且先手直击击杀」子场景结论相反。实现方单方归一为平局，属**越权裁决**；应上报主 Agent/仲裁册。
- **附加幻觉**（见 H2）：该分支注释还声称旧行为「…反射双死被判胜，TC-11 语义破坏」，与 TC-11 实际内容（支持先手胜）相反。

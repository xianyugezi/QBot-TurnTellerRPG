## 一、一句话说明

打造一次装备时：**固定项按图纸照抄**；**随机项条数由图纸/包声明**，**内容从相性池抽**
（池 = 通用池 ∪ 主相性专属池；主+副命中联动时专属池被特殊池覆盖）；**装备被动按相性
变体求值**；结果（相性值、属性、套装词条、被动）**打造时冻结进装备实例**，同模板多件互不
相同、以 `uid` 精确区分。

## 二、声明形状（内容包）

### 2.1 图纸（`items`/`equipment` 条目，图纸是物品的一种）

| 字段 | 类型 | 说明 |
|---|---|---|
| `blueprint_fixed_stats` | `list<obj>` | 固定属性，每行 `{stat, value, value_rule?}`；**`value` 照抄**（`value_rule` 缩放见 §六 待裁决） |
| `blueprint_random_stat_count` | `obj` | 随机属性条数 `{min, max}`，`0~2`（可配）；缺省回落 `settings.deep_craft.craft_rules.random_stat_count` |
| `blueprint_fixed_set_affix` | `str` | 固定套装词条 id（照抄） |
| `blueprint_random_set_affix_count` | `obj` | 随机套装词条条数 `{min, max}`，`0~2`；缺省回落 `craft_rules.random_set_affix_count` |
| `blueprint_random_set_affix_pool` | `str` | 可选的候选池收窄（空 = 用相性池解析结果；见 §四 边界 6） |
| `blueprint_passive` | `str` | 固定装备被动 id（引用 `traits.json`）；受相性影响时可变更为其他被动 |
| `affinities` | `obj` | 图纸相性 `{相性id: 数值}`（作为相性累计的**前置贡献**） |

### 2.2 相性四段（`settings` 顶层，打造与深度炼金共用的通用层）

```
settings.affinities[]        {id, name, desc, exclusive_pool}      相性定义 + 专属池引用
settings.affinity_pools[]    {id, kind, desc, entries[]}           kind ∈ common/exclusive/linkage
settings.affinity_linkage[]  {main, sub, override_pool}            主+副联动 → 专属池被覆盖
settings.affinity_reactions[] {kind, from, to, pair, value}        材料互动（冲突/增幅/反转）
```

**池词条行（`entries[]`）**——一个池同时服务随机属性 / 随机套装词条：

| 键 | 类型 | 作用 |
|---|---|---|
| `stat` | `str` | **随机属性候选**：命中该键即属性词条，属性键 = 该值 |
| `value` | `number` | 随机属性的数值（缺省 0；品质/等级缩放见 §六 待裁决） |
| `set_affix` | `str` | **随机套装词条候选**：值 = 套装词条 id |
| `weight` | `number ≥0` | 抽取权重（全 0/缺失 → 取候选首项） |
| `min_level` | `int ≥1` | 装备等级下限（低于则排除） |
| `requires_affinity` | `str`（单相性） | 该词条要求相性（**必须是 `{主, 副}` 的子集**，否则抽不出） |
| `effect_ref` / `value_rule` | `str` | 保留键（`effect_ref` 供后续被动/强化词条；本批消费 `stat`/`set_affix`） |

> `requires_affinity` 的**多相性列表**由引擎 `affinity.affinity_requires` 支持，但字段元数据
> 当前登记为 `str`（门禁更严，保持不变）→ 内容包请用「主专属池 + 联动覆盖池」表达
> 「主+副同时要求」，不要用列表（见 §六 待裁决）。

### 2.3 装备被动（复用 `traits.json`，不新建注册表）

```jsonc
// traits.json 条目（含相性变体的“部分被动”）
{ "id": "<被动id>", "name": "…", "effects": ["<effect id>"],
  "affinity_variants": { "<主相性id>": "<变体被动id>",
                         "<主相性id>|<副相性id>": "<变体被动id>" } }
```

- 有 `affinity_variants` = 可变更；无 = 固定被动（表达原案 §11「部分」）。
- 求值顺序：`"<main>|<sub>"` 优先 → 退 `"<main>"` → 无命中保留原被动（复用
  `affinity.resolve_affinity_effect`，不本地匹配）。

### 2.4 产物实例字段（`ItemInstance`）

| 字段 | 内容 |
|---|---|
| `stats_bonus` | 固定 + 随机属性合并后的 `{属性键: 数值}` |
| `set_affixes` | 套装词条 id（固定 1 + 随机 0~2，去重） |
| `passives` | 本次求值后的被动 id（固定 + 相性变更结果） |
| `affinities` | 本次相性结算值 `{相性id: 数值}`（主/副从中判定；供后续强化/附魔复用） |

> 随机属性的**逐条 provenance（`stat` / `value` / 来源池）**落在打造快照
> `persistent_state.deep_craft_last.random_stats`；实例本体只留合并后的 `stats_bonus`。

## 三、抽取顺序（一次打造内的确定性步骤）

```
1. 材料归一 → 等级 / 品质经验 / 品质等级
2. 品质抽取          ← 注入随机流第 1 个随机数（批41 语义不变）
3. cost 约束
4. 相性累计          图纸相性（前置）+ 材料相性（投入顺序）→ accumulate_affinity
5. 主/副判定         rank_affinities（最高=主、第二=副；并列按 affinities[] 声明序）
6. 池解析            resolve_available_entries(config, main, sub, level)
                     = 通用池 ∪ 主专属池；联动命中 → 主专属池被 override_pool 覆盖；
                       requires_affinity ⊆ {main,sub} 过滤；min_level 过滤
7. 条数抽取          随机属性条数（图纸声明优先，回落 craft_rules）→ 1 个随机数
                     随机套装词条条数（同上）→ 1 个随机数
8. 逐条抽取          按 weight **不放回**抽（同载荷键去重）；随机套装词条排除固定项
9. 被动求值          blueprint_passive → affinity_variants → resolve_affinity_effect
10. 冻结进实例       固定+随机属性 / 套装词条 / 被动 / 相性值
```

随机数消费顺序固定（品质 → 属性条数 → 套装条数 → 属性抽取 → 套装抽取），同种子必同结果。

## 四、边界行为（明确口径）

| # | 情形 | 行为 |
|---|---|---|
| 1 | **无相性**（`main=None`） | `requires_affinity` 非空的词条**全部抽不出**（原案 §12「本质一个池子，没有对应相性就抽不出来」）；通用池中不要求相性的词条仍可抽 |
| 2 | 主/副**并列** | 按内容包 `affinities[]` 声明顺序破平；无声明序则按 id 升序（确定性） |
| 3 | **副相性缺失** | `sub=None`；联动不命中 → 回主专属池；要求副相性的词条抽不出 |
| 4 | 联动命中 | 主专属池**整体被 `override_pool` 覆盖**（原案 §8「特殊联动池也是专属池的一种，触发会覆盖掉专属池」） |
| 5 | 候选不足声明条数 | 实际条数 = `min(声明条数, 候选数)`，**不补空**、不降级到其他池 |
| 6 | `blueprint_random_set_affix_pool` 声明 | 在**已解析候选**中再按 `_pool` 收窄；声明池不在「通用 ∪ 专属/联动」可达集内 → 无候选 = 抽不出（不外开第二条池查询） |
| 7 | 权重全 0/缺失 | 取候选首项（确定性；**不引入未声明概率**），仍逐项去重 |
| 8 | 固定套装词条 | 随机抽取时**排除**固定项，避免重复 |
| 9 | 无 `traits` 定义 / 被动无变体 | 被动 id 原样保留（框架不臆造） |
| 10 | 注入随机源缺失/非法 | 条数取 `min`、抽取退化取首项（确定性，不报错） |

## 五、与既有 `forge_sets`（套装档位/激活）的关系

**核查结论：产物上的套装词条目前无法被既有套装结算识别——如实登记为缺口。**

- 既有套装结算（`core/forge_sets.py` + `core/forge_set_skills.py`）的件数来源是
  **锻造节点 id**：`player["set_tracker"]`（族 id→件数）优先，否则从
  `equipped`/`equip_nodes`/`equip_snapshot` 取条目的 `node_id`/`id`（`forge_sets.py:116-118,687-713,730-739`），
  与 `forge.json sets[].pieces` 求交。
- 深度打造产物的身份是 `ItemInstance`（`item_id` + `slot` + `uid` + `set_affixes`），
  **没有锻造节点 id**；`EquipmentSlot` 只存 `item_id/name/slot_level/locked/gems/uid`，
  也不携带套装词条。因此「同名套装词条件数 → 激活」这条链**当前未接通**。
- 文档化的 `INS-07 set_tag` 消费方**未实现**（全仓 `grep set_tag` 仅命中注释）。
- **建议复用路径（待裁决后再接线）**：在唯一已穿戴件枚举点（`equip_mods._worn_defs`，
  与副手失活同源）按穿戴实例的 `set_affixes` 归并族件数写 `set_tracker`，即可让既有
  `set_lookup`/`resolve_set_skills` 零改动识别打造套装。**前置待裁决**：套装词条 id 与
  `forge.json` 套装族 id 的对应关系（原案未定义；是否要求同名，或需一处映射声明）。

## 十、批 44：投入概率暴击（内容作者向 · 彩档品质 10 可达性）

> 上游：`docs/深度打造_决策记录.md` §七（用户裁定「投入概率暴击」解彩档 q10 可达性，
> **不**拉高 cap、**不**强制扩材料表）；`打造_材料表与图纸表_草案v2.md` §3。
> 引擎落点：`qbot_rpg/core/deep_craft.py::quality_exp`（判定期在该函数内，品质等级
> 判定之前）；随机源 = 批40 玩家级随机流（`ctx["rng"]`，可注入确定性 RNG 复现）。

### 10.1 一句话

投料提交时按**图纸档**掷一次概率，命中则给**额外品质经验**（倍率可配），使高档图纸有机会
冲破常规经验上限达到**品质 10**。全部参数包声明、可调；**缺省关闭**——不声明时引擎不掷、
不消耗随机数，行为与既有**逐字段一致**。

### 10.2 参数表（`settings.deep_craft.craft_rules.quality_exp_crit`，R5 落点裁定）

| 键 | 类型 | 默认 | 范围 | 说明 |
|---|---|---|---|---|
| `enabled` | bool | `false` | — | 总开关；**缺省关**（不声明 = 零变化，且不消耗随机数） |
| `grades` | `list<str>` | `[]` | 图纸档 id | 适用档；**空 = 全档**，可只开高档（如 `["金","彩"]`） |
| `chance_by_grade` | `obj` | 铜 .15 / 银 .10 / 金 .07 / 彩 .05 | 每值 0~1 | **逐档暴击概率**（低档更高、高档更低，§七建议值，待实测校准） |
| `chance_default` | number | `0.05` | 0~1 | 档未在 `chance_by_grade` 声明时的概率 |
| `mult_by_grade` | `obj` | 铜/银/金/彩 = `2.0` | 每值 ≥0 | **逐档暴击倍率** |
| `mult_default` | number | `1.0` | ≥0 | 档未声明时的倍率（1.0 = 不加成，只记暴击标记） |
| `additive_exp` | number | `0.0` | 任意 | 命中时在倍率之外追加的**固定**品质经验 |
| `applies_to` | enum | `quality_exp` | `quality_exp` | 作用目标（当前仅品质经验） |
| `affects_quality_level` | bool | `true` | — | `false` = 暴击经验只展示，**品质等级仍按暴击前经验**判定 |
| `rolls_per_craft` | int | `1` | 1~2 | 每次打造掷数；任一命中即暴击（>1 显著抬高期望） |
| `exp_cap` | str/num | `last_threshold` | `none`/`last_threshold`/数值 | 生效档位最终经验封顶；`last_threshold` = 取阈值表末项 |
| `rng_stream` | enum | `player` | `player` | 随机流标记（引擎只走注入的玩家级随机流） |

> **档 id 必须与 `blueprint_grades[].id` 一致**（引擎按图纸 `blueprint_grade` 查表，不认
> 任何固定档名）。若内容包用自有档位 id，请在自己的 `chance_by_grade` / `mult_by_grade`
> 里声明，或设 `chance_default` / `mult_default`（**默认 `mult_default=1.0` 不会加成**）。

### 10.3 声明示例

```jsonc
// settings.deep_craft.craft_rules
"quality_exp_crit": {
  "enabled": true,
  "grades": ["彩"],                       // 只开彩档；[] = 全档
  "chance_by_grade": { "铜": 0.15, "银": 0.10, "金": 0.07, "彩": 0.05 },
  "chance_default": 0.05,
  "mult_by_grade": { "铜": 2.0, "银": 2.0, "金": 2.0, "彩": 2.0 },
  "mult_default": 1.0,
  "additive_exp": 0.0,
  "applies_to": "quality_exp",
  "affects_quality_level": true,
  "rolls_per_craft": 1,
  "exp_cap": "last_threshold",
  "rng_stream": "player"
}
```

### 10.4 语义与随机消费顺序

```
1. 材料归一 → 等级 → 暴击前品质经验 QE0 = Σ(品阶基数 × 相性 × 件数边际) × 种类奖励 × 互动
2. 投入暴击判定        ← 仅当 enabled 且档位适用且概率 >0 时消费随机数（rolls_per_craft 个）
                        命中：QE = QE0 × mult(+档) + additive_exp；未命中：QE = QE0
3. 经验封顶            生效档位：QE = min(QE, exp_cap)（last_threshold → 阈值末项）
4. 品质等级            按 exp_for_level（affects_quality_level=false → 用 QE0）判级
5. 品质抽取            注入随机流（批41 首位随机语义在**未启用暴击时不变**）
```

- **不生效/未命中不改变既有随机序列**：`enabled=false`、档位不适用、概率 ≤0、`rng` 缺失
  时**一次随机数都不消费** → 品质抽取与后续词条抽取与现状一致。
- 启用后掷数**全部消费**（`rolls_per_craft` 个），任一命中即暴击 → 消费次数确定，同种子同结果。
- 暴击只加品质经验：**不改等级、不改 cost、不改相性累计**。

### 10.5 边界行为

| # | 情形 | 行为 |
|---|---|---|
| 1 | `enabled=false` / 未声明 | 不掷、不消费 → 计划逐字段等于现状（对拍断言：显式关 == 缺省） |
| 2 | 档位不在 `grades` | 不生效、不消费 |
| 3 | 概率 ≤0 | 不掷、不消费 |
| 4 | `applies_to ≠ quality_exp` | 不生效（保守，不外溢到其他计算） |
| 5 | `mult_default=1.0` 且档未声明倍率 | 记为暴击但经验不加成（作者须显式声明倍率） |
| 6 | `exp_cap=last_threshold` 而阈值表为空 | 不封顶 |
| 7 | `affects_quality_level=false` | `quality_exp` 为暴击后值，品质等级按暴击前值 |
| 8 | `rng` 缺失/非法 | 不掷（退化为不暴击），不报错 |
| 9 | `rolls_per_craft>2` | 校验器红拦（R-2，范围 1~2） |

## 十一、批 45：装备占比校准（内容作者向 · 面板预算与怪物数值倍率）

> 上游：`docs/深度打造_决策记录.md` §三 补充 1（用户 2026-09-19：装备占比 → 60%，其他数值不动）

### 11.1 一句话

把「装备这一份预算」乘以可配倍率（veinborn 校准 ×2.25 → 装备份额 8→18、占比 40%→60%、

### 11.2 参数表（`settings` 顶层）

| 键 | 类型 | 默认 | 范围 | 说明 |
|---|---|---|---|---|
| `panel_budget.white` | number | 7 | ≥0 | 面板预算·白值份（占比分母；**冻结**） |
| `panel_budget.equip` | number | 8 | ≥0 | 面板预算·装备基准份；有效份 = ×倍率 |

- **怪物侧**：只缩放 hp/atk 与防御补偿；mp/mag/spd/foc/lck/agi 与战斗词条保持原值

## 十二、批 46~48：符文附魔（内容作者向 · 三阶 / 跨装备类型 / 2·3 阶效果 / 3 合 1）

> 上游：原案 `打造系统_原案_20260919.md` §9；口径 `/root/deliverables/符文系统_实现口径.md`
> §〇 结论 7/8、§三、§五 43-A~D；决策 `docs/深度打造_决策记录.md` H1/H2 + §十一~§十三。
> 数据模块：`content/<包>/runes.json`（list）。引擎：`core/runes.py`（纯解析）、
> `core/jewel.py`（孔位/镶嵌）、`core/equipment.py`（数值聚合）、`core/upgrade.py`（3 合 1）、
> `core/battle.py`（2/3 阶战斗接线）。**总闸 = `settings.deep_craft.enabled`（默认关）。**

### 12.1 一条符文 = 一个条目（`runes.json`）

```jsonc
{
  "id": "rune_x",            // 必填、模块内唯一（命名空间独立于 items.id）
  "name": "…", "icon": "…", "desc": "…",
  "tier": 2,                 // 必填 1/2/3（独立刻度，禁止借用 quality 四档）
  "family": "…",             // 必填；同族才允许互为 3 合 1 输入
  "by_equip_type": {         // 差异表：default 必填；键 = items.type
    "default": { "stats": { "atk": 6 } },
    "weapon":  { "stats": { "atk": 9 } }   // 命中类型条目「顶层浅覆盖」default（stats 整块替换）
  },
  "effects": [ { "effect": "…", "trigger": "…" } ],  // 2/3 阶效果（见 12.3）
  "bias": { "affinity": "…", "bonus_pct": 0 }        // 3 阶偏向（见 12.4）
}
```

- `stats` 键**只能**取 `data/gear_stats.py` 的 `GEAR_NUMERIC_KEYS`（`_pct` 后缀 = 百分点）；
  自造键由校验器 **RUNE-05** 红拦。
- 一阶符文：`default.stats` 必须非空（**RUNE-05**）；数值经 `aggregate_bonus` 与普通装备词条
  **同层** flat/pct 汇入面板与战斗（副手折算件按副手失活 → 符文不生效）。
- 类型键取 `items.type`（Q5 默认项①）；未声明的类型 → 回落 `default`。

### 12.2 3 阶偏向性（`bias`，默认口径 = 偏向某相性）

```jsonc
"bias": { "affinity": "fire", "bonus_pct": 50 }
```

- 宿主装备的**主/副相性**（`items.affinities` → 相性通用层 `core/affinity.rank_affinities`）
  命中 `affinity` → 该符文数值贡献 **× (1 + bonus_pct/100)**；未命中 / 无 `bias` → 原值。
- `bonus_pct` 可 0（等价未声明）/可负（偏科惩罚）。
- 校验：`affinity` 必填非空（**RUNE-07 红拦**）；`bonus_pct` 非数红拦；低阶声明 `bias`、
  未知相性 id → 黄提示（`settings.affinities` 已接线时才查引用）。

### 12.3 2/3 阶特殊效果（`effects` + `trigger`）——两条铁律

```jsonc
// runes.json 里的符文条目：声明「在什么时点、引用哪个效果」
"effects": [ { "effect": "fx_grievous_on_hit", "trigger": "on_hit" } ]

// effects.json 里被引用的「效果容器」：只放 actions，**不要写 trigger**
{ "id": "fx_grievous_on_hit", "class": "special",
  "actions": [ { "type": "status_apply", "status": "s_grievous", "target": "enemy" } ] }
```

1. **`trigger` 只写在符文引用条目上**，取 `core/event_dispatcher.EVENT_POINTS`
   （`battle_start` / `action_start` / `on_hit` / `turn_end` …）。效果容器**不带 `trigger`** →
   才不会被全局事件分派器对所有战斗单位触发（否则敌方也会获得该符文效果）。
2. 效果内容仍由 `effects.json` 定义（口径 §三.2：符文不得内联执行语义）；
   `overrides` 可按符文覆盖参数；`target`（`self`/`enemy`）可写在引用条目上。
3. 只有**符文穿戴者一侧**在这些时点触发；副手折算件经 `active_rune_sockets` → 不触发。
4. 触发计数沿用既有上限（每次行动 10 / 每场 99，`EffectRuntime.config` 可配）。

**例 ①「重伤」（治疗削减）** —— 给目标挂一个带 `heal_taken` 修正的状态：

```jsonc
// statuses.json
{ "id": "s_grievous", "name": "重伤", "category": "harm",
  "stack_frame": "single", "duration": { "turns": 3, "charges": 0 },
  "actions": [ { "type": "stat_modifier", "stat": "heal_taken", "value": -40 } ] }
```

被该状态覆盖的目标受到治疗时，治疗量 **×(1 + heal_taken/100)**（-40 → 治疗仅 60%）；
下限 0（不反向扣血），封顶复用 S6 `max_boost_pct`（默认 ±100，可配）。该键为引擎语义键
（`core/effects.HEAL_TAKEN_STAT`），正=受治疗增幅、负=削减，数值全由内容声明。

**例 ②「每次攻击获得物攻加成，上限 n」** —— 叠层状态 + `action_start` 引用：

```jsonc
// statuses.json：层数上限 n = max_stack（包声明；不写则回落引擎 stack_default_max）
{ "id": "s_atk_build", "name": "蓄势", "category": "buff",
  "stack_frame": "stack", "max_stack": 5, "duration": { "turns": 3, "charges": 0 },
  "actions": [ { "type": "stat_modifier", "stat": "atk", "value": 4 } ] }

// effects.json
{ "id": "fx_atk_build", "class": "special",
  "actions": [ { "type": "status_apply", "status": "s_atk_build", "target": "self" } ] }

// runes.json
"effects": [ { "effect": "fx_atk_build", "trigger": "action_start" } ]
```

每次攻击 +1 层 → 加成 = 层数 × `value`（百分点，先按层求和再走 S6/S7 封顶）；
达 `max_stack` 后不再增。**上限一律包声明**（`max_stack`）。

> 实现注记（内容作者无须关心）：既有引擎 S5「同来源同侧只保留一个」下同来源不会叠层，
> 故符文接线侧对每次施加使用区分来源 `侧@行动序号`，让 S3 stack 真正逐次累层；
> `_aggregate_boost` 已按 `stacks` 乘算（批48 修正，含逐字段回归对拍）。

### 12.4 3 合 1 进阶（`recipe.json`，`kind=upgrade`）

```jsonc
{ "kind": "upgrade", "subtype": "rune_upgrade", "id": "rcp_rune_1_2",
  "inputs": [ { "item": "r_t1", "count": 3 } ],
  "output": { "item": "r_t2", "count": 1 },   // 可加 "rune_tier": 2 显式声明产出阶（回退）
  "cost": { "gem": 10 },
  "synth_allowed": true }                      // false = 深度未解锁 → 拒绝
```

- 3×同阶同 id → +1 阶；**禁跳级**（产出阶必须 == 输入阶+1）、**满阶拒绝**、**必成**。
- 闸：`synth_allowed=false` → `runes_deep_locked`；`settings.deep_craft.enabled` 非 true
  （且 ctx 带该段）→ `runes_disabled`；非法/不足/产出 hook 失败 → **零副作用**（原子回滚）。
- 越阶/跳级/不同 id/件数不足一律拒绝（`rune_skip_tier` / `rune_input_mismatch` / …）。
- 1→2→3 逐阶：3×一阶 → 二阶；3×二阶 → 三阶（链终点，无更高阶）。

## 十三、批 50：特效轴地基（内容作者向 · 一条轴怎么写、两个方向怎么填）

> 口径：`特效整理设计_1_修正轴全集.md`（轴全集）+ `特效整理设计_3_落点与分期.md`
> §1.0/§1.2 + 决策记录 §十三「双向修正轴优先」。
> **本批只登记：键族 + 声明段 + 校验 + 编辑器可见，不接任何消费点**——作者现在可以
> 写这些轴、编辑器看得见、校验器会拦错，但**引擎还没读**（接线批次在后续批）。
> 这就是为什么每条轴都注明「唯一消费点（待接）」：**没写消费点的轴不登记**，
> 免得出现「作者写了不生效」的陷阱键（`cooldown_reduction_pct` 的教训）。

### 13.1 一句话

**一条轴覆盖双向玩法**：减疗与增疗不是两条轴，是**同一个轴的两个取值**。

### 13.2 作者怎么写（装备/物品词条）

在 `items.json` / `equipment.json` 的条目顶层直接写轴键即可（与 `atk`/`dfn_pct` 同处）：

```jsonc
{ "id": "heavy_gauntlet", "name": "重伤护手", "slot": "weapon",
  "healing_received_pct": -50 }        // 受疗 ×0.5：被治疗打五折
```

**书写口径 = 百分点增量**（不是乘数、不是百分比正数）：

```
有效值 = 基准值 × (1 + 轴值 / 100)
```

| 想表达 | 写法 | 等价的乘数说法 |
|---|---|---|
| 受疗打五折（重伤） | `healing_received_pct: -50` | ×0.5 |
| 原样（默认） | 不写 / `0` | ×1.0 |
| 受疗加半（增疗） | `healing_received_pct: +50` | ×1.5 |
| 禁疗 | `healing_received_pct: -100` | ×0 |

**加算轴**（层数上限、行动条推动）不是百分比，直接写差值、键名**没有** `_pct` 后缀：
`stack_cap_delta: 2` = 层数上限 +2 层。

### 13.3 一条轴的两种填法 = 两个方向（不要建两条 trait）

`重伤` 与 `强化治疗` 是**同一条轴**的两个取值。内容侧**不得为两个方向各建一条 trait**
（否则相性池与图鉴会重复计数）：

| 预设 | 填法 |
|---|---|
| 重伤 | `healing_received_pct: -50` |
| 禁疗 | `healing_received_pct: -100` |
| 强化治疗 | `healing_received_pct: +50` |
| 易伤 | `damage_taken_pct: +30` |
| 铁壁 | `damage_taken_pct: -30` |

### 13.5 范围与默认值是可配的（不写死）

在 `settings.json` 加 `effect_axes` 段即可覆盖**建议缺省**（不改引擎代码）：

```jsonc
{ "effect_axes": {
    "healing_received_pct": { "min": -300, "max": 500, "default": 0,
                              "display": { "mode": "mult", "label": "受疗修正" },
                              "stack": "add" } } }
```

  例如 `immune_dmg`（免伤 30%）⇔ `damage_taken_pct: -30`。

## 十四、批 51：触发归属与事件补点（内容作者向 · 触发型效果怎么声明）

> 口径：`特效整理设计_3_落点与分期.md` §二「批 49」（旧编号 = 本批，本批叫**批51**）
> + `特效整理设计_1_修正轴全集.md` §1.8 **I01**（触发时点 ＋ 持有人归属过滤，P0 第 1 项）
> + `装备被动_实现口径.md` §3.3（归属过滤方案 A）。
> 本批是**装备被动系统的前置**：只补「触发能不能按宿主正确生效」这块地基，
> **不实现**被动身份解析 / 相性变体 / 生效集缓存 / 展示（那些属后续批，见 §14.6）。

### 14.1 一句话

**带 `trigger` 的效果不再对所有单位全局误触发**：装配层把「本侧拥有哪些效果」
写进战斗单位，引擎只在**其宿主侧**的那个时点触发它。

### 14.2 触发型效果怎么写（三段：时点 → 归属 → 条件）

```jsonc
// ① effects.json：效果本体（class=special + actions 容器；既有机制，不新开）
{ "id": "blood_feast", "name": "饮血", "type": "special",
  "trigger": "on_kill",                 // ← 时点（见 14.3 清单）
  "chance": { "mode": -1 },             // ← 概率（可省；三态复用既有 chance 口径）
  "actions": [ { "type": "heal", "value": 30, "target": "self" } ],
  "condition": { "self_hp_pct": { "<": 50 } } }   // ← 可选条件门控（复用 condition_engine）

// ② traits.json：命名被动 = effects 引用（既有注册表）
{ "id": "passive_blood_feast", "name": "饮血", "effects": ["blood_feast"] }

// ③ items.json / equipment.json：装备带哪些被动（实例 passives 由打造写入）
{ "id": "crimson_blade", "name": "赤刃", "slot": "weapon" }
```

**归属**由「这件装备实例带哪些被动」决定，不需要在效果条目里写任何归属字段：
装配层按**已穿戴件实例的 `passives`**（批40 `uid` 精确定位）→ `traits.effects`
→ 效果 id 集，写进该侧战斗单位；引擎据此把 `trigger` 限制在宿主侧。

### 14.3 事件时点清单（`EVENT_POINTS`，唯一源 `data/event_points.py`）

| 时点 | 触发侧 | 何时派发 |
|---|---|---|
| `battle_start` / `battle_end` | 两侧各一次 | 开战 / 收尾 |
| `action_start` / `action_end` | 行动者 | 每次行动开始 / 收尾 |
| `turn_start` | 行动者 | 行动者回合开始 |
| `turn_end` | — | **CTB 已删除回合单位 → 不再派发**（写法保留仅为兼容） |
| `status_gain` / `status_lose` | 状态持有侧 | 状态获得 / 消失（含过期） |
| `mark_gain` / `mark_lose` | 印记持有侧 | 印记获得 / 消失 |
| `death` | **死者侧** | 任一侧死亡 |
| `on_kill` | **击杀者侧** | 我击杀敌（**批51 新增**） |
| `revive` | 复活侧 | 复活 |
| `on_attack` / `on_hit` / `on_skill` | 攻击方 | 普攻 / 命中 / 技能 |
| `season_change` | 两侧 | 换季 |

**`death` 与 `on_kill` 不得混用**（本批最重要的语义区分）：

| 想表达 | 写 | 派发给谁 |
|---|---|---|
| 我击杀敌人时回血 / 叠层 / 免冷却 | `trigger: "on_kill"` | **击杀者**（1v1 的另一侧） |
| 我死亡时爆炸 / 给对手挂状态 | `trigger: "death"` | **死者自己**（动作 `target` 相对死者侧） |

两者都在**唯一死亡判定点**（`battle._death_check_side`）派发，由死亡标记门控 →
**每次击杀恰好一次**；同归于尽（击杀者也已死）或战斗已结束 → 不派发 `on_kill`。

### 14.4 归属规则（什么时候过滤、什么时候不过滤）

| 本场战斗 | 引擎行为 |
|---|---|
| **两侧都没声明归属集**（既有内容） | **全库扫描** = 本机制引入前的旧行为，**逐字段零变化** |
| **任一侧声明了归属集** | 该侧候选 = **自己拥有的** ∪ **未被任何一侧认领的**（全局效果） |

- 第二行里「自己拥有的」= 该侧装备被动展开的效果；「未被认领的」= 没有任何战斗单位
  声明拥有的效果，仍按**全局效果**对任意侧触发（避免归属过滤把既有全局触发**静默吞掉**）。
- 因此：**A 装备的触发只在 A 身上生效**，B（哪怕带同类效果）不会串到 A 的触发上；
  而没有被任何装备认领的全局事件效果（如季节/环境类）**照常对双方触发**。
- 旧内容（无 `passives`）→ 战斗单位不带归属键 → 走第一行，**回归逐字段一致**。

### 14.5 校验器会拦什么

| 情形 | 结果 |
|---|---|
| `trigger` 写了框架**未登记**的时点（拼错 / 自造 / 未来时点） | **黄提示**（Y-19，不阻断）——该效果**永不触发**，提示里带已知时点全集 |
| `trigger` 不是字符串 | **红拦**（R-1） |
| 缺 `trigger` / 空串 | 放行（非事件型效果） |

覆盖两处声明面：`effects.<idx>.trigger` 与 `runes.<idx>.effects.<j>.trigger`。

### 14.6 本批**做到哪**、**留什么给后续批**（与装备被动系统的边界）

**本批做**（P0 缺口收口）：
1. 归属过滤（`owner_effect_ids` / `claimed_effect_ids`）；
2. 事件补点 `on_kill`（击杀者侧）；
3. **最小接线**：装备实例 `passives` → traits `effects` → 战斗单位归属集 → 按宿主触发。

**本批不做**（属装备被动系统的后续批，别在本批找）：

## 十五、批 52：治疗与承伤双向轴（内容作者向 · 三条轴怎么真生效）

> 口径：`特效整理设计_1_修正轴全集.md` §5-D2（X17/X16 治疗双向）+ §5-D3（X02 承伤收敛）
> + `特效整理设计_3_落点与分期.md` §二「批 50」（旧编号 = 本批，本批叫**批52**）
> + `特效强度预算_设计.md` §四（红线守护复算清单）。
> 批50 把三条轴**只登记、不接引擎**（作者写了不生效）；本批**接线**——现在写了真生效。
> 同一批把 `heal` 的**唯一收口**建起来（批48 的重伤通道并入），并放开**负治疗**。

### 15.1 一句话

**治疗和承伤各是一条双向轴**：同一条轴，`<0` 是减半/减伤、`>0` 是增幅/易伤；
不配置 = `0` = ×1.0，引擎逐字段零变化。

### 15.2 治疗怎么写（受疗 / 出疗是两个实体上的字段，不合并）

```
治疗量 = 基础治疗 × (1 + 受疗修正/100) × (1 + 施疗修正/100)
        受疗 = 我受到的治疗（被治疗方身上的 `healing_received_pct`）
        施疗 = 我造成的治疗（施疗方身上的 `healing_done_pct`）
```

| 想表达 | 写在哪 | 值 | 效果 |
|---|---|---|---|
| 重伤 | 受疗方 | `healing_received_pct: -50` | 受疗 ×0.5 |
| 禁疗 | 受疗方 | `healing_received_pct: -100` | 受疗 ×0（治疗归零） |
| **负治疗（反转）** | 受疗方 | `healing_received_pct: -200` | 受疗 ×(-1)：**治疗转伤害** |
| 强化治疗 | 受疗方 | `healing_received_pct: +50` | 受疗 ×1.5 |
| 施疗削弱/增幅 | 施疗方 | `healing_done_pct: -50 / +50` | 我造成的治疗 ×0.5 / ×1.5 |

**反转开关 = 声明下界**（不另设布尔）：包在 `settings.effect_axes.healing_received_pct.min`
声明下界；默认 `-200` = 允许反转，声明 `min: -100` = 关反转（治疗到 0 为止）。

**旧键 `heal_amp_pct` 已归并**（批43 悬空键 → 现在真生效）：它在 pct 层等价换算为新轴
`healing_done_pct`（`本轴值 = +1 × 旧值`），旧键自身路由不动（`pct["heal_amp"]` 仍在）。

**重伤（批48 状态通道）与新轴同轴相加**，不是两次乘：
`受疗 = clamp(状态 heal_taken 合计(经 S6 封顶) + healing_received_pct, 声明 min, 声明 max)`。
例：状态 −40 + 轴 +50 = +10 → 治疗 ×1.1（不是 ×0.6×1.5 = ×0.9）。

**多源一次改全**（唯一收口 `effects.heal_apply`，`effects.py:1760`）：heal 原子
（`:2050`）/ absorb_heal（`:1303`）/ regen（`:1350`）/ lifesteal（`:1994`）/
`battle.absorb_hp` 吸血（`battle.py:4852`）——**只改一处必漏**，本批五处全接。

### 15.3 承伤怎么写

`damage_taken_pct` 是**主乘区**（`<0` 减伤 / `>0` 易伤），与免伤旧键 `immune_dmg`
**归并到同一处求值**（`battle._damage_taken_mult`，`battle.py:4120`）：

```
承伤乘区 = [1 + (damage_taken_pct − clamp(immune_dmg, 0, 100)) / 100] × status_damage_mult?
```

- `immune_dmg: 25` ⇔ `damage_taken_pct: -25`，**只乘一次**（不双计）；
- 两者并存时**同轴相加**（`-25` 与 `immune_dmg 25` → ×0.5），绝不叠乘成 ×0.5625；
- 读时按 `settings.effect_axes.damage_taken_pct` 的 `min/max` 钳制（不写死）；
- status `damage_mult`（倒地增伤）在**同一函数内**并入（`include_status=broken_hit` 门控沿用
  既有破位窗口）→ 三路来源一处求值、破位路径一次整型截断。

**收敛边界（如实登记）**：`effects` 的 `mitigation` 阶段按批50 `consumer_note` 明文
**保持独立**（它只做减伤、与护盾/保底伤害交织，混入易伤会错）。**唯一受影响的既有组合 =
「破位 + 非零 `immune_dmg`」**：截断序由「先破位截断、再免疫四舍五入」并为一次截断，
可能相差 ±1 点（实测 |差| = 1）；无 `immune_dmg` 且无轴时与旧序**逐位一致**、实机逐字段零变化
（`docs/深度打造_决策记录.md` §十八.2 对拍表 + §18.3 斩回复算）。

  "slot": "armor",

**书写口径 = 百分点增量**（不是乘数）：`有效值 = 基准 × (1 + 轴值/100)`；

## 十七、批 55：特效强度预算（内容作者向 · 特效词条用多少、超了会怎样）

> 依据：`docs/特效强度预算_设计.md` §二方案 B / §三推荐 / §四 红线清单。
> 配套测量：`docs/批55_特效强度预算_测量报告.md`；复跑：`scripts/batch55_dual_ruler.py`。

### 17.1 一句话

面板 60% 只算 `atk/dfn/hp`（`PANEL_AXIS_KEYS` 冻结）；**特效轴不进 `equip_share`**。
本批给内容作者一只**闸**：把生效的特效轴折成「综合等效%」，按怪物档位判是否超限；
外加一个**只报数**的真实装备占比。**不配置 = 完全不生效**（与引入前逐字段一致）。

### 17.2 内容包里怎么写

`settings.effect_budget`（**整段不写 = 关闭**）：

```json
{
  "effect_budget": {
    "enabled": true,
    "aggregate": "geometric",
    "cap_equiv_pct": 8,
    "tier_mult": { "normal": 1.5, "elite": 1.0, "boss": 0.625 },
    "gate_mode": "warn",
    "unknown_axis": "warn",
    "report_effective_share": true
  }
}
```

- `enabled`：总开关；`false`/不写 → 聚合器返回 0、gate 静默（**零行为**）。
- 档位上限 = `cap_equiv_pct × tier_mult[tier]`；缺省 = **普通 12% / 精英 8% / Boss 5%**。
- `gate_mode`：`off` 静默 / `warn` 黄提示（缺省）/ `red` 红拦（拒绝条目）。
- `unknown_axis`：内容用了**权表没登记**的特效轴时的动作（与越界取更严者）。
- `report_effective_share`：是否输出 `effective_equip_share`（A1 度量，只报数）。

### 17.3 等效怎么算（权表 = 坐标表，不是加法定律）

```
单轴等效% = 轴值 / calib × 校准等效%
输出等效 = Σ 单轴 output 分量；生存等效 = Σ 单轴 survival 分量
综合等效 = geometric: √((1+输出)(1+生存)) − 1      （或 product / max）
```

缺省权表（可被 `axis_weights` **逐键覆盖 / 追加**）：

| 轴 | calib | 输出等效 | 生存等效 | 出处 |
|---|---|---|---|---|
| `cooldown_pct` | −20 | +6.8% | — | 轮转模型 C=4 / k=0.4 |
| `damage_taken_pct` | −25 | — | +33.3% | `1/(1−0.25)` |
| `absorb_hp` | 15 | — | +43% | 净损血率模型（overheal 封顶取下沿） |
| `healing_received_pct` | 15 | — | +5% | 保守下沿 |
| `damage_dealt_pct` | +10 | +10% | — | 终伤乘区线性 |

> **保守提示**：求和口径把减伤与吸血的生存收益**线性相加**（高估叠加），闸**偏严**。
> 未登记的**已登记特效轴** → 按 `unknown_axis` 处理；`atk/crit` 等普通词条**完全忽略**。

### 17.5 只报数：真实装备占比（A1）

`effective_equip_share = e/(pool+u)`；`u = 综合等效%/100 × pool`。
面板 `equip_share = 60%` 不变，但把特效折算进去后，典型生存 build 的真实占比约
**43.7%**（`--effects` 会打印）。这一列**只诊断、不改战斗数值**。

### 17.6 备用杠杆（方案 C，缺省不用）

`settings.monster_scaling.effect_hp_mult` / `effect_atk_mult`（缺省 **1.0**）与

**本批不配置**——它向无特效玩家收税，报告 §三.1 明确不单独作主方案。

`settings.effect_axes`（可只写要覆盖的轴；整段不写 = 用框架建议范围）：

```json
{ "effect_axes": { "action_speed_pct": { "min": -80, "max": 400 } } }
```

装备 / 物品词条直接写轴键（百分点增量，D1 口径）：

```json
{ "action_speed_pct": 20 }     // 速度 ×1.2（提速）；-20 = ×0.8（迟缓）
```

| 项 | 口径 |
|---|---|
| 方向 | **双向**：`>0` 提速 / `=0` 原样 / `<0` 迟缓 |
| 单位 | **百分点增量**（`有效速度 = 白值 × (1 + pct/100)`）——不是倍率 |
| 范围 | **可配**：由 `settings.effect_axes.action_speed_pct.min/max` 声明（缺省 `-80 ~ 400` = ×0.2~×5.0） |
| 落点 | CTB 公式**分母**：`time_cost = recovery × speed_reference / max(effective_speed, min_speed) + delay`（复用 `ctb_rules.time_cost`，不新开管线；`min_speed` 下限保护沿用） |
| 零变化 | 未配置 / `0` → 有效速度 = 白值（逐字段一致） |

> **别同时写后摇**：`action_recovery_pct` 与 `action_speed_pct` 数学互为倒数，二者并存会让
> 作者叠加导致**指数级加速**。按 D2 裁决只保留行动速度；写了后摇轴 → 校验器黄提示
> `effect_axis_deprecated`（点名改用 `action_speed_pct`），**不硬拦**。

### 18.3 过量治疗怎么写

`settings.overheal`（**整段不写 = 关闭**）：

```json
{ "overheal": { "enabled": true } }
```

| 状态 | 满血时治疗 100 | 说明 |
|---|---|---|
| 缺段 / `enabled:false`（缺省） | HP 不变（`min(max_hp, hp+heal)`） | **与现状一致**：过量部分**丢弃** |
| `enabled:true` | HP = `max_hp + 100` | 按 E5「治疗可否超过最大 HP」= **保留** |

- 只对 **HP** 生效（E5 只讲「最大 HP」；MP 治疗仍按 `max_mp` 封顶）。
- **待裁决（设计未写清，不得臆造）**：
  - **BV-1 过量上限**：E5 只给布尔，未给「最多超多少」→ 本批**不设额外上限**（待裁决）。

    护盾阶段（伤害链②）原样不动（待裁决）。
- 5 处治疗落点统一收口 `core/effects.apply_heal_to_hp`：技能 `heal` 动作 / 行动收尾
  `absorb` 回复 / 再生 `regen` / 主动 `lifesteal` / 战斗常驻吸血 `absorb_hp`。

### 19.2 淬炼怎么配（`enhance.json → temper`）

- **开关** `enabled`（缺省 false）。**上限**：`total_cap = 装备等级 × cap_per_level`
  （默认 6；等级 35 → 总 210 点）；单项 = `floor(总 × per_stat_cap_ratio)`（默认 0.5 →
  105 点）。可用 `total_cap` / `total_cap_by_level` / `per_stat_cap` 逐级/逐属性覆盖。
- **装备等级来源**：实例新字段 `ItemInstance.required_level`（打造时由
  `deep_craft.plan_craft` 的 `level` 写入，D12）；旧档/非打造为 0 → 上限 0（不可淬炼），
  可用 `temper.default_level` 兜底。
- **属性**：`allowed_stats` 留空 = 该件已有属性键（∩ 框架数值键）；`value_type` flat/pct；
  每点加值 `value_per_point`（默认 1.0）。
- **消耗**：`cost_per_point.essence` 默认 **1593**（报告 §4.6 反解平衡点，依据见 19.5）；
  `cost_per_point.currency` 为第二道闸；`cost_growth`（0–1）让后期每点更贵；`stat_weight`
  逐属性消耗权重。
- **状态与分账**：淬炼分配存 `ItemInstance.temper_alloc`（**与 `enhance_level` 分账**），
  数值增量经 `core/temper.materialize_temper` **幂等物化进 `stats_bonus`** → 面板聚合/
  战斗桥/展示零改动。重放/重连不双计（以 `temper_alloc` 为准的差值物化）。
- **重置**：`reset_allowed`（默认 true）= 可重置、**不返还**精粹（决策记录 D2 建议）。

### 19.3 分解回收怎么走（`settings.forge → essence_rate`）

- **实例级路径**：`/分解 <打造装备名>`（或 `名称#uid前缀` / 完整 uid）→ 按 **uid 实例**
  分解（既有 `/分解` 按 `item_id` 分解不了独有实例，报告 C-4/R-3）。**仅当
  `essence_rate.enabled=true` 时启用**，否则走既有 item_id 路径（零变化）。
- **产出** = 材料（`decompose_rate` 逐材料 floor）+ 精粹（`floor(V × k1 × k2 × β^色序)`
  **整体取整一次** + 淬炼返还）。
- **投入价值 V** `v_basis`：`node_materials`（默认，蓝图节点固定材料价值 V1）/
  `item_price` / `fixed` / `level_scaled`。
- **对象范围** `scope`：`crafted_equipment`（默认，仅打造装备）/ `all_equipment`。
- **载体**：精粹 = **货币**（D4 建议），键 `essence_currency`（默认 `essence`）。**必须在
  内容包 `settings.currencies` 登记**，否则校验器 R-4 红拦 + 运行期入账被拒
  （复刻 `gem_wallet` 的货币键空间硬前置）。

### 19.4 两处数值问题的处理（主 agent 裁定 + 证据）

**① 84:1 失衡 → 两侧同时定。** 产出侧用报告 §3.1 公式（`k1`/`k2`/`β` 可配）；消耗侧
按报告 §4.6 反解平衡点设 `cost_per_point.essence = 1593`。**典型循环推演**（
`python scripts/batch57_cycle_sim.py`）：打造 100 件 → 分解 95 件（白装
`V=100600`）→ 满淬 5 件（210 点/件）：

| 量 | 值 |
|---|---|
| 单件精粹产出 | `floor(100600 × 0.35 × 0.50) = 17605` |
| 精粹入账（95 件） | **1,672,475** |
| 满淬 5 件消耗（`5 × 210 × 1593`） | **1,672,650** |
| **产出 / 消耗** | **0.9999×**（`p=1` 时才是 **1593×**，`p=84` 时 19×） |
| 反解平衡点 | **1592.83 ≈ 1593** |

**② β^色序 闸门无效 → 真闸门。** β 降为**正向**系数（默认 1.2：品质越高单件回收价值

| 投入 | 25% | 50% | 75% | 100% |
|---|---|---|---|---|
| 每点返还 | 673.83 | 565.68 | 474.89 | 400.00 |
| 返还/消耗 | 0.4230 | 0.3551 | 0.2981 | 0.2511 |

**N 轮循环模拟**（`simulate_cycle`，20 轮「分解 → 满淬 → 再分解」）：每轮净变化
**−215,320 < 0**、余额**单调递减**（起始 1,000,000 → 期末 −3,306,400）；材料侧每循环净损
≥35%（收敛级数 `1/(1−0.65)=2.857`）→ **不存在无限套利**。校验器 V8 硬拦
`temper_refund > cost_per_point.essence`。

### 21.4 m1 用例全量偶发红：根因与修法（工程，不影响作者）

- **现象**：`test_formula_whitelist_boolean_and_string::evaluate("true")` 全量跑偶发失败，
  隔离跑必过。
- **根因**：`true`/`false` 在 Python 里是普通标识符（不在白名单）→ **每次降级 Node 子进程**；
  而 Node `vm` 的 watchdog 在本容器 30ms 有效预算下会对**平凡脚本**误报
  `Script execution timed out after 30ms`（实测 2%~12%），Python 侧记 `eval_failed:runner_fatal`
  → 公式兜底 **0.0**。预编译 `vm.Script` / 复用 `vm.createContext` 都**不能**消除 → 是
  墙钟调度抖动余量不足，不是编译/建上下文开销。
- **修法（生产代码）**：① `_VM_CTX_SLACK_MS` 20→90（有效 30ms→100ms；`FORMULA_TIMEOUT_MS=10`
  执行预算契约不变，`while(true){}` 仍真实中断兜底 0）；② 布尔字面量（根节点）走 Python
  快路径，不再为字面量 spawn Node；混合运算（`true+1`/`true==1`）仍走 Node，保 JS 语义。
  修复后探针 400 次 **0 失败**（0.053s）。

## 执行方式
1. 先读规划文档批 1 部分 + 三个细化契约，确认六要素落地范围
2. 为每路建 git worktree（/tmp/dev_enhance、/tmp/dev_dummy、/tmp/dev_target），派 3 个子 agent 并行开发。给每路子 agent 的规格必须包含：改动文件清单方向、数据源/现成 helper 位置、验收命令、已知坑
3. 子 agent 自报结果不可信——主代理必须亲自复验：模拟器实测 + 相关测试 + 全仓 pytest

## 硬性规则（用户铁律）
- 内容包纯配置：veinborn 数据只在 content/veinborn/*.json 改；框架机制代码在 qbot_rpg/
- 模板配置化：所有玩家可见文案走 tpl_of + 对应模板文件（enhance_tpl.py 等新建）+ PLACEHOLDER_WHITELIST 登记
- 新指令名必须同步：parsers.DEFAULT_WHITELIST、router_setup stub 移除（强化/调合 的 stub）、tests/unit/test_assembly_router.py 的 ALL_REGISTERED、帮助组动态生成（注册即出现）
- 零 emoji；禁止裸静默（任何指令都有回执）；菜单/会话选择有响应
- 无「装备 穿」类发明新指令——指令形态以规划文档/契约为准
- 全仓 pytest 基线 10 failed（g0/battle_render×2/codex/e2e_m4×4/emoji/investigate）——不得新增红
- ruff/mypy 只查自己改的文件（context.py E402/E501、battle_reward.py mypy 是预存不算）
- commit 前隐私扫描（ghp_|sk-[A-Za-z0-9]{10}|BEGIN (RSA|OPENSSH|PRIVATE) 零命中）才提交
- commit 信息：feat(enhance)/feat(dummy)/feat(battle) 分路提交，引用规划编号

## 每路验收门禁
- 对应契约的验收用例（2c3b 六节测试矩阵）全过（新建测试）
- 模拟器实测：注册 阿伟 脊剑士 → 走通该路全部指令（强化需先有可强化装备——veinborn 若无 enhance.json 需新建最小配置包并过 build_pack 零红拦）
- 全仓 pytest 无新增红
- 输出：改动清单（标注框架 qbot_rpg/* vs 内容包 content/veinborn）+ 模拟器实测输出 + pytest 结果

## 完成后汇报

## P1 清单（2 条）

### P1-1 核心结算段引用整段穿帮：L189-212 不含「三类掉落 / reward 解析器」
- **位置**：§四开头依据行（L170）与 SET-R02（L177）两处引用 `【框架】L189-212（三类掉落=概率化 reward 条目 + 框架 reward 解析器统一入账）`。
- **实况**：框架 L189-212 实际内容为「§3.5 装饰珠插槽（L189-192）→ §3.6 时间系统（L194-205）→ §3.7 存档引擎开头（L207-212）」，**与掉落/reward 完全无关**。
- **复核**：同类内容在框架中的真实落点为 L388（loot.json 掉落表）、L671（enemies 三类掉落 battle/special/death）、L2400（奖励发放器：与任务 reward 同一发放器）、L2587（「框架 reward 解析器入账」）。概念真实存在（SET-R02 的内容判断本身正确），但**行号引用指向错误段落**，构成「①行号引对」失败，且出现在最核心的结算章节，误导实现者回溯依据。
- 建议：改引 `L388 / L671 / L2400 / L2587`。

### P1-2 §五观战与广播：头部「默认不实现」与 OBS-R1/R3「P1 默认实现/默认开」自相矛盾
- **位置**：§五头部（L215）：「以下均为**位阶可选（P2）**，默认不实现，登记契约供后续启用」。
- **实况**：同一节内 OBS-R1 位阶列写「P1 默认实现（简报）」，OBS-R3 写「P1 结算广播默认开，推送挂接 P2」。
- **影响**：同段落内对「广播/简报默认是否实现、默认是否打开」给出相反指令，实现者无法判断交付范围；且 OBS-R1 行内另有「可配开关（默认关）」，三层说法互相打架。
- 建议：统一口径——要么全 P2 默认不实现，要么明确「简报=P1 实现但开关默认关」，删除「默认不实现」总述。

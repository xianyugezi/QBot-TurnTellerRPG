## 五、🔴/🟡 问题清单（🔴 P0 / 🟡 P1/P2）

### 🔴 P0-1 世界 CAS 冲突「提前 return」击穿单事务原子性：半写状态被 COMMIT 【静态推导】

- **位置**：`repository.py:414-454`（`save_world_state` 事务体 `431-452`，提前 `return False` 于 `439`/`447`）+ `connection.py:343-351`（`tx()` 的 else→COMMIT 分支）
- **实际**：`save_world_state` 在 `async with self.tx() as tx:` 体内，对 WORLD_STATE_FIELDS（map_boss/world_stock/spawn_timers/dummy_override/last_spawn_time）逐个「SELECT + UPDATE/INSERT」；一旦**第 i 个键**（i>1）发生 CAS 冲突（`cur["version"] != exp` 或 `cur is None 且 exp != 0`），代码直接 `return False`。而 `return` 是**正常退出** `async with`：`tx()` 的异步生成器收到 `__aexit__(None,None,None)` → 无异常 → 走 `else:` 分支 → **COMMIT**（connection.py:345）。因此**冲突前已经写入的 1..i-1 个键（map_boss 等）随 COMMIT 落盘**，冲突键与之后键未写——形成跨键撕裂的「半写世界状态」。
- **契约应有**：4a TX-3（L262「世界级共享资源…事务 + CAS 比对，失败重读重试；跨群写入串行化」）+ TX-2（L261「任何中间失败整体回滚」）+ 0.2（L45「失败全回滚，无半写状态」）——`save_world_state` 自己的 docstring 也承诺「任一冲突 → 整体 ROLLBACK 返回 False」，实现与之相悖。撕裂的世界状态（例：A 写者 map_boss=新、B 写者 world_stock=新，因部分提交交错，最终 map_boss 来自 A、world_stock 来自 B）违反野图 BOSS/全体限购的跨键一致性。
- **现有测试未覆盖**：`tests/unit/test_storage.py:101-114`（test_world_cas）仅在**第一个键**（map_boss）构造冲突，冲突前无任何写入，故「提前 return 也等于提交空事务」，无法暴露本缺陷——需补「第 2+ 键冲突」用例断言整体回滚。
- **修复建议**：① 冲突检测改为在事务体内 `raise WorldCASConflict`（内部哨兵异常），由 `try/except` 包住 `async with self.tx()` 在外层捕获后 `return False` —— 异常路径才触发 ROLLBACK（connection.py:336-342）；或 ② 在 BEGIN IMMEDIATE 后**先一次性校验全部 5 个键版本**再统一写（单写锁下 BEGIN 后无并发写者可交错，读版本不会中途变），校验全过才写、任一不过直接 ROLLBACK。二者都满足时序；补充 TC 断言「map_boss 已更新 + spawn_timers 冲突 → 两者都回滚」。

### 🟡 P1-1 idem_claim 破坏 IDEM-2「幂等键与业务写同事务」承诺（便捷路径是陷阱）【静态推导】

- **位置**：`repository.py:462-485`（`idem_claim`）+ `repository.py:698-706`（`write_idem_key` 正确路径）
- **实际**：`idem_claim` 自带一个 `async with self.tx()`：SELECT → 未命中 → `INSERT OR IGNORE 幂等键` → **出 tx 即 COMMIT 幂等键行** → 返回 False。也就是说「便捷路径」调用方拿到 False 后若在**另一个事务**里跑业务写，幂等键已在上一事务提交：业务写随后失败回滚 → 幂等键残留 → 以相同 message_id 重试时 `idem_claim` 返回 True 直接幂等重放 → **业务零执行且永不补齐**（操作黑洞）。这正违背 IDEM-2（L289「幂等键插入与业务写同一事务——消除『业务已执行但幂等键未落』的崩溃窗口」）与 F4 崩溃窗口分析（§4.1 L279-281）。
- **说明**：模块自身 docstring（repository.py:465-468）已提示正确用法为 `async with repo.tx() as tx: await tx.write_idem_key(key); <业务写>`，故 `idem_claim` 属「API 陷阱」而非唯一默认路径；M0 内无调用方（commands M4 才接线）。
- **修复建议**：① 将 `idem_claim` 改为**只查不插**（`SELECT` 返回命中/未命中），把插入职责完全交给 `write_idem_key`（业务事务内），或在 docstring 顶部加「⚠️ 仅用于『claim 即提交、业务失败可容忍幂等键残留』的特殊场景」；② 若保留插入语义，则在业务失败时必须允许删除幂等键或改用临时 claim + 业务后 confirm。补 TC-06 变体：claim 后业务注入失败 → 重试应重新执行业务而非幂等空转。

### 🟡 P1-2 RW-4 / TC-09 `.pending` 暂存补写 + 「保存失败，请检查磁盘空间」未实现（丢档窗口开放）

- **位置**：`repository.py:362-366`（`save_player` 直接 `tx()`，无 OSError 兜底）+ 全 storage 层（grep `.pending|暂存|保存失败，请检查磁盘空间` 零命中）
- **实际**：写盘抛 OSError（磁盘满）时事务 ROLLBACK 后异常直接上抛，**没有**（a）向用户提示「保存失败，请检查磁盘空间」的挂起通道（该语义可留 commands 翻译，但 storage 未提供信号/异常类型区分）；（b）本地 `.pending` 文件队列暂存 + 磁盘恢复后补写。即 4a RW-4（L225「写抛 OSError → 弹人话提示 + 本地暂存(.pending 队列)，恢复后补写；绝不静默丢数据」）+ TC-09（L392 断言「未丢任何已确认数据」）未落地。
- **修复建议**：M0 若将「暂存/补写」递延到 M3+，必须**显式登记 ADR 递延**并在 `save_player` 的 OSError 路径保留「可挽救数据不丢」的接口位（如 `PendingStash` 抽象）；否则应把 `save_player` 包 `OSError` → 序列化行写入 `<db>.pending.jsonl` + 队列重放（重启/定时 flush 消费，成功后删除）。

### 🟡 P1-3 RW-6/D-04 启动 integrity 校验失败「自动回退最近 .bak」未实现，仅抛异常

- **位置**：`connection.py:210-215`（`_writer` 中 `_integrity_ok` False → `raise StorageIntegrityError`）+ `connection.py:218-225`（仅 `PRAGMA integrity_check`）
- **实际**：校验失败只抛 `StorageIntegrityError`（异常文本提示「应回退最近 .bak 后重试，服务不崩」），**没有执行实际恢复动作**：无「从 backups 表/backups/ 目录取最近 pre_migration/auto .bak → 原子替换当前库 → 重试一遍」逻辑；也无「关键表 round-trip 抽样」（RW-6 L227「integrity_check + 关键表 round-trip 抽样」）；失败后服务无法继续（异常会沿 `_writer()` 上抛，首个访问即崩，而非「服务不崩携带旧版继续」）。
- **契约应有**：4a RW-6 / D-04（L54「校验失败自动回退最近 .bak」、TC-11 L394「备份损坏→自动备份当前档→原子替换→失败自动回滚」）。
- **修复建议**：新增 `Database.restore_from_backup()`（backups 表取最近合法档 → VACUUM INTO/文件替换 → 重新 integrity_check + round-trip 抽样 → 失败再回滚），`_writer` 校验失败时自动触发一次而非直接 raise；或将「自动回退」动作登记为 M3/启动器协作项并 ADR 记录（当前实现与 D-04 相悖，需裁决）。

### 🟡 P1-4 RC-2/RC-3 回收站接口全缺：recycle_bin 只有表，无 add/restore/清理/占用 任何函数

### 🟡 P2-1 `_read_conn` 池耗尽守卫为死代码（`max_readers<=0` 恒假）

- **实际**：`self._max_readers = max(1, max_readers)`（connection.py:143），恒 ≥1 → 条件永不成立；池耗尽实际由 `wait_for(acquire, timeout)`（L239-243）兜底。

### 🟡 P2-2 权限 600 只覆盖主库文件：-wal/-shm 伴生文件与已存在目录未收紧

- **位置**：`connection.py:196-201`（仅 `chmod(self._path)`）+ `connection.py:140-141`（`makedirs(exist_ok=True)` 对已存在目录不改权限）
- **实际**：WAL 模式会产生 `<db>-wal`/`<db>-shm`，SQLite 按 umask（常见 0644）创建，**未 chmod 600**——数据文件字段权限契约（4a L184「数据文件权限 600、目录 700」）有信息安全缺口（WAL 内容可被同机其他用户读）；`exist_ok=True` 也不会修正已存在的宽松目录。
- **修复**：对 db 主文件 + `-wal` + `-shm`（若存在）统一 `os.chmod(0o600)`（可放 `_open` 尾部或在 `close` 持久化后补一次）；目录侧 `os.chmod(parent, 0o700)` 兜底已存在目录。

### 🟡 P2-3 60s 读缓存共享「frozen 外壳 + 可变嵌套 dict」，缓存快照可被外部串改

- **位置**：`repository.py:289/352-354`（`_player_cache` 存同一 Player 对象）+ `data/player.py`（frozen dataclass 含 Dict 字段）
- **实际**：frozen 只封外层；`Player.currencies/inventory[i].stats_bonus/attributes.base` 等均为可变 dict。`load_player` 返回**同一个**缓存对象，任一引擎/渲染消费方修改嵌套 dict，60s 内后续 load 全读到被改后的状态（违反 F1「内存缓存仅限读取快照」语义）。
- **修复**：缓存返回前浅拷贝容器（`dataclasses.replace` 不足，需对嵌套 dict 拷贝）或文档明确「消费方不得改嵌套 dict」；测试补「load 后修改嵌套 dict → 再次 load 不受影响」。

### 🟡 P2-4 回收/清理以 ISO 字符串字典序比较，格式漂移即静默失效

- **位置**：`repository.py:69-81`（`parse_utc`/`ago_utc`）+ `cleanup_idem_keys`（516）/`recycle_scan`（546）的 `created_at < deadline` 直接字符串比较
- **实际**：当前全库时间统一为 utcnow() 的 `%Y-%m-%dT%H:%M:%SZ` 定长格式，字典序=时间序成立；但一旦有任何来源写入 `+00:00` 后缀（`parse_utc` 容忍的格式）或非定长，字符串比较会错序，7 天/30 天清理将漏删或误删且无告警。
- **修复**：比较前统一 `parse_utc` 转 datetime 再比（先在 SQL 侧 `WHERE datetime(created_at) < ...`，或入库前强制归一为 Z 定长并加 CHECK/写入端断言）。

### 🟡 P2-5 `cleanup_idem_keys`/`recycle_scan` 的 `now` 参数语义反转（now < deadline 时把 deadline 改成 now）

- **位置**：`repository.py:511-513`、`541-542`
- **实际**：`if now is not None and parse_utc(now) < parse_utc(deadline): deadline = now` —— 语义是「若注入的 now 早于 deadline，就以 now 为清理线」，导致测试注入更早的 now 时清理窗口缩成「早于 now 的全部」，与「7 天前」直觉相反；生产 now=None 走正确线，属测试注入路径困惑+潜在误用。
- **修复**：改为 `deadline = ago_utc(retention_days, ref=now)`（以 now 为参照点回推 7 天），now 仅作时钟注入。

### 🟡 P2-6 编解码 int 强转无保护：脏数据（非数字 count/slot_level/level）加载即崩

- **位置**：`repository.py:144`（`count=int(d.get("count",1))`）、`159`（`slot_level=int(...)`）、`190-193`（`_int_dict`）、`226-228`（row_to_player level/hp/mp）
- **实际**：`int(None)`/`int("abc")` 直接抛异常；`_int_dict` 对 world_stock 中 None/字符串亦崩。SCHEMA-6「字段缺省=默认值，不拦截加载」在非 JSON 类型脏值上不成立（损坏库虽少，但「不崩」承诺被破坏）。
- **修复**：加安全转换（`_safe_int(v, default)`，None/非数字回默认），并让 `_int_dict` 跳过不可转项。

### 🟡 P2-7 job_id 折入 persistent_state 与契约落点/文档指针不符

- **位置**：`repository.py:62-63`（`_JOB_ID_KEY` 注释「见 contract_deviations」）、`110-111`（写）、`219`（读弹出）
- **实际**：① persistent_state 在 4a §1.2（L88）是「②非会话持久：checkin_state/shop_state/resource_state/time_state/dummy_log」专属；把框架字段 job_id 混入该 JSON 键空间，属契约未登记的【工程补白】，且可能与某系统自有的 `persistent_state["job_id"]` 键冲突（写侧覆盖、读侧弹出丢失）。② 代码引用「见 contract_deviations」文档，工作区**无此文件**（grep 零命中），文档指针悬空。
- **修复**：在 4a §0.3 ADR 登记该补白（或改入 stats 的保留键/独立 JSON 列），并新增 `contract_deviations.md` 落该条目，删除悬空引用。

### 🟡 P2-8 migrate_database 吞 CancelledError 且 _bootstrap 忽略失败结果（迁移失败无观测、重启前不再重试）

- **位置**：`migrations.py:230-243`（`except BaseException` 捕获含 CancelledError，直接返回 failed）+ `repository.py:300-308`（`_bootstrap` `await migrate_database(...)` 不检查 `MigrationResult.state`，置 `_booted=True`）
- **实际**：① 取消信号被吞（应重抛 CancelledError）；② 迁移失败后 `_booted=True`，本次进程内**永不重试**（每次访问走 `if self._booted: return`），且失败无任何日志/告警出口（D-06 允许携带旧版跑，但需可观测）。
- **修复**：`except (Exception,)` 而非 BaseException（CancelledError 重抛）；`_bootstrap` 检查 `state=="failed"` 时打告警或抛存储层异常；保留失败原因便于 commands 翻译（MIG-5 人话提示）。

### 🟡 P2-9 RC-4 备份 30 天保留清理缺失 + pre_migration_backup 可能的孤儿 .bak

- **位置**：`migrations.py:122-145`（登记备份但不清理）+ repository 全文件（无 `cleanup_backups()`）
- **实际**：backups 表只增不清理，`idx_backup_created` 建成无人消费（RC-4 L311「created_at 距今 >30 天自动删除对应 .zip + 元信息行」缺失）；且 `pre_migration_backup` 里 VACUUM INTO 成功后若 backups INSERT 失败，会留孤儿 `.bak` 文件（无善后）。
- **修复**：补 `cleanup_backups(retention_days=30)`（事务：过期行 → 删 .zip（带 OSError 容错）→ 删行）；INSERT 前/失败时清理目标文件或用唯一临时名。

### 🟡 P2-10 管理用 db.execute/fetchone 与 tx() 共享同一非重入写锁：tx 体内调用即死锁（无守卫）

- **位置**：`connection.py:277-299`（`execute/fetchone/fetchall` 各自 `async with self._write_lock`）vs `tx()`（同锁，L325）
- **实际**：若调用方在 `async with db.tx():` 体内再调 `db.execute(...)`（同任务），非重入 asyncio.Lock 会**永久挂起**（嵌套检测仅拦 `tx()`，不拦管理方法）。当前代码内迁移/管理调用均在 tx 外，属潜在 footgun。
- **修复**：管理方法在进入锁前做与 `tx()` 相同的同任务事务归属检查（或文档强制「tx 体内一律用 tx.execute」+ 测试守卫）。

### 🟡 P2-11 RC-5 周级/超阈值 VACUUM 调度 与 磁盘低水位预警缺失；RW-2 防抖合并未落多数

### 🟡 P2-12 会话快照为不透明 JSON：storage 不重建 BattleSnapshot 类型，round-trip 边界未文档化

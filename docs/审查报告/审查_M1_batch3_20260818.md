## 四、🔴 P0 清单

### P0-1 combo 条件求值「未知键静默放行」→ 印记条件恒真，且 1d 条件原语零接线
- **位置**：qbot_rpg/core/combo.py `evaluate_condition` L382-428（尤其 L386 `result=True` 起、对未知键无任何回落分支）；`_resolve_derivation` L1303-1332 用该函数判步条件。
- **实际**：条件 dict 含 `marks_total / self_marks / target_marks / marks_set / marks_any / consume` 等非 combo 键时，循环只检查已知的 count/target_hp_pct/round/status/and/or/not，未知键**被忽略**，`result` 保持 True。`{"marks_total": {"min": 5}}` 或 `{"and": [{"count": 2}, {"self_marks": {...}}]}` 中 marks 子句被丢弃 → 派生步在印记不足时**仍判为满足、正常派生**（静态推导：单条件槽全不命中 → 返回 True）。
- **应有**：细化_1c3 TC-13「条件表达式引用未注册字段 / 求值异常 → 求值失败**默认"条件不满足"（安全失败），战斗不崩溃**」；细化_1d §3.1 公共语义「支持 and/or 复合引用（如 and: 连段 count + self_marks），复用派生条件引擎复合机制」——marks 键要么被正确求值、要么按"不满足"截断，绝不能恒真放行。
- **证据**：`MarksManager.evaluate`/`eval_condition`/`MarkCondition`（marks.py L366-410）全库 grep **零调用方**（qbot_rpg 下无任何消费点）；1d §5.3「双轴交互：派生条件可复合引用」要求 marks 条件可进派生条件，而本实现既不消费 marks.evaluate 也不对未知键安全失败。
- **影响**：1d §3.1 C-1..C-5 五原语 + AT-14 不可达成；含印记条件的派生技能将无条件释放（静默、不崩、但语义完全翻转，属反安全方向）。同时违反 TC-13。
- **修复建议**：①evaluate_condition 增加"未知键 → result=False（安全失败）"收口（或显式注册 marks 键转发 MarksManager）；②battle 侧把 step.condition 中的 marks 子句交由 `marks_manager().evaluate` 复合求值（同步接 _combat_map 侧 source/target 映射）——二选一，缺一不可。

## 五、🟡 P1 清单

### P1-1 combo_state.step_index 双缺陷：从不写 ≥0 + 快照回读 0→-1（快照 roundtrip 破坏 + 形态机进度缺失）
- **位置**：combo.py `ComboState.from_dict` L195 `step_index=int(d.get("step_index", -1) or -1)`；`_apply_delta` L831-865 恒 `step_index=state.step_index`；首次注册 L1074-1077 置 -1；全引擎无任何 `step_index=x(x≥0)` 赋值。
- **实际**：①`0 or -1` 在 Python 中求值为 -1——快照中 `step_index=0`（合法：1c1a §2.1「空闲=-1；其余≥0」）回读为 -1，roundtrip 破坏（from_dict→to_dict 不等）；②引擎从不推进 step_index，链上节点执行后字段恒 -1。
- **应有**：1c1a §2.1 字段 5「step_index=最近执行步骤索引（≥0），支撑循环互派生形态机（L97-103/L340）」；TC-15 形态机进度需可持久化/恢复（1c3 TC-43 快照还原含 combo_state）。
- **影响**：互派生"形态机进度"无载体（TC-15/TC-43 部分不可成立）；快照含 0 时恢复错位。
- **修复建议**：`from_dict` 改 `int(d.get("step_index", -1))`（去掉 `or -1`）；`apply_action` 在命中步后写入 `step_index=step.index`；补 roundtrip 单测。

### P1-2 marks_state 战斗结束/逃跑成功不清零（与 combo 双轴生命周期不一致）
- **位置**：battle.py `_settle` L716-743（L721-727 仅清 `combo_state`）；`_flee_actor` L1098-1099（成功后经 _settle）。
- **实际**：战斗结束（胜/败/逃/平）与逃跑成功，marks_state 原样留在快照；全 battle 无任何 `marks_state` 清零点。
- **应有**：细化_1d §2.3「战斗内资源：随战斗结束清零，与连段（combo_state）一致」；§2.2「逃跑成功清空、失败保留」；合成 AT-07「战斗结束清零」。
- **影响**：同一引擎对双轴生命周期处理不一致；若世界层复用/保留战斗快照对象，印记跨战斗残留（违背 1d §0.2/§2.3）。
- **修复建议**：`_settle` 中与 combo_state 同位置清空 `marks_state={'player':[],'enemy':[]}`，reason 并入 combo_zeroed 审计或另立 audit。

### P1-3 技能 effects/actions 在战斗技能路径零执行（mark 三动作/打断/consume 仅道具路径可达）
- **位置**：battle.py `_do_action_inner` L1022-1023 全部 normal/skill 走 `_resolve_combo_action`；`_resolve_combo_action` L1131-1163 仅 apply_action→form_id→`_resolve_damage_action`；`execute_action` 全 battle 唯一调用点 = `_resolve_item_action` L1117。
- **实际**：技能带 `effects:[{type:mark_add|mark_remove|clear_marks|interrupt|aoe|...}]` 时，技能结算只算伤害，**从不执行 execute_action**；effects.execute_action 的 mark_add/mark_remove/clear_marks 分支（effects.py L1548-1570）与 interrupt 分支（L1581-1592）均不可达。consume_marks（1d §3.3 P-1）无任何实现/接线。
- **应有**：细化_1d §4.1「印记 target 独立于伤害 target；施加必中；**技能结算末尾施加**」+ AT-09..13；1c2 §1.3 字段 24「effects 归口效果系统；interrupt 唯一实现走 effects.json」+ 1c3 TC-39「tag 仅派生语义标记，打断效果由效果系统 L0 interrupt 唯一实现」。
- **影响**：印记经战斗技能**综无法施加/消除**（marks 薄转接只对道具/直连可达）；打断技对目标连段清零失效（还是 P1-4 的根因之一）；1d 9 原语仅条件/公式侧落地、动作侧技能路径断线。
- **修复建议**：`_resolve_damage_action` 或 `_resolve_combo_action` 增加技能 `effects`/`actions` 的 execute_action 消费（复用 _resolve_item_action 形态，rt 绑定同快照）；先于伤害链按 1d §4.1「结算末尾」施加，伤害判定前置仅确定 miss 与否；consume_marks 不足即拒并入 should_reject 口径（D-01）。

### P1-4 打断/霸体闭环未接线：apply_interrupt 零 battle 调用方 + armor_active 永不置位
- **位置**：combo.py `apply_interrupt` L899-946、`is_armored` L888-897；battle.py L338/877 仅初始化 `_armor_active`，L1144 传给 apply_action；全 battle 无 `_armor_active[...] = True` 赋值、无 apply_interrupt 调用、`result.armor` 不回写。
- **实际**：「攻击窗口三条件」判定（1c2 §2.2）引擎已实现且单测可达（test_c06/c07/c08），但实战流程中：无人调用 apply_interrupt → 打断技对目标连段零效果；无人置位 armor_active → 霸体免疫窗口永不成立；`cast_info`/`apply_action` 算出的 armor 返回值 battle 不消费。
- **应有**：1c2 §2.2「打断技结算时刻判定一次，目标正在连段+非霸体+非 hold 免疫 → 清零」；TC-INT-01..05、TC-34..40；TC-ARM-01..04。
- **影响**：本批验收的打断/霸体博弈全链路（用户可感知的连段反制）未通过公开战斗 API 生效，仅测试直连引擎可达。
- **修复建议**：battle 在技能结算（P1-3 的 effects 消费处）对 `tag=interrupt` / `effects:[{type:interrupt}]` 调 `combo_engine().apply_interrupt(attacker,target,snap,self._armor_active)`；把 apply_action 返回的 armor 写入 `_armor_active[attacker]`（行动开始置位、结算完成清位，1c2 §2.2「使用期间」）。

### P1-5 被拒短路后 `_turn_acted` 前置置位残留 → "不耗回合"语义在默认流程与快照边界误判
- **位置**：battle.py `_do_action_inner` L1007 `self._turn_acted[attacker]=True`（判定前置位）；`_resolve_combo_action` 被拒分支 L1145-1154（状态保持 ACT 未推 RES ✓ 正确，但未回滚 _turn_acted）；`next_action_owner` L970 与 `to_snapshot` L1516 均读 _turn_acted。
- **实际**：指令被拒（⑥）后，状态确实保持 ACT（docstring 自述正确），但 `_turn_acted[attacker]=True` 已残留。静态推导两处副作用：①`next_action_owner()`（L970）把被拒玩家当"已行动"，默认「do_action(player)→enemy_act→end_turn」流程下被拒动作仍会推进回合轮转 → "不耗回合、可反复尝试"（1c1c TC-DEF-04/1c2 §2.4）在未显式重试的调用方被打穿；②`to_snapshot`（L1516「玩家已行动未到 tick 边界=回合内不可落快照」）把"被拒未行动"误判为"玩家已行动"，回合开始即被拒后本应可落快照却抛 BattleStateError（1g3 S0 误判）。
- **修复建议**：被拒分支回滚 `_turn_acted[attacker]=False`（或判定前先用 `should_reject` 预检、通过后才置位）；补测试断言"被拒后 state==ACT 且 next_action_owner 仍返回 player / to_snapshot 不抛错"。

# 开发规则文档（RPG 框架项目）

> 版本：v1.0 · 2026-08-15
> 对标：Google Engineering Practices / 大厂开发规范（腾讯云服务器部署场景）
> 适用范围：rpg_framework（NoneBot2 回合制 JRPG 框架）全部代码、内容包、文档、Git 流程
> 一句话：**框架提供机制，内容包提供配置；代码给更强的编程模型写，规则保证它写得像一个人写的；内容包给小白用编辑器做，规则保证做坏了也不崩。**
> 总纲遵循：《设计总纲：只建议不限制》（校验/拦截哲学）与《RPG回合制框架设计文档》v2.12（本文档为其配套工程规范，冲突时以设计定稿为准）

## 一、代码规范

> 本项目代码主要由更强的编程模型生成（用户是编程小白提需求），因此代码规范的目的是**让不同模型、不同时间生成的代码保持同一套风格与结构**，可读、可审、可测。

### 1.1 项目结构与模块边界（硬约束）

目录结构以《框架设计文档》第 14 章为准，**禁止随意新建顶层模块**：

```
plugins/rpg_framework/
├── __init__.py            # 插件入口（含编辑器子进程拉起）；只做装配，不写业务
├── commands.py            # 指令路由（on_command 注册、权限、频率控制）
├── engine/                # 纯规则引擎，不依赖 NoneBot
│   ├── battle.py          # 1v1 回合状态机
│   ├── damage.py          # 公式求值（安全表达式）
│   ├── levelup.py / inventory.py / equipment.py / worldtime.py
├── content/               # 内容包加载/校验/注册表
│   ├── loader.py / validator.py / registry.py
├── state/                 # 玩家数据/SQLite 存档
│   ├── character.py / game.py / storage.py
├── editor/                # Web 编辑器（api.py + web/ 前端）
├── utils/                 # 渲染、消息合并等通用工具
└── tests/                 # pytest 测试（与插件同仓）
```

分层铁律：

- **引擎层不 import NoneBot**（`engine/`、`state/`、`content/` 必须可脱离 NoneBot 单测）——这是测试规范能落地的前提。
- **依赖方向单向**：commands → engine/state/content → utils；禁止反向依赖、禁止循环 import。
- 新增能力先放对层，放错层视为架构缺陷，评审时拦截。

### 1.2 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 文件/模块 | 小写 snake_case，一个词优先 | `battle.py`、`worldtime.py` |
| 类 | PascalCase | `BattleStateMachine`、`ContentValidator` |
| 函数/方法 | 小写 snake_case 动词开头 | `resolve_damage()`、`load_pack()`、`save_character()` |
| 私有函数/方法 | 单下划线前缀 | `_apply_pipeline()` |
| 常量 | 全大写 snake_case | `MAX_MSG_LEN = 4500`、`MIN_CMD_INTERVAL = 1.0` |
| 变量 | 小写 snake_case，语义明确 | `player_qid`（QQ 号）、`pack_id` |
| 内容包 ID/字段 | 小写 snake_case（与 JSON 键一致） | `two_handed`、`max_combo` |

- 内容包 JSON 的**字段名一经发布即为公共 API**，改名必须走 9 章文档流程 + schema_version 迁移，不得静默改。
- 中文语境项目：注释与字符串文案用中文，**标识符一律英文**（防止编码/工具链问题）。

### 1.3 类型标注（强制）

- 所有公开函数必须带完整类型标注；内部函数至少标注参数与返回值。
- 常用类型用 `typing`：`Optional`/`List`/`Dict`（Python 3.9 兼容写法），不追求 `|` 新语法（服务端可能跑 3.9/3.10）。
- 领域类型用 `TypeAlias` 或 dataclass 表达，禁止裸 dict 满天飞：

```python
# 反例：裸 dict 无约束
def apply_effect(ctx: dict, effect: dict) -> dict: ...

# 正例：dataclass + 类型别名（引擎层，不依赖 NoneBot）
@dataclass(frozen=True)
class CombatantSnapshot:
    max_hp: int
    hp: int
    atk: int
    ...

def apply_effect(ctx: CombatContext, effect: EffectDef) -> ActionResult: ...
```

- 存档/内容包结构建议用 Pydantic 或 dataclass + 显式校验；若用手写 dict，必须在 `content/validator.py` 收敛全部结构断言，禁止散落各处 `if "xxx" in data`。

### 1.4 注释规范

- 模块头部 docstring：一句话职责 + 引用设计文档章节（如 `# 对应《框架设计文档》3.1 1v1 回合状态机`）。
- 公开函数 docstring：参数含义、返回值、**抛出的异常**、对应定稿条款。
- **注释解释"为什么"（设计决策、定稿拍板、坑），不解释"是什么"**（代码本身看得懂）。
- 设计决策注释必须带来源：`# 用户拍板：一轮一条消息，防刷屏（框架设计文档 3.1）`。
- 硬编码数值禁止裸奔：要么常量、要么内容包字段，临时魔数必须注释关联 formula.json 参数段。

### 1.5 异步与性能规范（硬约束）

来源：《框架设计文档》15 技术要点：

- 所有 `>50ms` 操作（内容包校验、CSV 导入、zip 打包、文件 IO）必须 `asyncio.to_thread` 或放入 worker，**禁止阻塞事件循环**。
- SQLite 一律 `aiosqlite` 独立连接；**单写连接队列 + busy_timeout**，禁止多连接并发写。
- 自动保存防抖合并（200ms 内合并多次变更为一次落盘）；**战斗结算强制落盘**（防丢档）。
- 指令处理目标：单条指令端到端 `<200ms`；超时操作先回"处理中"提示再异步完成。
- 定时任务统一走 `nonebot_plugin_apscheduler`，与"操作时懒计算"并存，**重置以定时器为准**。

### 1.6 错误处理规范

- **绝不静默吞异常**：except 后必须至少 log；用户可见路径必须给"人话提示 + 下一步"（统一错误反馈模板，框架设计文档 7.5）。
- 用户输入错误走统一错误模板：`原因 + 正确用法 + 下一步建议`。
- 仅一种情况允许静默：**无 GM 权限的玩家使用 GM 指令直接无视**（不报错不提示，防暴露指令存在）——这是设计决策，注释注明。
- 引擎层抛领域异常（如 `BattleNotInProgress`），由 commands 层捕获翻译成人话；**禁止引擎层拼用户文案**。

### 1.7 工具链

- 代码风格：`ruff`（或 black + isort）统一格式；`mypy`/`pyright` 静态检查通过方可提交。
- 提交前跑 `pytest`（见第 4 章）；CI 门槛：ruff + mypy + pytest 全绿。
- 内容包 JSON 提交前必须过 `validator.py`（见第 2 章）。

## 二、内容包 JSON 规范

> 内容包 = 纯 JSON 配置（`content/<pack_id>/`），由 Web 编辑器生成，玩家 git pull 更新。**JSON 是运行时公共 API，任何变更都要考虑向后兼容。**

### 2.1 模块清单与 manifest（硬约束）

- 每个内容包必须有 `manifest.json`：`name`、`version`（语义化）、`schema_version`（整数，随新模块升版）、`author`、`modules`（启用的模块文件清单，不含 .json 后缀）。
- `modules` 数组 = 启用的模块声明：新增模块 = 在数组补一行；**不声明 = 对应系统不加载**（向后兼容，旧包零改动可跑）。
- 校验器规则：`modules` 声明的文件缺失 → 黄色提示不拒绝；**未声明的文件存在 → 不加载**（防误启用）。
- 新模块注册顺序（加载依赖）：`effects → statuses → marks`（效果家族先注册）→ `skill_chains` → `action` → 其余。效果家族被 traits/items/skills/enemies 引用，必须先入 registry。

### 2.2 字段定义唯一数据源（硬约束）

《框架设计文档》4.2：**所有模块的字段定义是唯一数据源**——编辑器表单、CSV 列头、JSON Schema、校验规则四处共用一张元数据表，杜绝"各处手写漂移"。

- 新增字段 = 在元数据表加一行（字段名/中文名/类型/默认值/范围/引用目标），四个消费方自动更新。
- 类型枚举：`int / str / bool / enum / ref / obj / list / map / formula`（formula 为 v2.10 新增，JS 公式类型）。
- `ref` 字段必须有引用目标（哪个 JSON 文件/注册表），校验器查引用存在性。
- 自定义字段：作者可加 `x_` 前缀字段，校验器一律放行（仅查引用存在性）。
- **虚拟属性键空间**（4.2.3）：`stats.json 注册属性 ∪ {crit_bonus, crit_mult_up, elem_res} ∪ {ele_atk_<元素>}`，消费方统一查键空间；未注册键 → 黄色提示不拦截。

### 2.3 校验规则（只建议不限制，硬约束）

遵循《设计总纲：只建议不限制》：

**红色拦截（拒绝加载，仅限 5 类真正的非法值）：**
1. 类型错误（数字填成文字 / NaN / null）
2. 负数（<0）
3. 非数字
4. 引用不存在（效果/属性/元素/印记/物品/怪物 ID 指向空）
5. 结构错误（JSON 格式坏 / 必填字段缺失 / 死配置，如条件 min>max、reset 模式 eq=max、battle+revert 矛盾）

**黄色提示（不拦截，可加载）：**
- 数值大小 / 范围越界（"生命值 999999，超出常见区间，确认是故意设计？"）
- 概率高低、组合强度、上限可配 0=不限（crit.cap / max_stack / 触发上限等）
- 软标注字段（difficulty/playstyle）永不红色报错
- 新模块缺失："没找到 effects.json……旧包照常玩"（提示不拒绝）

**报错必须人话**：报错示例统一按《框架设计文档》4.5 模板，如：
- 引用完整性："『巨剑』引用的部位『双手武器』不存在，请先在部位页面添加"
- 部位互斥环："你的武器、盾牌、副手互相排斥形成了一个圈，谁也装不上，请删掉一条互斥"
- ID 唯一："已经有一个叫『铁剑』的物品了，换个名字吧"

**禁止**任何"必须/强制/上限/封顶/拒绝"类文案出现在提示语中（总纲修正映射表）。

### 2.4 热重载规范（硬约束）

- 编辑器保存 → 文件 mtime/哈希检测 → 该包即时生效（3 秒自动检测，或 /重载 手动）。
- **热重载原子性**（框架设计文档 15.5）：先写临时文件再原子 rename；**全部文件写完统一触发重载**；内存保留上一份校验通过的 registry 快照，失败自动回退并人话提示。
- 按文件 mtime 增量校验，只重载变更模块（新模块同样纳入 mtime 监控）。
- **进行中对局持旧快照（ID+名称冗余存储），新对局用新配置**——防热重载导致对局异常、防配置删除导致引用悬空（删除配置按"无效果/无链/无印"降级，不报错）。
- 热重载后必须过完整校验器；校验失败 = 回退旧 registry + 人话提示，**绝不半套配置运行**。

### 2.5 向后兼容规范

- `schema_version` 随新模块引入升版（当前 4）；框架按 schema_version 决定迁移路径。
- 存档迁移：字段级（缺补默认 / 多忽略）；存档含 `content_pack_id + version`，更新自动迁移不丢档。
- 旧配置自动迁移示例：内联 effects 数组 → effects.json ID 引用（语义字段取默认值，旧包零改动可跑）。
- **换包策略三选一**（编辑器设置）：自动迁移（尽力映射）/ 全服重置（确认后清空）/ 双存档并行（旧包保留可切回）。
- 删除字段/改名：必须走"弃用周期"——先黄色提示 N 个版本，再移除；引用按 ID 存储、显示按名字（改名后引用不丢）。
- 数值语义变更（如命中 K 从 1 → 0.2）必须以新定稿为准并写入登记段，禁止默默改默认值。

### 2.6 JSON 文件格式约定

- 编码一律 UTF-8（无 BOM）；缩进 2 空格；键按元数据表顺序排列（编辑器生成，手工编辑仅改值）。
- JSON 内**不写注释**（标准 JSON 不支持）；设计说明写在对应定稿文档/登记段。
- 文件名全小写 snake_case；ID 生成规则：`类型_序号`（item_0001 递增），用户只看中文名。
- 提交 git 前必须 `validator.py` 全绿；zip 分享/导入遵循安全规范 7.5（zip slip / zip 炸弹防护）。

## 三、Git 规范

> 分发渠道 = git 仓库（作者托管，玩家 git pull 更新）。仓库承载两种受众：**开发者**（写代码）与**玩家/作者**（拉内容包更新），规范要同时服务两者。

### 3.1 仓库结构

```
rpg_framework/
├── plugins/rpg_framework/    # 框架代码
├── content/                  # 预置内容包（demo_blank ~ demo_full）
├── docs_archive/             # 设计定稿文档（见第 9 章）
├── tests/                    # pytest
├── CHANGELOG.md
└── README.md
```

- `content/` 与代码同仓，但**内容包变更与代码变更分开提交**（见 3.3 scope），方便玩家只 pull 内容更新。
- 大型二进制/生成物不入库（编辑器构建产物、备份 zip 一律 .gitignore）。

### 3.2 分支策略（简化 Git Flow）

```
main                稳定分支：只接受 release 合并，永远可部署
├── develop         集成分支：日常开发合并目标
│   ├── feature/xxx     功能分支：从 develop 切出，PR 回 develop
│   └── fix/xxx         缺陷修复分支：从 develop 切出
├── release/x.y.z   发布分支：从 develop 切出，只修 bug 不打新功能
└── hotfix/x.y.z    紧急修复：从 main 切出，修完同时合并 main + develop
```

简化规则（小团队可只留 main + feature）：

- **main 永远可用**：任何时刻 main 可部署、可被玩家 git pull。
- 每次内容包发布 / 框架发布 = 打 tag：`v1.2.0`（代码）、`pack-v1.2.0`（内容包）。
- 个人/小团队直接 commit 到 develop 可以接受，但 **main 必须走 PR/合并请求**。
- 禁止直接 push main；禁止 force push 共享分支。

### 3.3 提交信息（Conventional Commits）

格式：`<type>(<scope>): <subject>`

| type | 含义 | 本项目典型 scope |
|---|---|---|
| feat | 新功能 | battle / content / editor / pack 等 |
| fix | 缺陷修复 | 同上 + formula / validator |
| docs | 文档（含定稿/登记段） | docs / 具体文档名 |
| style | 格式（不影响逻辑） | - |
| refactor | 重构（无行为变化） | - |
| perf | 性能优化 | - |
| test | 测试 | tests |
| chore | 构建/工具/依赖 | - |
| revert | 回滚 | - |

示例：

```
feat(battle): 实现 1v1 回合状态机，一轮一条消息（框架设计文档 3.1）
fix(formula): 修复元素通道未参与随机数判定的问题（伤害公式定稿 1.2 ⑥）
docs(pack): 登记技能派生系统到框架文档附 A
test(damage): 增加命中判定边界用例（专注=0 时命中率下限 10%）
```

- subject 用中文，动词开头，≤72 字符；**正文写"为什么"**：关联设计文档章节 / 定稿编号 / 用户拍板事项。
- 破坏性变更必须在提交信息尾部加 `BREAKING CHANGE:` 说明，并同步 CHANGELOG。
- 一次提交一个逻辑变更；内容包 JSON 变更（`feat(pack):`）与代码变更分开提交。

### 3.4 PR 流程

1. 从 develop 切 feature 分支 → 开发 → 本地过 `ruff + mypy + pytest` 全绿。
2. 开 PR（合并到 develop）：标题用 Conventional Commits 格式；描述模板包含：
   - 变更内容（对照设计文档章节）
   - 测试执行结果（附 pytest 输出摘要）
   - 兼容性影响（schema_version 是否升版 / 存档是否迁移）
3. 代码评审：按第 5 章清单，**至少 1 名评审通过**；重大变更（涉及引擎核心/安全）必须 2 名。
4. 合并：squash merge（保持 main 历史干净）；CI 全绿才可合并。
5. release 分支 → main 的合并：只接受 bug 修复；合并后打 tag + 更新 CHANGELOG（第 6 章）。

## 四、测试规范

> 依据《框架设计文档》15.16：**pytest 单测伤害公式/状态机/存档往返；故障注入（回复前崩溃路径）**。引擎层不依赖 NoneBot 是测试可落地的架构前提（1.1）。

### 4.1 测试层级

- **单元测试（tests/unit/）**：engine/content/state 纯逻辑，不联网、不启 NoneBot。
- **集成测试（tests/integration/）**：commands → engine 全链路（用 NoneBot 测试夹具打桩）。
- **内容包冒烟测试**：对 content/ 全部预置包跑 validator + 模拟一局战斗（锁定→攻击→结算）。

### 4.2 引擎覆盖要求（必须覆盖）

| 模块 | 必测场景 |
|---|---|
| battle.py | 状态机合法流转（玩家行动→怪物反击→结算）；非法流转拒绝（战斗外攻击）；怪物丢失/出没时段结束退出；中断恢复续打；僵尸战斗回收（lifecycle.recycle_days） |
| damage.py | 判定顺序写死（命中→会心→格挡→双通道→防御率→拦截链→扣血）；边界：专注=0 命中下限 10%、会心封顶 95%、伤害下限 max(1, …)、格挡上限 40% |
| levelup.py | 经验曲线边界（0 经验/满级不增长/升级回满 HP/MP） |
| inventory.py | 堆叠上限、道具不耗回合、药剂同类型回合限次 1、绑定物品不可赠送/掉落 |
| equipment.py | 部位占用/互斥/数量校验、互斥环加载期拦截 |
| worldtime.py | 刷新补刷（含离线封顶 N 小时）、出没时段跨天（20:00-06:00）判定、非出没时段暂停刷新 |
| storage.py | SQLite 事务、崩溃恢复、并发写队列、自动保存防抖合并 |

### 4.3 存档往返测试（round-trip，硬约束）

- **往返原则：存什么 → 读什么 → 完全一致**。对每类快照（战斗快照/调合会话/状态印记/连段/商店限购）做序列化→反序列化→比对。
- 快照含 ID+名称冗余：测试删除配置后读档（按"无效果/无链/无印"降级，不抛异常）。
- 版本迁移测试：构造旧 schema_version 存档 → 迁移 → 断言字段级缺补默认/多忽略。
- 随机数一致性：中断恢复后同一回合随机序列一致（formula_state.random_seed 往返）。

### 4.4 伤害公式测试（确定性优先）

- **确定性用例**：固定种子/固定输入 → 断言精确数值（如 ATK=30、倍率 100%、无弱点、命中必中 → 期望伤害区间）。
- **性质用例（property-based）**：随机 1000 组属性 → 断言不变量：伤害 ≥1、不会心时在 [0.95,1.05]×基础 区间、会心率 ≤95%。
- **判定顺序用例**：构造同时满足"命中/会心/格挡"的输入，断言顺序执行（格挡作用于会心后、双通道相加后）。
- 公式参数全部来自 formula.json 参数段（damage/hit/crit/block/defense/weakness…），测试用独立 fixture 包，**禁止硬编码生产参数**。

### 4.5 故障注入（硬约束）

来源：《框架设计文档》15.16 + 保存失败兜底设计。核心场景：

| 故障点 | 注入方式 | 断言 |
|---|---|---|
| 回复前崩溃 | mock 发送出口抛异常 | 战斗状态回滚/可重试，不双结算（message_id 幂等） |
| 存档写入失败 | mock storage 抛 OSError | 弹"保存失败，请检查磁盘空间"，绝不静默丢数据；失败本地暂存可补写 |
| 热重载失败 | 写入非法 JSON 触发重载 | 回退上一份校验通过的 registry，服务不崩，人话提示 |
| 公式求值异常/超时 | 公式含死循环/非法变量 | 兜底 0 / 条件不满足，不崩溃 |
| 双扣防护 | 并发两条购买指令 | SQLite 事务下只扣一次（限购/货币） |
| 掉线重连 | 模拟网络断开 | 静默恢复或广播"我回来了"，玩家数据完好 |

- 每个故障注入用例必须有断言，禁止"不崩就行"的无断言测试。

### 4.6 测试基础设施

- 纯 Python 单测（pytest + pytest-asyncio），SQLite 用 `:memory:` 或 tmp_path fixture。
- 固定随机种子 fixture（伤害/掉落模拟用 seed 参数化）。
- 内容包测试样例放 `tests/fixtures/packs/`（合法包 / 坏引用包 / 缺模块包 / 旧 schema 包各一）。
- 覆盖率门槛：engine/ + content/ 行覆盖 ≥80%；新功能必须有测试才合入（TDD 或功能后补均可，但 PR 时必须有）。

## 七、安全规范

> 安全优先级：**公式沙箱 > 权限 > 防刷 > 数据安全**。本项目面向公网 QQ 群 + 公网编辑器，任何 RCE/越权都是 P0。

### 7.1 JS 公式沙箱（硬约束，安全例外不受"只建议不限制"覆盖）

依据《效果表达式变量体系定稿 v1.2》：

- **执行隔离**：`vm.runInNewContext` 隔离全局；代码强制 `'use strict'`；ctx 传**深拷贝只读快照**（不传宿主对象引用，防原型链污染）。
- **AST 静态黑名单**（加载时检查，命中=**拒绝加载**）：Identifier 禁 `constructor / __proto__ / prototype / Function / eval / globalThis / process / require / setTimeout / setInterval / fetch / XMLHttpRequest`；禁 NewExpression（`new Array / new ArrayBuffer / new RegExp / new String`…，战斗公式无任何 new 需求）。
- **资源上限**：公式长度 ≤4KB；结果类型白名单 number/boolean/string（≤1KB）；单次求值超时 vm timeout 10ms（防死循环/ReDoS）；校验/预处理放 worker 或防抖。
- **失败兜底**：运行期异常/超时 → 返回 0 / 条件不满足（try-catch 不崩溃）+ 日志警告。
- **随机数一致性**：Math.random 单次结算内缓存、回合内复用同一随机种子（显示与结算一致、中断恢复一致）。
- **新增公式调用点必须过沙箱**：代码评审 A 项 P0；禁止任何绕过（如直接 eval/exec/新开 VM 不设 timeout）。
- 内容包可配 `expr` 参数段（timeout_ms/max_len/result_max_len/cache_enabled/random_seed_per_turn），但**黑名单不可配**（安全例外）。

### 7.2 权限体系

- 三级权限：**机主**（数据库最高权限，全部）/ **GM**（机主授予，重载/备份/恢复/封禁）/ **普通玩家**（仅游玩指令）。
- GM 权限由机主在编辑器/数据库配置，**不自动授予群管理**。
- 无 GM 权限使用 GM 指令 → **直接无视**（不报错不提示，防暴露指令存在）。
- 封禁闭环：`/封禁 <QQ号> [时长] [原因]`、`/解封`、`/封禁列表`；被封玩家触发游玩指令 → 人话提示原因；封禁操作留痕（谁封/何时/到期）。
- 快捷绑定防绕过：**GM 指令不可绑定为快捷**（绑定层拦截 + 执行层权限二次检查，双保险）。
- 指令别名（command_aliases）不影响权限校验；`keep_original` 仅控制入口可见性。

### 7.3 编辑器安全（公网暴露面）

- 首次启动强制设密码（≥8 位含字母数字，弱密码拒绝）；登录 token 随机 + 过期 + 单设备互踢；**登录失败 5 次锁定 15 分钟**（防爆破）。
- **公网访问默认关闭**（仅 localhost），需手动开启；公网强制 HTTPS（内网穿透自带或反代），http 明文拒绝/警告。
- CSRF 防护 + 渲染转义（XSS）+ CSP 头。
- 服务器多人编辑：保存时版本冲突检测（行级冲突提示）。
- AI 辅助创作：BYOK（用户自带 Key），Key 仅存本机配置 600 权限，不上传任何第三方；**AI 只生成数据不执行任何操作**，全走预览确认 + 校验器。
- 编辑器 API 一律鉴权；未登录访问跳登录页，API 返回 401。

### 7.4 防刷与滥用防护

- 指令频率：全局每指令 ≥1s / 单群每分钟 ≤20 条 / 单日总量上限（见第 8 章，参数可配但默认值不得随意放宽）。
- 指令幂等：以 message_id 做幂等键，防重复结算/双扣。
- per-player 串行队列（同一玩家指令按到达顺序处理，防乱序）；世界级共享资源全局锁 + 事务 + CAS。
- 会话快照 version 号 + 指令幂等（防双扣/重复结算）；僵尸会话无操作回收（统一 settings lifecycle.recycle_days，可配 0=不限，防内存泄漏；默认天数见框架 settings 模块）。
- 消息长度/分页控制，防止单条消息过大触发风控。
- 敏感操作（全服重置/换包）必须二次确认（编辑器确认弹窗）。

### 7.5 数据安全

- SQLite 存档/备份/.bak 目录权限 600/700（防旁路读取玩家数据）。
- 日志脱敏：QQ 号/API Key 脱敏（RotatingFileHandler 大小+份数轮转）；"复制日志"按钮打包脱敏日志。
- CSV 双向防公式注入（= + - @ 前缀单元格转义或拒绝）。
- zip 导入：解压到临时目录 → 条目路径白名单（拒 `../` 与绝对路径，防 zip slip）→ 条目数/总大小上限（防 zip 炸弹）→ manifest 校验 → 全量校验通过后原子替换 + 触发重载。
- 备份恢复事务化：校验备份完整性 → 自动备份当前档 → 原子替换 → 失败自动回滚；备份保留周期（统一 settings lifecycle.backup_retention_days，可配）。
- 资源治理：VACUUM（周级或文件超阈值）、磁盘低水位监控（<15% 预警推送机主）、回收站自动清理（lifecycle.backup_retention_days 同键）。

## 八、QQ 平台约束

> 硬背景：QQ 平台对机器人消息频率/内容敏感，**防封号是最高优先级运营约束**（小白用户无法处理封号）。所有设计决策向"少发消息、发短消息、不像机器人"倾斜。

### 8.1 频率控制（默认阈值，可配但不可随意放宽）

- 全局：每指令处理间隔 ≥1s（指令防抖）。
- 单群：每分钟 ≤20 条机器人消息。
- 单日：总量上限（防突发刷屏）。
- 定时推送（公告/排行榜）默认关闭（"事件推送默认关，防刷屏"）；运营公告用定时 + 限频发送。
- 超出频率 → 丢弃或排队，绝不爆发式补发（风控退避：发送失败按指数退避重试，不无限重发）。

### 8.2 消息长度与结构

- 单条消息长度预算：渲染层统一预算，超长自动截断**分两条发送**（不吞消息、不超长）。
- 列表一律分页：背包/任务/商店默认 5 条/页（可配），翻页语法 `背包2`；筛选链（类型→子类→品质）减少翻页次数。
- 战斗状态行：默认显示前 5 个状态，超出追加"还有 N 个状态"（防一条消息塞满）。
- 渲染层：超长消息合并策略见 8.3；CQ 码转义防注入（消息段级提取 at/图片/表情）。

### 8.3 防封号核心策略（消息合并）

- **一轮一条消息**：玩家行动结算 + 怪物反击结算合并返回（框架设计文档 3.1）——消息量减半。
- 战斗开始 1 条、战斗结束 1 条（结算：EXP/金币/掉落/升级）、探索结果 1 条；**单次操作最多 1-2 条消息**。
- 1v1 回合制本身抑制刷屏（无全屏 AOE 播报、无大量状态广播）。
- 私聊 = 无干扰操作空间（看背包/整理装备不刷群屏）——把低频操作引导到私聊。
- 升级推送/稀有掉落推送默认关，作者显式开启（防惊喜变骚扰）。
- 机器人被风控冻结 → 明确提示"QQ 号被限制登录，请到腾讯安全中心解封或更换机器人 QQ"（启动器文案）。

### 8.4 内容与行为合规

- GM 指令对无权限者静默（不暴露指令存在，降低被举报面）。
- 角色名 ≤20 字，过滤控制字符与超长 emoji（防消息解析异常）。
- 不搞赌钱系统（PVP 明确不做赌注玩法——规避平台红线）。
- 敏感词：聊天内容不主动回复非指令消息（指令白名单匹配，无匹配忽略，减少无关发言）。
- 指令触发模式可配（@机器人/前缀/直接触发），但**默认全局快捷模式需配防误触**：只匹配白名单指令名开头、GM 指令永不快捷、频率控制照常。
- 消息发送出口统一封装：失败重试 + 风控退避 + 超长分条（所有发送路径必须走统一出口，禁止裸 send）。

## 九、文档规范

> 项目全部设计以"定稿文档"为准，框架主文档（《RPG回合制框架设计文档》）通过**登记段**回写各系统定稿。文档是唯一事实源，代码实现必须可追溯到文档。

### 9.1 定稿更新流程（硬约束：改定稿 → 登记段 → Changelog）

任何系统设计变更（新增模块/字段/机制、数值语义调整、判定顺序变化）必须三步走：

**第 1 步：改/写定稿文档**
- 系统级变更写独立定稿（如《效果系统设计定稿》《怪物行动AI设计定稿》），标注版本号 + 日期 + 用户拍板事项。
- 沿用格式：版本头（版本/日期/定位/变更摘要）→ 正文 → 校验器章节 → 设计依据尾注。

**第 2 步：框架主文档登记段**
- 在《RPG回合制框架设计文档》追加登记段（附 A/B/C/D/E…），声明"版本/定位/落点/总原则"。
- 登记段必须包含：新模块/字段元数据表（4.2 层）、校验器新增行（4.5 层）、快照扩展（A.5 层）、编辑器登记（6 层）、**判定顺序（写死保留）**、跨文档仲裁。
- 落点标注精确到章节锚点（"落点：4.1 模块树 + 4.1.1 manifest"），可直接 patch 进主文档。
- 登记段尾注写登记依据：定稿版本 + 用户拍板 + 检查结论。

**第 3 步：Changelog + 代码 + 测试**
- CHANGELOG.md 按 6.2 记录本次变更（Added/Changed/Fixed/BREAKING）。
- 代码实现登记段声明的字段/行为；测试补充对应用例（4.2-4.5）。

**强制规则：**
- 先有定稿/登记段，再写实现代码；代码与文档不一致 = P0 缺陷。
- 登记段与定稿冲突时，**以最新定稿为准**（登记段内已标注仲裁结论）；再冲突以《设计总纲：只建议不限制》优先。
- 跨系统变更必须走"跨系统登记"（如 v2.9 _cross_system_registration），逐项标注冲突仲裁。
- 文档版本号递增规则：登记段随主文档版本升（v2.9→v2.10→v2.12）；系统定稿独立版本。

### 9.2 文档格式约定

- 中文写作；版本头统一：`> 版本：vX.Y · 日期` + `> 定位` + `> 总原则`。
- 校验器章节必须区分**硬拦截**（引用不存在/类型错误/结构错误/负数）与**提示**（数值/概率/组合强度），措辞遵循总纲修正映射表。
- 所有上限声明附"可配 0=不限"；所有"写死"必须标注为结构依赖（判定顺序/管线顺序/引用关系）。
- 代码块示例用 json/text 标注；字段表用表格（字段名/中文名/类型/默认值/范围/引用目标）。
- 用户拍板事项必须记录（"用户拍板：…"），防止后续被推翻或重复讨论。

### 9.3 文档评审

- 定稿合入前过 3 项检查：① 与主文档/既有定稿无冲突（或已仲裁）② 校验器措辞符合总纲 ③ 登记段落点明确可 patch。
- 高风险变更（JS 公式、判定顺序、存档结构）建议多角度检查（如"3 子 agent 检查"模式：沙箱逃逸/内存炸弹/原型链/求值时机/状态语义/系统落点）。
- 文档即代码：docs 变更走 PR，与代码变更同流程评审。

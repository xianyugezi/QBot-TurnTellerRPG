## 1. 依赖关系表（逐模块）

### 1.1 先说清「依赖」是什么 —— 三层机制

要给小白写「一键勾选」，必须先分清三种完全不同的「依赖」。混在一起就会要么吓到用户，要么
勾了报错。

#### 第 0 层 · 声明门（决定数据「在不在」）—— 这是最重要的一层

> **`content/loader.py:284`**：「按声明顺序 + 注册顺序加载（缺失文件 → Y-6 继续；**未声明文件不加载**）」

即：`manifest.json` 的 `modules` 数组是**总开关**。没写进 `modules` 的模块，**它的
`<模块>.json` 根本不会被读取**（哪怕文件躺在包目录里）。于是：

1. 该模块的条目 id **不进入引用注册表**（`validator.py:451 _collect_ids` → `validator.py:469-470 _register_id`）；
2. 别的模块引用它就命中 **R-4「引用不存在」红拦**（`validator.py:3504-3526`）；
3. 任一红拦 → `loader.py:320-321` `_raise_if_blocked` → **整包拒绝挂载**（游戏起不来）。

**结论：模块开关不是"显示开关"，是"数据闸门"。** 这是本设计所有「硬依赖」的根因。

#### 第 1 层 · 硬依赖（不勾 → 红拦 / 整包挂不上）

- 判定规则：**R-4 引用不存在**（`validator.py:3522-3526`）+ 各专项校验器的 R-4/R-5。
- id 空间的 key = 模块 `ModuleMeta.kind`（`validator.py:466-467`；kind 表见 `field_meta.py:3155-3387`）。
- **重要豁免**：字段带 `soft_label=True` 时，`validator.py:3406-3407` **直接 return** ——
  该字段以及它**整棵子树**的引用校验全部短路。所以「软标注段里的引用」= **软依赖**。
  （本表已按此口径把「硬 / 软」分开；这一步若不做，会把 `enemies.ai`、`maps.gather_points`、
  `skill_chains.steps` 之类误判成硬依赖。）

#### 第 2 层 · 软建议（黄字「建议同时启用：X」，不硬拦）

- 唯一来源 = `module_catalog.py:38` 的 `requires` 字段；
- 计算：`web/api.py:980` `missing_requires`、`web/api.py:1358`；
- 渲染：`web/static/index.html:2289-2296` `moduleDepHint()` →「建议同时启用：X」；
- 开关时二次提示：`web/editor_ops.py:1057-1068`（启用时缺前置 → 提示；停用时被人依赖 → 提示）。
- 目录原文口径（`module_catalog.py:38-40`）：「**黄提示…不硬拦**」。
- **这批提示已有登记，以它为准** —— 本设计不推翻，只在其上补「硬依赖」。

#### 第 3 层 · 功能可用性（不报错，但「勾了也白勾」）

既不红拦也不黄提示，只是**没有数据来源**。最典型的三例：

| 例子 | 现象 | 依据 |
|---|---|---|
| `recipe` 勾了、`items` 没勾 | 材料 / 产出的物品引用**不校验**，配方能存但炼不出东西 | `alchemy_models.py:752-755`（N-1 note「items 模块未接线…降级 note」） |
| `codex` 勾了，但 `enemies`/`fishing`/`items`/`recipe`/`forge` 都没有 | 图鉴四册分母全 0 → 完成度恒 0，页面恒空 | `core/codex.py:43-53`（`CATEGORIES`：monster←enemy / item←item / fish←fishing / craft←forge∪recipe） |
| `gathering` 勾了、`items` 没勾 | 采集点产出物品引用不校验；但 `item` 字段本身**仍必填** | `map_models.py:334`（V-2Z）、`:330`（GP-02 必填） |

## 3. 冲突 / 坑

### 3.1 组合之间有没有互斥？—— **没有，5 个组合可以任意叠加**

**结论：不存在互斥模块对。** 依据（机制层面，不是经验）：

1. 模块开关的本质是**声明门**（`loader.py:284`「未声明文件不加载」）→ 声明**更多**模块只会
   **注册更多 id 空间**，是纯增量操作，不会让另一个模块失效；
2. 每个模块的数据住在自己独立的 `<模块>.json` 里（`loader.py:288`），物理上不抢占资源；
3. 校验器对同一个模块只判「结构 + 引用 + 值域」，没有「A 与 B 不能同时启用」这类规则
   —— 全库检索 `validator.py` 未见模块级互斥判定（仅有 **id 重名**与 **`excludes` 装备互斥位**，
   后者是**条目级**装备冲突，不是模块级）。

**唯一真实的"冲突"是 id 重名**，且它**跨组合叠加时最容易踩**（把 `basic_rpg` + `craft_master`
一起勾，会有 5 个模块同时写 `items`/`equipment`）。见 §3.2。

> 因此「推荐组合」的 UI 语义应当是 **「叠加勾选」**（勾第二个组合 = 并集），而不是
> 「二选一」。这也意味着：**同一模块被多个组合包含时，勾选必须是幂等的**（不能重复写进
> `manifest.modules`）。

---

### 3.2 冲突一：**同 namespace 的 id 重名 → R-5 红拦**

`validator.py:471-483` 的 `_register_id`：**namespace 相同 + id 相同 → R-5 `id_duplicate`（红拦）**。
namespace 由 `ModuleMeta.namespace` 决定（`field_meta.py:90-113` 的 `NAMESPACES`）。

| namespace | 成员模块 | 重名后果 | 依据 |
|---|---|---|---|
| `item_lib` | `items`、`equipment` | **红拦 R-5** | `field_meta.py:3239,3246`；`validator.py:471-483` |
| `effect_family` | `effects`、`statuses`、`marks` | **红拦 R-5**（三表 id **必须跨表唯一**） | `field_meta.py:90`（原注「ID 跨表唯一」）、`field_meta.py:3165,3175,3183` |
| `skill_lib` vs `action_lib` | `skills` / `action` | 仅**黄提示**（V-10 跨库重名） | `field_meta.py:113,3203-3205` |
| `job_lib` | `jobs` | 库内唯一 | `field_meta.py:3220` |

**踩坑风险最高的组合**：
- **`craft_master`（装备打造专精）** —— 重度同时使用 `items` + `equipment`，最易写出同名 id
  （例如物品里已有 `iron_sword`，装备表又建一个 `iron_sword`）。
- **任何带战斗的组合** —— `effects`/`statuses`/`marks` 三表都要 id 唯一。写「灼烧」状态叫
  `burn`，又写一个 `burn` 效果 → 红拦。

**处理建议（给批65）**：
1. **不自动改用户的 id**（会破坏引用）；
2. 组合勾选**不触发**该冲突（冲突来自内容，不来自勾选），所以**不需要**在组合层拦；
3. 但建议组合说明里**加一行小白提示**：「同名的效果/状态/印记只能有一个」；
4. 校验红拦文案里已有 `previous_module` 字段（`validator.py:478`）→ 可直接告诉用户「和哪个模块的哪条重名」。

### 3.3 冲突二：**「勾了但没有数据来源」的空转模块**（任务点名的重点）

这是最容易被忽略、也最伤小白体验的一类：**不报错、不提示，但勾了完全没用**。

#### 实测证据（逐包统计模块声明数 vs 实际条目数）

在 `veinborn`（29 模块）、`test_demo`（27）、`zz_craft_demo`（8）里逐模块数条目，**空转实测结果**：

### 3.4 处理建议总表（自动补 vs 提示）

给批65 的三档策略（**按依赖类型分流，不要一刀切**）：

| 依赖类型 | 例子 | 策略 | 理由 |
|---|---|---|---|
| **目录已登记的 `requires`** | `equipment`→`items`、`enhance`→`equipment`、`gathering`→`maps` | **勾组合时自动补进 `modules`**，并在 UI 标「（自动带上）」 | 框架已声明；不补会黄提示，补了体验最好 |
| **校验器硬依赖但目录未登记** | `gathering`→`items`、`dungeon`→`maps`+`enemies`、`conditional`→`stats`、`fishing`→`maps`+`settings` | **先补 `module_catalog.requires`（改数据），再由上一条自动生效** | 避免组合机制里硬编码一份"隐藏依赖表"（会漂移） |
| **数据条件依赖**（填了字段才需要） | `items.grant_skills`→`skills`、`enemies.traits[]`→`traits`、`equipment.job_restrict`→`jobs` | **不自动勾**；在**字段级**给黄提示（或纳入 `on_demand` 由编辑器在保存时提示） | 自动勾会把 11 模块的 `basic_rpg` 膨胀成 15 模块，违背"最小集" |
| **功能软 / 空转**（E1-E10） | `codex` 无四册来源、`forge` 无产物、`contest` 无产出 | **黄提示**（不自动勾） | 自动勾会把组合变成"全选"，且这些模块确实可以孤立存在 |
| **功能重叠**（E14） | `slots` vs `settings.slot_defs` | **沿用既有 `overlap_with` 黄提示**，组合里降为 `recommended` | `module_catalog.py:87-99` 已裁决过口径 |

### 4.1 风格对齐说明（为什么这样写）

仓库里已有两个「预设」先例，字段风格已定，本草案**沿用而不另创**：

| 先例 | 位置 | 字段风格 | 本草案沿用 |
|---|---|---|---|
| 模块目录 | `module_catalog.py:30-56` | `@dataclass(frozen=True)` + `Tuple[Entry, ...]` + `CATALOG_BY_MODULE` 索引 | ✔ 同形（`ModulePreset` dataclass + `MODULE_PRESETS` tuple + `PRESET_BY_ID`） |

> ⚠ **命名避让**：`entry_presets.py` 的 "preset" 指**条目级预设**（新建物品时选"材料/药剂"）。
> 本草案的 "preset" 指**模块组合**。建议**不要**共用一个词根命名 API，
> 或至少在 docstring 里互相指路，否则后续维护会混。

### 4.2 Python 片段草案（建议新增 `qbot_rpg/content/module_presets.py`）

```python
"""框架推荐组合（模块预设）——「一键勾选一批模块」的数据源。

定位（批65 机制侧消费）：
  · 空白包/新包的作者不知道从哪开始（同 `module_catalog.py:3-5` 的痛点）；
  · 本表给 4~6 个**成品组合**，点一下就把一批模块写进包 `manifest.json` 的 `modules`
    并按骨架创建数据文件（写入机制归批65 / `web/editor_ops.set_module_enabled`）。

与相邻概念的分工（**不要混**）：
  · `module_catalog.py`  ：**单个**模块的框架通用知识（含 `requires` 软提示）；
  · `entry_presets.py`   ：**条目级**预设（新建一条物品/装备时选"材料/药剂"）；
  · 本模块               ：**模块级**推荐组合（本文）。

设计口径（依据见 `模块预设组合_设计.md` §1~§3）：
  · `auto_added` = **硬依赖闭包**（不勾会 R-4 红拦 / 功能不可用），必须一起写进 modules；
  · `recommended` = **软建议**（黄提示，不自动勾）——含"空转"提醒与功能重叠提醒；
  · `on_demand`  = **数据条件依赖**（用户填到相关字段才需要），**不自动勾**，由字段级提示承担；
  · 三条铁律：模块键必须 ∈ `CATALOG_BY_MODULE`（不臆造）；`picks ∩ auto_added = ∅`；
    勾选必须**幂等**（同一模块被多个组合包含时不得重复写入）。
"""

from __future__ import annotations

from dataclasses import dataclass
from typing import Dict, Tuple

from qbot_rpg.content.module_catalog import CATALOG_BY_MODULE


@dataclass(frozen=True)
class ModulePreset:
    """一个「推荐组合」。

    id         ：组合键（英文 snake_case；API / URL 用）
    label      ：中文名（面向非技术用户）
    help       ：一句话说明（≤30 字；面板副标题，说"这是做什么的"）
    audience   ：适用人群（一句话，帮用户自己对号入座）
    picks      ：卖点模块——**用户看得见、决定选不选这个组合**的模块；
                 面板里高亮，说明文字里点名。
    auto_added ：因硬依赖被一起勾上的模块（UI 标「（自动带上）」）
    recommended：配套建议（黄字提示，**不自动勾**）
    on_demand  ：数据条件依赖（填到相关字段才需要，**不自动勾**）
    why        ：为什么是这些（一句依据；给编辑者审查用，不展示给小白）
    order      ：面板展示顺序（小 → 前）
    """

    id: str
    label: str
    help: str
    audience: str
    picks: Tuple[str, ...]
    auto_added: Tuple[str, ...] = ()
    recommended: Tuple[str, ...] = ()
    on_demand: Tuple[str, ...] = ()

def module_preset_key_errors(
    presets: Tuple[ModulePreset, ...] = MODULE_PRESETS,
) -> Tuple[str, ...]:
    """组合自检：返回问题描述元组（空 = 全绿）。

    与 `entry_presets.framework_preset_key_errors` 同口径（测试与自检共用），
    检查 4 条：
      ① 组合 id 唯一；
      ② 所有模块键 ∈ `CATALOG_BY_MODULE`（**不臆造模块名**）；
      ③ `picks ∩ auto_added = ∅`（同键不得既是卖点又被"自动补"）；
      ④ **硬依赖闭包**：每个 `modules` 成员的目录 `requires` 必须已在 `modules` 里；
         若未在、但已登记在 `recommended`/`on_demand`，则**不算错**（是"软"的）；
         两边都没有 → 报错（说明组合自己漏了依赖）。
    """
    out = []
    seen = set()
    for p in presets:
        if p.id in seen:
            out.append(f"preset id 重复: {p.id}")
        seen.add(p.id)
        mods = set(p.modules)
        for key in p.modules + p.recommended + p.on_demand:
            if key not in CATALOG_BY_MODULE:
                out.append(f"{p.id}: 未知模块键 {key!r}（不在 CATALOG_BY_MODULE）")
        for key in p.auto_added:
            if key in p.picks:
                out.append(f"{p.id}: {key!r} 同时在 picks 与 auto_added")
        declared_softly = set(p.recommended) | set(p.on_demand)
        for key in p.modules:
            entry = CATALOG_BY_MODULE.get(key)
            if entry is None:
                continue
            for req in entry.requires:
                if req not in mods and req not in declared_softly:
                    out.append(
                        f"{p.id}: {key!r} 的 requires {req!r} 既不在 modules "
                        f"也不在 recommended/on_demand（硬依赖漏了）")
    return tuple(out)


__all__ = [
    "MODULE_PRESETS",
    "PRESET_BY_ID",
    "ModulePreset",
    "module_preset_key_errors",
]
```

**字段说明（给批65 的实现约束）**

| 键 | 类型 | 用途 | 注意 |
|---|---|---|---|
| `labels` | `{module: 中文名}` | 面板显示 | **必须走包声明优先**（`web/api.py::_display_labels`，`module_catalog.py:10-13` 的口径）——不要直接读目录里的默认名 |
| `already_enabled` | `[module]` | 已启用的显示"已勾" | 用于**幂等**：只对 `to_enable` 调 `set_module_enabled` |
| `to_enable` | `[module]` | 需要新勾的差集 | `= modules − already_enabled`；**空数组 = 该组合已全勾**（UI 应禁用按钮/显示"已启用"） |
| `count` | `int` | 面板显示"共 N 个模块" | `= len(modules)`（不含 recommended） |
| `recommended` / `on_demand` | `[module]` | 勾完后追加黄提示 | 复用 `editor_ops._dep_warning()` 的形状（`{level:"yellow", code:..., message:..., how_to_fix:...}`），建议 `code="module_preset_suggestion"` |

**写入语义（三条，必须写进批65 的实现）**

1. **并集写入**：`new_modules = 既有 modules ∪ preset.modules`，**保序**（既有的在前），
   去重 —— 绝不能整体替换。
2. **幂等**：对 `already_enabled` 里的模块**不重复调用** `set_module_enabled`，
   避免重复创建骨架 / 重复写盘。
3. **一个组合 = 一次事务**：批65 若逐个模块调用 `set_module_enabled`，
   中间失败会留下"勾了一半"的包。建议**先在内存里算好目标 `modules` 与文件骨架，
   一次写盘**；或复用现成的批量写入口。

> **对齐 `loader.py:84-93`**：`manifest.modules` 的**书写顺序不影响正确性**
> （`_ordered_declared` 会按 `FIXED_REGISTER_ORDER`（`loader.py:46`）重排注册序）。
> 因此不必在写盘时排序；但为了阅读友好，建议按
> `settings → stats → formula → effects → statuses → marks → …` 的目录顺序写。

# M0 复查 · 批1-路5 · 架构分层契约（G0）静态审查报告

> 审查对象：`qbot_rpg/` 全目录分层结构（core/storage/content/data/world/commands/web 各 `__init__.py` 与模块 docstring）、`qbot_rpg/commands/errors.py`、`qbot_rpg/world/session.py`、`tests/contract/test_g0_architecture.py`（含其依赖的 `scripts/check_architecture.py`）。
> 基准：`细化_3a_架构分层契约.md`（铁律 R1~R6、目录职责 §2.1、领域模型 D-03/D-04/D-06、纯字符串契约 §5、验收 TC-01~22）。
> 方法：**纯静态审查**（read/glob/grep 文本扫描）；本环境无 bash 沙箱且任务明令禁止运行任何命令/脚本，故一切"能否通过/能否运行"结论均以**【静态推导】**标注，不构成运行验证。
> 结论分级：P0（阻断/已存在违规）= **0**；P1（严重缺陷/门禁隐患）= **1**；P2（改进/潜在/文档类）= **4**。

## 一、总体结论

分层架构的**实际落地与契约高度一致**：R1/R2/R3/D-03/D-04/D-06/§5 在当前代码上（静态）全部满足，未发现已存在的分层违反、依赖方向错误或 import 泄漏（P0 = 0）。

唯一 P1 出现在**验收工具本身**：`scripts/check_architecture.py` 的 `find_nonebot_imports` 对 `from nonebot import X`（ImportFrom 形态）存在**静默漏检盲区**，而 `tests/contract/test_g0_architecture.py` 的 TC-01/TC-02 直接复用该函数，导致 R1/R2 这一 P0 级铁律的验收门禁无法检出其契约明文列举的违规形态。属「缺漏」维度的严重项。

其余 4 项为 P2：errors.py 设计注释自相矛盾（幻觉维度）、core 领域异常文案口径（R4 边界）、检查脚本 `layer_of`/相对 import 解析的潜在缺陷（潜伏）、data 层 typing_extensions 兜底（已知接受项）。

## 二、P1 问题（1 项）

### P1-1 【缺漏/门禁失效】`find_nonebot_imports` 漏检 `from nonebot import X`（ImportFrom 形态）

- **位置**：`scripts/check_architecture.py` L133-151（核心缺陷在 L141-148）；受影响测试 `tests/contract/test_g0_architecture.py` L44、L56（TC-01/TC-02 直接复用 `arch.find_nonebot_imports`），及 L25-32（子进程跑脚本 TC-01/TC-02）。
- **问题**：对 `ast.ImportFrom` 节点，代码只遍历 `node.names`（被导入的符号名）并与 `"nonebot"` 比对，**从未检查 `node.module`**：
  - `import nonebot` / `import nonebot.adapters` → `alias.name` 为模块名 → 能检出 ✅
  - `from nonebot import on_command` → `node.module=="nonebot"`，`alias.name=="on_command"` → **不匹配，漏检 ❌**
  - `from nonebot.adapters.onebot.v11 import Bot, Message` → `alias.name=="Bot"` → **漏检 ❌**
- **契约违反**：细化_3a R1 明文「不得出现 import nonebot（**含 from nonebot...** / importlib 动态加载）」；TC-01 要求断言「Import/ImportFrom 节点」。`from nonebot import ...` 恰是 NoneBot 插件最惯用写法，正是契约点名要抓的形态。当前代码恰好全为注释/无真实 import（故测试不红），但一旦任何零层文件写入该形态，门禁会**静默放行**——R1/R2 验收形同虚设。
- **静态推导**：当前 `qbot_rpg/` 内所有 `nonebot` 命中均为 docstring/注释（errors.py L8、commands/__init__.py L4-5、router.py L9-10、sender.py L10、parsers.py L7、web/api.py L5、content/hot_reload.py L137/L157），无真实 import；故测试当前可过，问题在于「该过时过、该拦时拦不住」。
- **修复建议**：在 L146 的比对前，对 `ast.ImportFrom` 先取 `node.module` 单独判断（`node.module == "nonebot" or (node.module or "").startswith("nonebot.")`），再叠加现有 `alias.name` 逻辑；并补一条用例：构造含 `from nonebot import on_command` 的临时文件喂给 `find_nonebot_imports`，断言命中。
- **级别说明**：因当前无真实违规，未升 P0；但 R1/R2 为 P0 级铁律，门禁盲区应视为**优先修复项**，可在评审中按 P0 隐患对待。

## 三、P2 问题（4 项）

### P2-1 【幻觉/设计矛盾】`commands/errors.py` 声称「领域异常类型在此定义」，与 R3/R4 及自身 docstring 自相矛盾

- **位置**：`qbot_rpg/commands/errors.py` L28-29（`errors()` 注释「M4 实装：领域异常类型（BattleNotInProgress 等**在此定义**）」，L30-32 抛 NotImplementedError）；对照同文件 L3（docstring「**捕获** core/world 抛出的领域异常」）。
- **问题**：同文件两处自相矛盾——docstring 说 errors.py 是「翻译器」只捕获 core/world 抛出的异常；函数注释却说异常类型「在此定义」。若 M4 按后者落地，core 需 `import` 该异常才能抛出，将产生 **core → commands 反向依赖 = R3 P0 违规**（core 禁止依赖 commands）。当前实际领域异常均已正确落在所属层：`BattleStateError`（core/battle.py L195）、`SessionConflictError`（world/session.py L20）、`WorldNotFoundError`（world/game_world.py L23）、`StorageError`（storage/connection.py L44）——唯独这处注释指向错误设计。
- **修复建议**：将 L29 注释改为「领域异常定义在所属层（core/world/storage），此处仅登记翻译映射」；`errors()` 若保留占位，建议改为返回异常→文案映射的 dict 签名，避免与翻译语义冲突。

### P2-2 【错误/边界】core 领域异常消息含用户可读句子，R4「内部标识」口径偏弱；契约点名异常 `BattleNotInProgress` 未实现

- **位置**：`qbot_rpg/core/battle.py` L369/L371/L909/L997/L1001/L1003/L1486/L1574/L1577/L1605（`BattleStateError` 消息含「战斗已终局」「无法开始新回合」「已死亡/退场」等可直接面向用户的中文句子，混排内部引用「1g1b §一」）。
- **问题**：细化_3a §5.4/TC-19 要求 core 异常消息为「内部标识，非用户文案」（如示例 `BattleNotInProgress`），文案只由 commands/errors.py 翻译。当前消息可读中文句子 + 规范引用混合，属**边界状态**：未直接外发（壳层翻译），但若 M4 errors 简单透传即成 R4 违规；且契约 §5.4 点名的 `BattleNotInProgress` 异常全仓不存在（被通用 `BattleStateError` 取代），`commands/errors.py` 的翻译注册表将无对应键。
- **修复建议**：core 异常收敛为内部错误码/枚举（如 `BattleStateError(code="NOT_IN_BATTLE")`），可读文案彻底移出引擎；M4 errors 以 code 为键翻译。属 M1 战斗里程碑范畴，可顺带在 M4 对齐。

### P2-3 【缺漏/潜伏】`check_architecture.py` 两处解析缺陷（未造成当前误报，但削弱工具健壮性）

- **位置**：
  - `scripts/check_architecture.py` L100-106 `layer_of`：对 `qbot_rpg/__init__.py`，`parts=["qbot_rpg","__init__.py"]`，`i+1 < len(parts)` 恒真 → 返回文件名 `"__init__.py"` 而非 `"root"`（`root` 分支实际不可达）。后果：TC-03 中该文件 `ALLOWED_DEP.get("__init__.py")` 为 `None` → 方向检查对根包**静默跳过**（当前根包无 import，无实害）。
  - `scripts/check_architecture.py` L255-270 相对 import 解析：`from . import sibling`（level=1, module=None）会解析到 `qbot_rpg/__init__.py` 制造**伪 root 边**，而非同层兄弟模块（当前 qbot_rpg/ 无相对 import，未触发）。
- **静态推导**：上述两点当前均不产生误报/漏报，属潜伏缺陷。
- **修复建议**：`layer_of` 特判文件名 `__init__.py` → 返回上层包名或 `root`；相对 import 的 `sub==""` 分支应遍历同包模块而非回退到包 `__init__`。

### P2-4 【缺漏/已知接受】`data/types.py` 以 `typing_extensions` 兜底，弱化「data 仅标准库」约束

- **位置**：`qbot_rpg/data/types.py` L20-23（`try: from typing import TypeAlias` / `except: from typing_extensions import TypeAlias`）。
- **问题**：细化_3a §1.4/§2.2 规定 data「仅标准库（dataclasses/typing/enum）」「最底层，零外部依赖」；§3.1 又要求 Python 3.9 兼容。Python 3.9 下需 `typing_extensions` 第三方包，`qbot_rpg.data`（经 `tests/conftest.py` L12 导入）将不可 import，违反「仅标准库」字面约定。当前环境为 Python 3.11（.venv），`typing` 自带 `TypeAlias`，运行不受影响。文件内已自注「P2-13 修复：注释承诺的 typing_extensions 兜底落地」——属**已知、已接受**的既有偏差项，本次仅登记复核确认。
- **修复建议**：维持现状可（已知项）；若求严格合规，可把 Python 最低版本明确提至 3.10 并在 pyproject 声明，或改 `import typing_extensions` 为纯 `typing` 条件导出。

> 需求源头：用户 2026-09-19 口述「**材料相性这个设定可以共享给深度炼金用，相性影响药剂效果之类的**」
> （`docs/深度打造_决策记录.md:47-48`）
> 上游定稿：`docs/审查参考/炼金系统设计定稿.md`（三层结构）、`/root/deliverables/打造系统_原案_20260919.md` §8/§12
> 通用层现状：`qbot_rpg/core/affinity.py`（批 38 落地，`docs/深度打造_决策记录.md:60`）
> 本报告性质：**只读仓库 + 设计**，不含实现代码、不改仓库任何文件。
> 结论口径：**唯一源 = `core/affinity.py` + `data/affinity_keys.py`；炼金侧只调用，不另造一套**（红线）。

## 〇、一句话结论

> **通用层已经够用，不必为炼金改 `core/affinity.py` 的现有四个接口**——`accumulate_affinity` /
> `rank_affinities` / `resolve_available_entries` / `resolve_affinity_effect` 四个函数**原样即可**
> 支撑三种口径的「材料相性 → 主副相性 → 效果取值」主干（已实测跑通，见 §六 抽样自证）。
>
> **缺口全部在炼金侧的数据通路与产出承载上**，共 4 条（§一.3）：
> ① 材料相性没进炼金快照（`alchemy_core.py:407-419`）；
> ② 池条目 `weight` 无消费者、通用层无加权抽取接口（`field_meta.py:413`）；
> ③ 结算算出的 `scaled_effects` 不落实例（`alchemy_settle.py:367` vs `:383`）；
> ④ 使用路径只读物品定义、不读实例（`use_commands.py:310-331`），强度型无处落地。
>
> **唯一建议动通用层的地方是「池条目作用域」**（§三，用于区分药剂专属词条与装备词条），
> 而且**可以做成可选参数、缺省零行为变化**；是否动，属 §五 待裁决。

### 1.1 `core/affinity.py` 现有接口（全部为纯函数、确定性、零 content import）

### 1.2 已经能直接支持「药剂效果受相性影响」的部分（不必动）

- **A. 材料投入顺序已经存在，`accumulate_affinity` 的入参形态天然对得上。**
  炼金 `apply_feed` 构造 `new_chain = list(base) + records`（`core/alchemy_core.py:782-783`），
  并把有序链写进快照 `snap2["materials"] = new_chain`（`core/alchemy_core.py:819`）。
  原案要求「材料互动的结算顺序按照材料的投入顺序」（`打造系统_原案_20260919.md:58`），
  与 `accumulate_affinity` 的顺序敏感实现（`core/affinity.py:185-226`）**语义一致，零适配成本**。
- **B. 主/副相性判定无需新逻辑。** `rank_affinities` 的「最高=主、第二=副」（`core/affinity.py:255-259`）
  即原案 §8 口径（`打造系统_原案_20260919.md:33-34`）。
- **C. 池模型与打造同源，且 `requires_affinity ⊆ {main, sub}` 的过滤已实现。**
  `core/affinity.py:334-340` 的 `have = {main, sub}` 过滤意味着：**副相性词条也能抽出来**
  （已实测，见 §六 抽样 B-1），这正是原案「专属池 + 联动覆盖」的所需语义。
- **D. 效果取值表按 (主[,副]) 二分键查表，且「更具体的键优先」。**
  `core/affinity.py:369-376` 先查 `"main|sub"` 再查 `"main"`——强度型系数表可以直接声明两档精度，
  无需新增接口。
- **E. 已注册进的校验与编辑器可见性，炼金侧可直接复用。**
  settings 四段字段元数据：`content/field_meta.py:393-442`；
  材料/图纸 `affinities` 声明字段：`content/field_meta.py:2349-2352`（items 保留键见 `:1600`）；
  校验器：`content/validator.py:1866-2038`（含**跨模块**材料相性键引用红拦 `:2020-2038`）。

### 1.4 炼金侧现状的两条并存效果字段（接入前须先对齐）

- 炼金**结算**读的是 `base_effects`（珠的基础效果）：`core/alchemy_settle.py:371`、`:322-333`。
- 真实内容包（veinborn）的**药剂**用的是 `effects: ["heal_small"]`（效果 ID 引用，见 `content/veinborn/items.json`
  `pulse_potion` 条目），数值在 `content/veinborn/effects.json` 的 `{type:"heal", power:50}`。
- `/道具` 使用路径读的是 `item_def["effects"]`（`commands/use_commands.py:314`），**不是 `base_effects`**。

即：**「药剂」当前走 `effects` 引用链，「装饰珠」走 `base_effects` 数值链**。相性接入选哪条链，
直接决定强度型落在哪（§五 Q5）。这属「相性→药剂效果」的前置对齐项，非本设计能替代裁决。

## 二、「相性 → 药剂效果」的三种可能口径

> 三者**不互斥**，可单选/组合。共同主干（已验证跑通）：
> `材料 affinities 序列 → accumulate_affinity → rank_affinities → (main, sub) → 各口径取值`。
> 下表的「声明形状」全部写在**内容包**（不改框架），生效点全部在**炼金侧**。

### 口径 A · 强度型（相性 → 效果强度/持续时间系数）

**语义**：主（必要时叠加副）相性 → 一个系数，作用于成品效果数值/持续回合。

**声明形状（内容包 settings，示意）**
```jsonc
// settings.alchemy.affinity_effect   —— 交给 resolve_affinity_effect() 取值的表
{
  "炎火":            { "effect_mult": 1.2,  "duration_mult": 1.0 },
  "炎火|雷":         { "effect_mult": 1.35, "duration_mult": 1.2 },
  "冰晶":            { "effect_mult": 0.95, "duration_mult": 1.5 }
}
```

**调用顺序（全部为现有接口）**
```
accumulate_affinity(材料相性序列, settings.affinity_reactions)   # core/affinity.py:148
  → rank_affinities(累计, settings.affinities)                    # core/affinity.py:233
  → resolve_affinity_effect(settings.alchemy.affinity_effect, main, sub)  # core/affinity.py:351
  → （炼金侧）把 effect_mult 乘进现有 coef 流程
```
生效参考点：`core/alchemy_settle.py:522-523`（`tier = score_to_tier(score)`；`coef = coef_for(tier)`）
——相性系数与品质系数**相乘**是最小改动落点（相性成为第二个乘区）。

**须由深炼金细化提供**
1. 系数**作用面**：是「全部数值叶」（照 `_scale_effects` 的递归口径 `alchemy_settle.py:322-333`），
   还是只作用某个字段（如 `power`）？
2. 与品质系数（`quality_coef`，定稿 `:412`）的关系：**相乘**还是**相加**？是否设上下限封顶？
3. 是否作用**持续回合**（定稿 `:388` 原子动作词汇表含 `概率触发`/`aoe` 等，需点名哪些受相性缩放）。
4. 副相性是否参与强度（若不参与，只用 `"main"` 键即可，无需 `"main|sub"`）。

**已知落地阻塞**：G3 + G4（系数乘完不落实例、使用链路不读实例）。

---

### 口径 B · 附加型（相性 → 追加附加效果/状态）——**优先复用池模型**

**语义**：主/副相性 → 从相性池里取词条 → 追加为成品的附加效果（如 冰晶 → 附「减速」）。

**声明形状（内容包 settings，与打造同一套池）**
```jsonc
// settings.affinity_pools  —— 与打造共用，不新建第二套池
[
  { "id": "p_common", "kind": "common", "entries": [
      { "stat": "atk", "weight": 10 },
      { "effect_ref": "slow", "requires_affinity": "冰晶", "weight": 30 }   // 副相性也可抽
  ]},
  { "id": "p_fire", "kind": "exclusive", "entries": [
      { "effect_ref": "burn",   "weight": 50, "min_level": 3 }
  ]},
  { "id": "p_ice",  "kind": "exclusive", "entries": [
      { "effect_ref": "freeze", "weight": 50 }
  ]}
]
// settings.affinities[].exclusive_pool 指向 p_fire / p_ice；settings.affinity_linkage 做联动覆盖
```

**调用（现有接口 + 一个抽取步）**
```
resolve_available_entries(config, main, sub, level=炼金职业档或配方等级)   # core/affinity.py:293
  → 得到候选行（每行带 _pool/_pool_kind，可追溯）
  → （缺失步 G2）按 weight 抽 1~N 条
  → 取行内 effect_ref，追加进成品效果
```
效果侧可复用定稿既有口径：状态异常复用 effects 原子动作（定稿 `:285`）。

**须由深炼金细化提供**
1. **抽几条**（固定 1 条 / 按连锁段数 / 按主相性值档位）？
2. **谁来抽**：成品**自动**附加，还是像特性继承那样进**候选清单供玩家选**（`build_feature_pool`
   口径是"供玩家 /继承 选"，`core/alchemy_core.py:633-680`）？
3. 附加效果与**特性继承（traits）/ 超特性**的关系：是进 `traits` 池，还是独立的 `effects` 附加位？
   （定稿 `:266-268` 明确「base_effects 珠基础效果」与「traits 继承特性」是**两套词条**。）
4. 抽取是否消耗 PP（特性继承消耗 PP，`core/alchemy_core.py:689-711`）？

### 口径 C · 成功率/品质型（相性 → 成功率、品质档、特性与超特性出现率）

**前置事实（先核查，已核查）**：

| 项 | 现状字段名与落点 | 结论 |
|---|---|---|
| 成功率 | **不存在**。定稿 `:167`「基础调合 100% 成功」 | 相性**无法**影响成功率，除非新增机制（须用户裁决） |
| 品质档 | `settings.alchemy.quality_tiers`（定稿 `:411`）；`QualitySystem.score_to_tier / cap_quality / coef_for`（`core/alchemy_settle.py:497-524`） | ✅ 有现成落点（`extra_cap` / `mean` / `score`） |
| 品质系数 | `quality_coef`（定稿 `:412`；实测 `commands/alchemy_commands.py:864` 注入） | ✅ |
| 特性字段名 | `traits.json`：`rarity(normal/super)`、`group(互斥组)`、`repeatable`、`source(素材/成品/金色素材)`（定稿 `:374-375`）；代码消费：`pp_cost_of` 按 `rarity=="super"` 计价（`core/alchemy_core.py:689-695`） | ✅ 字段已存在 |
| 超特性 | **第 4 特性位独占**：定稿 `:201`（`gold_slot_exclusive`）、`:243`；代码落点 `build_feature_pool` 的 `gold` 桶（`core/alchemy_core.py:645,676`）+ `alchemy_deep.py:82`（D-10 第 4 位金色独占） | ✅ 结构已有 |
| 特性**出现率** | **不存在概率机制**：`build_feature_pool` 收集候选后**全部**可继承，无 roll | ⚠️ 新机制 |

**声明形状（内容包 settings，示意）**
```jsonc
// settings.alchemy.affinity_quality   —— 交给 resolve_affinity_effect() 取值
{
  "冰晶":        { "quality_bonus": 5 },        // 加到品质分/上限
  "炎火|雷":     { "quality_bonus": 10, "super_trait_rate": 0.15 },
  "月光":        { "quality_mult": 1.1,  "trait_pool_bias": "gold" }
}
```

生效参考点：`core/alchemy_settle.py:497`（品质均值）、`:500-503`（`_extra_cap` → `cap_quality`）、
`:516-519`（刻度降级后 `score`）。特性侧须新增概率步（当前无）。

**须由深炼金细化提供**
1. 落到**哪一档**：品质分加值 / 品质上限加值（`extra_cap` 口径）/ 品质系数乘区？三者语义不同
   （上限是封顶、加值改分布）。
2. **超特性出现率**是否要新造概率机制（当前 0 概率机；且特性是"玩家自选继承"，
   加概率 = 改交互模型，**代价最大**）。
3. 是否设「品质分/系数上限」避免与核心镶嵌（`extra_cap`，定稿 `:202`）、挑战（品质上限+10，定稿 `:214`）叠爆。

## 三、池共享：打造与炼金共用同一套定义/互动/池

### 3.1 共用部分（**零新增，直接共享**）

| 共享项 | 唯一源 | 两系统怎么共用 |
|---|---|---|
| 相性定义 | `settings.affinities`（`field_meta.py:393`） | 打造图纸/装备与炼金配方/药剂引用**同一批相性 id**（`validator.py:2020-2038` 已做跨模块键引用红拦） |
| 词条池 | `settings.affinity_pools`（`field_meta.py:403`） | 同一个 `resolve_available_entries`（`affinity.py:293`）服务两侧 |
| 互动规则 | `settings.affinity_reactions`（`field_meta.py:430`） | 两侧都走同一个 `accumulate_affinity`，**投入顺序**语义统一（原案 `:58`） |
| 联动覆盖 | `settings.affinity_linkage`（`field_meta.py:422`） | `_matched_linkage`（`affinity.py:280-290`）同款判定 |
| 材料相性声明 | items/equipment 条目 `affinities`（`field_meta.py:2349`） | 打造材料与炼金材料是**同一张 items 表**，天然共享 |

> 原案「本质就是一个池子，但如果没有对应相性，部分词条就抽不出来」（`打造系统_原案_20260919.md:57`）
> 已在 `resolve_available_entries` 实现：**单次查询 = 通用池 ∪ 主相性专属池（联动命中则被覆盖）**，
> 再按 `requires_affinity ⊆ {main,sub}` 过滤（`affinity.py:322-344`）。**这是"优先复用"的落点，无需重写。**

### 3.2 炼金专属词条怎么在同一池模型里表达（三种声明形状）

#### 方案 P1（**推荐**）· 池条目加 `scope` 作用域字段

在同一池内用**条目级作用域**区分用途；`scope` 命名沿用仓库既有先例
（`field_meta.py:487`「限流粒度 player/group」、`:598`「商品范围」）。

```jsonc
// settings.affinity_pools[].entries[]
{ "effect_ref": "burn",   "weight": 50, "scope": ["craft"] },              // 只给打造抽
{ "effect_ref": "slow",   "weight": 30, "scope": ["alchemy"],              // 只给炼金抽
  "requires_affinity": "冰晶" },
{ "stat": "atk",          "weight": 10 }                                   // 不写 scope = 两侧通用
```

- **接口改动**：`resolve_available_entries(config, main, sub, level=None, scope=None)`
  —— `scope=None` **不过滤**（完全向后兼容，批 38 全部既有调用/测试零变化）；
  `scope="alchemy"` 时保留「无 scope 条目」∪「scope 含 alchemy 的条目」。
- **改动面**：`core/affinity.py`（一个可选参数 + 一个过滤分支）、`field_meta.py`（条目加字段）、
  `content/validator.py`（enum 校验）。**data/affinity_keys.py 新增一个 `ENTRY_SCOPES` 常量**（与
  `POOL_KINDS` 同处，`affinity_keys.py:28-31`）。
- 优点：**一个池、一套查询**，符合原案"本质一个池子"；药剂词条与装备词条可在同一专属池内混排；
  也允许"某相性专属池整池都是药剂词条"（全部条目写 `scope:["alchemy"]`）。

#### 方案 P2 · 查询时追加"用途专属池"（不动条目结构）

`affinities[].exclusive_pool` 保持单一引用（打造用），炼金侧额外声明一个池引用，
由调用方在查询后并集。

```jsonc
// 配方或产物侧声明（炼金专属池引用）
{ "id": "rcp_flame_bomb", "affinity_extra_pool": "p_alchemy_fire" }   // 新增包声明字段
```
- **接口改动**：需要 `resolve_available_entries` 支持额外池入参（或调用方自行并集后过滤）。
- 缺点：**并集+过滤逻辑会出现在调用点**，若打造侧也照做，等于两处实现同一语义（不违反红线但接近）。
- 优点：**不改池条目 schema**，纯增量。

#### 方案 P3 · 新增池 `kind`（**不建议**）

给 `POOL_KINDS` 加 `alchemy` 之类，让查询按 kind 并集。
- 现状 `resolve_available_entries` **只并集 `kind==common`**，专属池是经 `exclusive_pool` 单一引用进入的
  （`affinity.py:323-332`）。加 kind 需同时改并集逻辑 + 校验 enum + 编辑器，**改动面最大**，
  且与"专属池经相性引用"的既有模型冲突。**不建议**。

#### 反方案（**红线，禁止**）

在炼金侧自建 `alchemy_affinity` 段或一套"药剂相性池"——违反用户裁定
「**不得在两处各写一套相性（唯一源）**」（`docs/深度打造_决策记录.md:52`）。

### 4.2 可验收小批（2~3 个）

> 建议沿用决策记录批号：**批 46**（`docs/深度打造_决策记录.md:68`，依赖=批 38 + 炼金侧细化）。

#### 批 46-A · 「相性进炼金链路」只读接入（**不改任何产出**）
- **范围**：G1 材料相性进记录/快照 + 调 `accumulate_affinity`/`rank_affinities` + 面板显示主副相性。
- **明确不做**：不改产出数值、不动 `_produce`、不动使用链路。
- **验收**：
  1. 给定材料链（含互动规则）→ 快照内 `affinity_main/sub` 与 `accumulate_affinity`+`rank_affinities`
     独立调用**同值**；
  2. **回归对拍**：不配置 `settings.affinities` 时，`/炼金`+`/投料`+`/确认` 全链路输出与接入前**逐字段一致**
     （对齐批 39 对拍口径，`docs/深度打造_决策记录.md:172`）；
  3. 缺 `affinities` 声明的材料 → 相性位为空、不报错、不影响既有流程。

#### 批 46-B · 强度型（选定口径 A）
- **范围**：相性系数表 → 乘进 `coef` → **落实例**（解 G3）→ 使用链路读取（解 G4）。
- **验收**：同配方、材料等级/品质相同但**相性不同** → 两件成品效果数值不同且比值 = 声明系数；
  `/道具` 实际结算值随实例变化（证明 G4 已通）。
- **依赖**：需先定 §五 Q5（实例承载方式）。

#### 批 46-C · 附加型（口径 B，池共享）
- **范围**：`resolve_available_entries` + `scope`（或 P2）+ 抽取步 → 附加效果。
- **验收**：
  1. 无相性 → `requires_affinity` 词条**抽不出**（对齐原案 `:57`）；
  2. 命中主相性 → 该相性专属池词条**可抽**；副相性词条在主=另一相性时**仍可抽**；
  3. 联动命中 → 专属池被 `override_pool` **覆盖**（用同一套断言覆盖打造与炼金两条调用路径）。

> **可并行的前置小批**：内容包声明第一批相性 + 池 + 互动（纯 JSON + 校验器过门禁），
> 因为 §一 G6 表明**当前无任何内容可测**；不先做这个，46-A 只能靠测试 fixture 验证。

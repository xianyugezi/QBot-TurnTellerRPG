## 四、P0 必改（2 条）

### P0-1｜S1/S5 「高覆盖低 / 强覆盖弱」比较恒真，覆盖规则失效
- 位置：`qbot_rpg/core/effects.py:527`（`power` 定义）与 `:602`（S5）、`:614`（S1）
- 实际内容：
  ```python
  power = self._boost_of(sdef)          # :527 已取"本次新状态"强度
  ...
  if power >= self._boost_of(sdef):      # :602 / :614 与 self._boost_of(sdef) 自身比较 → x>=x 恒 True
  ```
- 应有内容（细化_1b §4.1 S1/S5，P4 合约 C-1/C-5）：「新状态强度 ≥ 既有实例强度」才覆盖；弱/低新状态应走 `covered_low` 不替换（既有实例强度 = `existing["value"]`，即 `first_action_value`）。
- 影响（静态推导）：`covered_low` 分支（:608/:622）永远不可达=死代码；「先强后弱」反向场景下弱新状态无条件重置/覆盖强既有状态（S1 应"高覆盖低，新低不覆盖旧高"、S5 应"强覆盖弱，等强重置"），规则语义破坏。现有 `test_c1` 只测「弱→强」正方向，未覆盖反向 → BUG 未被测试暴露。
- 修复建议：两处比较量改为既有实例强度，如 `power >= float(existing.get("value", 0))`（注意与 `_boost_of` 小人百分比口径的换算，:477-482 处理 `"20%"` 返回 0.2 而 `existing["value"]` 存 20，需统一口径）；并补「先强后弱→covered_low」用例。

### P0-2｜formula_engine 整模块零调用方 + 零测试；L0 公式框恒返回 0
- 位置：`qbot_rpg/core/formula_engine.py`（全文件，grep 全库唯一引用为其自身/`__init__` docstring）；`qbot_rpg/core/effects.py:1355-1361`、`:20-22`
- 实际内容：`evaluate / evaluate_detail / validate_expr` 无任何模块或测试调用（静态推导，grep 证实）；L0 `_resolve_value` 公式框分支：
  ```python
  eval_fn = ctx.variables.get("eval_formula")
  if callable(eval_fn) ... → 求值
  ... 否则 warnings.warn + return 0        # effects.py:1362
  ```
  且全库无任何地方注入 `ctx.variables["eval_formula"]`（grep `eval_formula` 仅 3 处引用，均为 effects 自身）。
- 应有内容（细化_1b §3.1 value 三型含 JS 公式框、§5 F-1~F-5；变量定稿 §1.1）：公式框应经公式引擎求值；F 组 6 条验收（含 F-2 AST 黑名单/超时安全验收）应有测试落地。

## 六、P2 建议（7 条）

1. `crit_roll` 未应用 cap（damage.py:329 计算 P 未 clamp）——与 T10 语义不一致（crit_prob 已 cap）；`crit_roll` 亦忽略参数化 `crit_mult_up`（恒用默认 CritMultUp）。建议统一。
2. `total_damage` 未校验/钳制 rng（damage.py:552）——rng=NaN/±Inf 时 `math.floor` 抛异常（静态推导），违反「clamp 优先」护栏；建议 `rng` clamp 进 `DamageFormulaParams.rng` 闭区间。
3. formula 词法黑名单可被 `\uXXXX` 转义标识符绕过（静态推导）：`_scan_tokens` 对 `\` 走「未识别字符」跳过，`\u0065val(...)` 以 `u0065val` 作普通标识符放行，Node 侧解析为 `eval`。因 vm 沙箱不暴露 process/require/globalThis 等危险全局（`_js_runner.js:73-76` 仅注入 Math/this_battle_round），**不构成 RCE**，但「黑名单不可绕过」的表述不严谨；建议在词法层禁 `\u` 转义标识符或文档注明黑名单为纵深防御、权威边界为 vm。
4. 模板/字面量占位符展开不感知字符串上下文：`_expand_placeholders` 会替换 JS 字符串字面量内的 `[...]`（如 `"[我方攻击]"`→`"5"`，语义漂移），建议仅替换代码位置或文档限制。
5. `DamagePipeline(order=())` 静默禁用全部阶段（effects.py:916-934，空 tuple 为 falsy 跳过 warning、_order=() 不执行 apply_damage）；建议空 order 按默认处理或显式报错。另 `_stage_guts` 副作用键名笔误 `"quard_hp"`（:1196）。
6. `prepare_defense` 内死循环（effects.py:1037-1042，action 遍历体全为 `pass`）；`effects.py` 与 `damage.py` 同名导出 `DamagePipeline`（类 vs 类型别名）易混淆；`_UID_COUNTER`（:269）不随 `from_json` 恢复，恢复后新实例 uid 可能与旧实例撞号（`_remove_status` 以 status_id+uid 匹配会误删，静态推导低概率）。
7. 侧名约定：`battle.resolve_damage` 以任意 `attacker/target` 字符串为快照键，而 `EffectRuntime.ensure_actor`/`DEFAULT_PIPELINE_ORDER` 固定 `BATTLE_SIDES=("player","enemy")`；非标准侧名时五块快照与防御行读取会错位（静态推导）——建议 resolve_damage 校验/归一化侧名。

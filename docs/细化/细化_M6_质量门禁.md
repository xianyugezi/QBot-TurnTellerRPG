## 一、覆盖率实算（COV · 【总纲】ADR-04 / 【批6A】P0-2 / 【批6B】P1-2）

### 1.1 机制说明

M6 把「覆盖率 ≥80%」从「verify_m0 §5 仅打印提示 + 估算口径」落成**真实可执行载体**：coverage 依赖入 requirements.txt（锁版本，规则 8）→ `coverage run --source` 三个目录测量 → 按目录聚合行覆盖百分比 → 任一目录 <80% 即 exit≠0 → 报表归档 docs/verify/。口径 = **各自 ≥80%**（【总纲】ADR-04 定死，拒绝合计稀释——content/ 零代码配置层低覆盖被 core/ 冲平即假绿，【批6B】P1-2）。阈值断言挂 run_all_tests 阶段3（或独立 coverage 段），与 5d §3.2 L140「覆盖率核算 → 输出覆盖率报表」一致。伪托修正（verify_m0/记录.md/run_all_tests 改引真实 D5）见 §六。

### 1.4 边界异常

- **合计稀释拦截**：若实现侧图省事用 `coverage report --fail-under=80` 单一阈值（综合百分比），视为违反 COV-02——综合 80% 可能因 core/ 高覆盖掩盖 content/ 低覆盖（【批6B】P1-2「content/ 零代码配置层，最该守住「只建议不限制」安全承诺」）。断言必须按目录各自判定。
- **coverage 与 pytest-cov 二选一**：本档选 `coverage` 命令行（`coverage run`/`coverage report`），不强制 pytest-cov 插件；若实现批次选 pytest-cov（pytest.ini `--cov`），必须保证同样输出逐目录百分比并满足 COV-04 各自阈值语义。
- **core/worldtime.py 与 engine/worldtime.py 同名并存**：两个文件都存在（core/worldtime.py 为战斗/成长侧、engine/worldtime.py 为时间天气侧），目录映射按各自目录归属，测量时以 `--source` 三目录路径精确覆盖，不合并。
- **message_format/ 子包**：core/message_format/ 为渲染模板子包，属 core/ 覆盖范围（`--source=qbot_rpg/core` 自动含子包）；若其行覆盖拖低 core/ 目录，属于正常统计（不豁免），实现批次应补其测试或登记。
- **measure 不达标但门禁绿的反模式**：run_all_tests 若仅打印百分比而不改退出码，即复现「估算冒充核算」——COV-04 强制 exit 语义，由 TC-COV-04 断言。

### 2.3 边界异常

- **存量基线生成时机**：首次跑 lint 前先按 LNT-05 生成基线清单（记录实际存量），再接入快速门——顺序颠倒会让门禁首跑即红、不可达（防「全仓零问题」不现实）。
- **E501 豁免陷阱**：line-length=100 已放宽到项目风格；若再全局 ignore E501，长行不受控 → 禁过度豁免（LNT-01 明示）。
- **mypy strict 两难**：strict 一次开启 → 数百存量错误塞满基线清单、不可维护 → 本档定档 non-strict 起步 + 新增必拦（LNT-02【细化定型】）；引擎核心新增文件尽量标注（规则 F 项 P1 精神）。
- **快速门与短路原则的张力**：5d L133「不通过直接中止」vs L144「继续执行收集全部失败」——本档取 L144（收集全部失败、退出码非 0），`--skip-lint` 作逃生口（【细化定型】），避免「中途中止掩盖后续失败」。
- **verify_m0~m5 不接 lint**：存量 verify 脚本不逐脚本接 ruff/mypy（避免破坏既有门禁稳定）；lint 收敛在 run_all_tests 阶段0 单点（CI 与本地共用）。

### 4.3 边界异常

- **CI 与本地双口径**：CI 若自造一套阈值（如 workflow 内只跑 pytest 不跑 coverage），会与本地 run_all_tests 结果不一致 → CI-02 强制共用入口（run_all_tests 全量）或逐 step 复刻同一命令序列（二选一）。
- **存量提交豁免**：CI-03/06 只校验新增提交，历史无 scope/BREAKING 的提交不追溯改写（防大规模 git 重写破坏历史；记录.md 已载「7 commit 未 push 待 token」，不在此列）。
- **commit-msg 钩子 vs verify_m6 断言**：二者任选其一（CI-03 二选一）；选钩子则本机强制、CI 不覆盖；选 verify_m6 断言则 CI/本地共用校验点——本档不强制实现形态，由实现批次选一并在 verify_m6 留断言。
- **feat(pack) 空窗**：生产 content/ 目录尚不存在（仅 tests/fixtures/packs 四件套），feat(pack) 分提交校验在 content/ 建立前为空转 → 契约先行（CI-04），校验逻辑就绪后随 content/ 落地生效。
- **CI 依赖网络**：CI 环境需能访问 pip 源安装依赖（依赖安装 step 是首步）；离线/内网环境 CI 可跳过（登记为遗留，本地 run_all_tests 仍为门禁权威）。

- **变更内容**：对照设计文档/细化文档章节说明改了什么（附细化档号 + TC 号）

### 5.4 边界异常

- **dsh 审查 vs PR 评审两套体系衔接**：仓库实际评审 = docs/审查报告/ 的里程碑式设计/实现审查（dsh），与规则 §5 PR 合并门禁是两套（【批6A】P1-2「两套体系，衔接未定义」）。本档定义衔接 = dsh 审查报告结论 → PR 模板勾选映射（dsh P0/P1/P2 对应模板 P0/P1/P2 标级，审查报告归档 docs/审查报告/ 并链接 PR）；小团队直推 main 豁免由 D8 按规则 §3.2 L232「个人/小团队直接 commit 到 develop 可以接受，但 main 必须走 PR」登记。

# 审计③「如无必要，勿增实体」· 重复机制 / 多套实现

> 审计对象：`/root/QBot-TurnTellerRPG`（只读；本文件为唯一写入物）
> 判据（可操作形态）：
> 1. 同一概念只能有一个实现 / 一个源；
> 2. 同一件事有两套并行机制 = 违规（例：两套品质口径、两套冷却、两套池抽取、两套强化）；
> 3. 别名/兼容层必须能说清「为什么存在 + 什么时候能删」；
> 4. 重复的配置段（两个段表达同一件事）= 违规；
> 5. 多绕一层（无收益的中间层/包装）= 违规。
>
> 每条判定分三类：**①真重复** / **②合理分层** / **③有意并存**。
> 证据规则：每条带 `file:line`；未验证处标「存疑」；不写实现代码。

## 3. 真重复清单

### F1 · `forge.json["settings"]` ↔ `settings.json["forge"]`（配置段真重复，且已漂移）· 严重度 高 · 成本 低 · 迁移风险 中

- **两处**：
  - `content/<pack>/forge.json` 顶层 `"settings"` 段（`content/test_demo/forge.json`、`content/veinborn/forge.json` 均有；`content/zz_craft_demo/forge.json` 无）。
  - `content/<pack>/settings.json` 的 `"forge"` 段（`content/test_demo/settings.json:216-224`、`content/veinborn/settings.json`）。
- **为什么算重复**：两段键集与语义完全一致（`forge_fee/synth_ratio_3to1/straight_forge/decompose_rate/exp_per_forge/sets_enabled/augments_enabled`）。
  - `test_demo`：实测两段 **`==` True**（7 键全同）。
  - `veinborn`：实测 **`==` False**——`forge.json.settings` 缺 `carry_sec` / `set_piece_counts`，而 `settings.json.forge` 有。**漂移已经发生**。
- **读取关系**：主源 = `settings.json["forge"]`（`content/forge_settings.py:246,268`；`commands/forge_commands.py:427`）；`forge.json["settings"]` 只在「显式 settings 缺位」时兜底（`core/forge_tree.py:146-158` 第 ③ 步；`core/forge_deadlock.py:394-395`）。
  - **生产路径实测**：`commands/forge_commands.py:410-415 _engine()` 恒把 `settings=_settings_of(ctx)` 传入，`ForgeTreeEngine._resolve_settings` 必在第一个分支（`settings.get("forge")` 命中）返回，**第 ③ 步 `self._forge.get("settings")` 永不触发**；即 `forge.json["settings"]` 在生产中是**死影子副本**，仅离屏「只喂 forge.json」的调用会走到。
- **建议合并方向**：以 `settings.json["forge"]` 为唯一段；`forge.json` 只保留 `trees/sets/augments` 数据；删除 `forge.json["settings"]` 及 `forge_tree._resolve_settings` 第 ③ 步、`forge_deadlock` 的 fallback，并加校验器红拦「forge.json 出现 settings 段」。
- **迁移风险**：低——运行时主源不变，删兜底只影响「只喂 forge.json、不喂 settings.json」的离屏调用（`forge_tree.py:146-158` 明确支持该形态）。需同步改调用点与测试。

### F2 · `forge.decompose_rate` ↔ `alchemy.decompose_rate`（同键两段，forge 侧死键）· 严重度 中 · 成本 低 · 迁移风险 低

- **两处**：
  - 真源：`core/gem_wallet.py:178-200 decompose_rate()` 读 `settings.alchemy.decompose_rate`（包 `content/test_demo/settings.json:107` 完整 6 档）；校验 `content/alchemy_settings.py:306-336`。
  - 影子：`content/forge_settings.py:52-59 DEFAULT_DECOMPOSE_RATE`（同一条 0.4→0.65 曲线）+ `:78` 注入默认 + `:99` 进 `FORGE_SETTINGS_KEYS` + `:151-152` FieldMeta + `:282-288` 合并；包 `content/test_demo/settings.json:220`（只有 `{"正式":0.4}`）。
- **为什么算重复**：同一概念（分解回收率）、同一键名、同一档位键、同一曲线；`forge` 侧无任何生产消费者（全仓 grep 只读到 `forge_settings.py` 自身与 `forge_models.py:496` property）。
- **文档自认**：`docs/深度打造_实现说明.md:1432-1433`「`forge.decompose_rate` 是历史『声明未消费』键，本批不动（D11 待裁决）」；`docs/深度打造_决策记录.md:1323` D11。
- **建议合并方向**：删 `forge.decompose_rate`（默认表 + `FORGE_SETTINGS_KEYS` + FieldMeta + 合并分支 + 包内声明），回收率只留 `settings.alchemy.decompose_rate`；若要保留 forge 段形态，应改为「forge 段显式引用 alchemy 段」而非复制。
- **迁移风险**：低——现网内容对 forge 侧只有 `{"正式":0.4}`，删除后运行时数值由 alchemy 段提供（test_demo 已是完整 6 档），行为不变；需同步改 `tests` 中 TC-20 对 forge 段回收率的断言。

### F3 · 符文阶解析第二实现 `core/upgrade.py::_rune_tier_of` · 严重度 中 · 成本 低 · 迁移风险 低

- **两处**：
  - 唯一源：`data/runes.py:77-87 rune_tier_of`（边界用 `MIN_RUNE_TIER/MAX_RUNE_TIER` `:64-66`）；`core/runes.py:69,79` import 并在 `:339` 使用；`core/jewel.py:75` 亦 import。
  - 第二实现：`core/upgrade.py:883-905 _rune_tier_of`——自写解析，且**硬编码 `1 <= t <= 3`**，另有「产出端配方回退」分支。
- **为什么算重复**：同一概念（符文 `tier ∈ {1,2,3}`）两处解析；唯一源用常量，第二实现用字面量，常量一改就会漂移。自述「档位解析走独立三阶刻度」`core/upgrade.py:771,77`。
- **建议合并方向**：`_rune_tier_of` 改为调用 `data/runes.rune_tier_of`（唯一源），仅保留「产出端 `output.rune_tier` 回退」这一层额外语义（这是它相对唯一源多出的、有理由的部分）。
- **迁移风险**：低——行为等价（当前常量恰为 1/3）；需回归 `tests/unit/test_batch46_runes*` / `test_upgrade*`。

### F4 · 材料回收公式两写：`gem_wallet._recover_materials` ↔ `decompose.material_recovery` · 严重度 低中 · 成本 中 · 迁移风险 中

- **两处**：
  - `core/gem_wallet.py:309 _recover_materials`（旧 `/分解` 主路径）。
  - `core/decompose.py:100-124 material_recovery`（新实例级分解）。
- **为什么算重复**：同一公式「逐材料 `floor(count × rate)`」两处实现；`decompose.py` 自述「口径**对齐**既有 `gem_wallet._recover_materials`」——即有意镜像，但两份代码一旦一处改口径就会分叉，而分解是新旧两条路径并存（§2 #13）。
- **建议合并方向**：把 floor 公式下沉为 `data/` 或 `core/` 单一纯函数，`_recover_materials` 与 `material_recovery` 都调用它；输入归一（`ctx` hooks vs 纯 list）留在各自适配层。
- **迁移风险**：中——`_recover_materials` 依赖 ctx 与物品定义形态，抽出共同核需要先行覆盖测试；建议仅在两者都在改时顺手收敛，不要为清理单独重构。

### F5 · 珠档位解析第二实现 `core/upgrade.py::_jewel_tier_of` · 严重度 低 · 成本 低 · 迁移风险 低

- **两处**：`core/jewel.py:295-331 jewel_tier_of`（支持 str/int/Mapping/tier，回退 `common`）vs `core/upgrade.py:742-759 _jewel_tier_of`（只认合法档位键 + `tier` 序号 + 配方 `jewel_tier`，回退 `None`）。
- **为什么算重复**：同一概念（珠品质档读取）两个解析器；返回兜底不同（`common` vs `None`）是**语义差异**，说明二者不是简单复用而可能给同一输入不同答案。
- **建议合并方向**：把 `jewel_tier_of` 提为唯一解析（含「无法解析→None」的严格模式参数），`upgrade` 调它并自行把 `None` 映射为「数据直通」。
- **迁移风险**：低——两处都经 `QualitySystem.index_to_tier`，回归 `test_batch2*` 即可。

# 审计①：「万物皆插件」· 核心引擎层

> 范围（只读）：`qbot_rpg/core/`、`qbot_rpg/assembly/`、`qbot_rpg/data/`、`qbot_rpg/logic/`
> —— **注：`qbot_rpg/logic/` 目录不存在**（全仓 `find` 无该目录），本路实际审了 `core/ + assembly/ + data/`，`qbot_rpg/content/`（框架侧模型/校验器）作为邻接层在证据出现处附带登记。
> 对照：`content/` 各包实际声明（`veinborn`、`zz_craft_demo`、`demo_*`、`zz_probe_ext`、`zz_probe_packmeta`）
> 方法：全文 grep + 逐条反例检查（换包是否也走这条路）+ 扩展点缺口构造；每条带 `file:line`。

## 0. 判据（先把原则讲清）

**「万物皆插件」** = 框架只提供**机制**与**扩展点**；**内容与业务**一律走**内容包声明**。

可操作判据：

1. **新增一个内容包，是否需要改框架代码？** （需要 = 违规）
2. **框架代码里是否出现"某个内容包特有的东西"？**（包名 / 包内业务 id / 某包专属字段名 / 某包专属流程分支 = 违规；我们的红线叫「**框架零包名**」）
3. **某玩法能否只靠包声明做出来？** 若某机制只能由框架硬编码提供、包无法声明（也无扩展点）= 缺扩展点（违规）
4. **是否有"专为某个包写的 if 分支 / 特例"？**（哪怕没写包名，但只有那个包会走到 = 违规）
5. **扩展点是否完备**：E1（指令）/ E2（渲染）/ E3（测试脚本）之外，是否还有"包想扩展但没法扩展"的地方？

一个重要的判读口径（本审计用）：**注释/文档里出现包名不算功能性违规**，但它不能掩盖同文件里真正硬编码的东西；本报告只把**会被代码执行到、会改变行为**的硬编码计入违规清单，注释里的包名单独在 §5 登记。

### V1 ·【必须修】`_AIR_STATUS_IDS` 写死 veinborn 跃空状态 id

**位置（file:line）与代码摘录**

`qbot_rpg/core/battle.py:333-339`：

```python

_AIR_STATUS_IDS: Tuple[str, ...] = (

```

使用点：`qbot_rpg/core/battle.py:3682`（`_air_stance_instances` 过滤）、`:3700`（`_clear_air_stances` 落地清理）。

**为什么违反判据**

- 判据 **2**：`sw_vault_air` / `vs_air_window` / `va_air_window` / `rb_vault_air` / `vc_vault_air` / `po_vault_air` 是**包内业务 id**（技能/状态 id），出现在框架代码里。
- 判据 **1**：新增一个带"空中姿态"玩法的内容包，**必须改 `battle.py` 这张表**，否则跃空窗口初始化/落地清理都不认它的状态 —— 注释自己承认了这一点。
- 判据 **4**：这是一个"只有约定 id 的包才会走到"的特例表。

**反例检查（是否真的只服务某包）**

已核对：6 个 id 全部只出现在 `content/veinborn/`（`skills.json` / `statuses.json` / `skill_chains.json`），其它包（`test_demo`、`demo_full`、`demo_lv15/30/45`、`zz_craft_demo`）**一个都没有**。→ **确认只服务 veinborn，不是通用机制恰好被用**。这是真违规。

反方向也要说清：`_air_stance_instances` / `_clear_air_stances` 的**算法本身是通用的**（"扫某个 side 的状态实例、按 id 命中清理"），坏的只是"命中集合"写死了。所以修复面很小。

**建议的扩展点形状**

- 首选：让状态**在包内自我声明**。在 `statuses.json` 条目上加一个框架字段，例如 `"stance": "air"`（或 `"air_stance": true`、`"tags": ["air_stance"]`），装配时扫描 registry 里所有 status 定义，构建该集合；框架只认**声明的语义值**，不认具体 id。
- 次选（过渡最省事）：`settings.battle.air_status_ids`（数组，包声明），框架读配置；缺省空 = 无空中姿态。缺点仍是"包要列 id"，但至少不用改框架。
- 判据 5 角度：现有 E1/E2/E3 都不覆盖"给状态打玩法标签"，这属于**缺第 4 类扩展点**（见 §3-G1）。

**严重度 / 修复成本**

必须修。成本 **中**：需要装配层（`assembly/context.py` 已在建 registry）暴露"扫描 status 声明"，再改 `_AIR_STATUS_IDS` 的两处使用 + 补测试。

### V6 ·【建议修 / 待裁决】pvp 防御与速度键 `dfn/con`、`agi/spd` 兼容链写死

**为什么违反判据**

**反例检查**

- 反方向：同一函数 `pvp.py:181-192` 有"**全量透传**"——把包属性表里的**所有** base 键追加进 combatant。所以一个用全新防御键（比如 `tough`）的包，它的 `tough` **能**进战斗快照；但引擎语义键 `dfn`/`con` 仍只会读取写死的那几个名字，新键不会自动成为"防御"。

**建议的扩展点形状**

## 3. 扩展点缺口清单（包想做但做不到）

> 每条都尽量给出"具体例子 + 证据 file:line"，能构造的构造，构造不了的指出机制点。

### G1 · 包无法声明一个新的「跃空/空中姿态」状态

- **包想做的事**：新包写一个"御空"玩法，声明一个状态 `my_air_stance`，希望框架把它当空中姿态（窗口初始化、到期落地、落地清理）。
- **为什么做不到**：框架只认 `battle._AIR_STATUS_IDS` 里 6 个写死的 id（`battle.py:333-339`），另见 V1。
- **证据**：`battle.py:3682`、`:3700`；类型 `statuses.json` 目前**没有**任何"姿态标签"字段可声明（`core/event_dispatcher.py:71-75` 只认 `on_gain/on_lose/on_expire`）。
- **缺的扩展点形状**：状态声明加"玩法标签/角色"字段（`stance: air`），框架按声明集合工作。

### G2 · 包无法在 SP 面板新增/自定义解锁项

- **包想做的事**：新包加一个"采集精通"SP 项，或给自己的锻造面板加第 6 项。
- **为什么做不到**：`_PANEL_IDS` 闭集强判未知项为"锁定"（`forge_sp.py:211-213`）；`sp_panel_view` 只遍历静态 `FORGE_SP_PANEL`（`:230`）；见 V2。
- **证据**：`forge_sp.py:81-115`、`:209-213`、`:219-238`。
- **缺的扩展点形状**：面板目录以 `proficiency.json.sp_panel` 为唯一源，框架成员判定/渲染都走引擎注入的数据。

### G3 · 包无法更换内置系统的「职业 id」

- **包想做的事**：一个包想把炼金职业 id 从 `alchemy` 改成 `炼金`（或 `alchemy2`），或复用锻造引擎但用自己的职业 id。
- **为什么做不到**：框架把职业 id 写死为常量：`core/alchemy_core.py:99` `ALCHEMY_JOB_ID="alchemy"`、`core/forge_tree.py:74` `FORGE_JOB_ID="forge"`、`core/fishing_job.py:58` `FISHING_JOB_ID="fishing"`。引擎按这些 id 去 `proficiency`/`jobs.json` 查节点，包必须用同名 id 才能对上。
- **证据**：上述三处 + `core/alchemy_settle.py:217`、`core/forge_material.py:209`、`core/fishing_settle.py:114`（`_PROF_JOB_ID="fishing"`）。
- **缺的扩展点形状**：系统与"包内职业 id"解耦，例如 `settings.alchemy.job_id` / `settings.forge.job_id`，或系统按 `profession role`（`role: alchemy`）绑定包内任意 job id。
- **附**：`fishing` 的 job id 还在两个文件各定义一次（`fishing_job.py:58` 与 `fishing_settle.py:114`），属唯一源问题（§3-D2）。

### G4 · 包无法新增一个装备数值键（词条键闭集）

- **包想做的事**：新包要一个全新词条轴 `frost_dmg_pct`。
- **为什么做不到 / 半做不到**：`data/gear_stats.py` 自称唯一源，`GEAR_NUMERIC_KEYS = GEAR_FLAT_KEYS + GEAR_PCT_KEYS + GEAR_COMBAT_KEYS + GEAR_EFFECT_KEYS`（`gear_stats.py:489`）是**闭集**；校验器按它红拦：`content/rune_models.py:135`、`content/enhance_models.py:473`、`core/temper.py:185-190`。文档明写"新增词条 = 本文件加一行"（`gear_stats.py` 模块 docstring）。
- **反例检查**：`settings.effect_axes` 段允许内容包覆盖**范围/默认值**（`gear_stats.py:217-218`），但**不改键集**；`pvp.py:185-192` 的"全量透传"能让 base 里的新键进 combatant，但装备词条（flat/pct）的新键会被聚合端/校验端丢弃。
- **判定**：这是"框架定义数值命名空间"的有意设计，不一定是 bug；但按判据 3，**包新增一个新数值轴需要改框架** —— 登记为**缺口候选**，严重度见 §5 待裁决。
- **缺的扩展点形状**：包声明自定义词条轴（含聚合方式、默认、消费点），框架按声明做通用路由（现有 `route_bonus_into` 已具备"按后缀拆 flat/pct"的通用能力，差的是"允许包注册新键"）。

### G5 · E2 渲染钩子只有 2 个事件，包无法挂钩其它渲染点

- **包想做的事**：包想改战斗开始/面板/某个具体指令的渲染。
- **现状**：`assembly/pack_render.py:85` `KNOWN_EVENTS = ("command.reply", "battle.round")`；声明未知事件只警告+忽略（`:307-311`）。
- **判定**：`command.reply` 覆盖"一切经 runner sender 闭包发出的指令回复"，覆盖面已较广；`battle.round` 覆盖战斗正文。**暂列缺口候选（低优先）**：如果包需要"战斗开始""升级提示"等独立时点，目前没有。
- **证据**：`pack_render.py:83-85`、`:289-313`。
- **缺的扩展点形状**：事件枚举下沉到 data 层（学 `data/event_points.py` 的做法），包按声明的时点挂钩。

### G6 · 包声明的自定义敌人属性在"难度模板补全"中被丢弃（待运行时确认）

- **机制点**：`qbot_rpg/content/validator.py:241-243` `_ENEMY_STAT_KEYS_DEFAULT` 是固定 9 键；`apply_enemy_difficulty_template`（`:324-353`）**只遍历这 9 键**构造 `completed`，包声明的其它属性键不会进入补全结果。调用点 `validator.py:1018`。
- **为什么是缺口**：包若给敌人加自定义属性（如 veinborn 的白值键），模板补全后可能丢失自定义键。
- **证据**：`validator.py:241-243`、`:324-353`、`:1018`。
- **状态**：**待裁决**——需要跑一次装配确认自定义键是否真的丢（本审计只读代码，未运行引擎）。见 §5。

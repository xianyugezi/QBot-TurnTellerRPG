# 框架级扩展设计：战斗状态条件化（Enemy 印记触发 + 技能效果条件）

> 性质：QBot-TurnTellerRPG 框架级通用能力（非 veinborn 专用补丁）——后续所有内容包（veinborn/云海/自研）可复用。
> 需求来源（用户 2026-09-02）：
>   ① enemy AI 条件行动需能读 battle 内印记（"部位技在无破坏印记时才可用""困斗满才放宣泄"）——纯配置表达"怪物响应玩家施加的状态"
>   ② 技能效果需能读我方/对方属性、Buff、印记、Debuff 等改变效果（"对方有破绽印记→这刀×1.5""自己血<30%→治疗+50%"）——纯配置表达"技能响应战斗状态"
> 硬约束：纯配置可用（内容包 JSON 直接写），框架代码只加"求值原语"，不改既有行为（新增=可选，缺省=原行为）。
> 遵循：规则 24 全流程（需求→设计→实现→测试→审查→文档同步→提交）、最小单元提交。

## 二、功能一：enemy AI 印记触发（monster_conditions 扩展）

### 2.1 新增 2 个触发类型（内建，进 TRIGGER_TYPES）

```
"enemy_mark"   — 敌方身上印记（读 battle_state["marks_state"]["enemy"]）
"player_mark"  — 玩家身上印记（读 battle_state["marks_state"]["player"]）
```

### 2.2 trigger schema（对齐既有 trigger 形态，纯配置）

```jsonc
// 存在判定（缺省 = 层数≥1）
{"type":"enemy_mark", "mark":"vein_core_broken"}
// 不存在（部位技"无破坏印记才可用"→ 用 absent）
{"type":"enemy_mark", "mark":"vein_core_broken", "absent":true}
// 层数阈值
{"type":"enemy_mark", "mark":"surge", "min":6}
{"type":"player_mark", "mark":"threatened", "max":0}
```

字段：
- `mark`（必填）：印记 id（mark_id）或冗余 name（对齐 count_by_name 匹配）
- `absent`（可选 bool）：true = 要求不存在（count==0）；缺省 false = 存在
- `min` / `max`（可选 int）：层数阈值（与 absent 互斥？→ 设计定：absent=true 时忽略 min/max；min/max 并存 = 区间）
- 求值 = MarksManager 语义（count_by_name 按 side 查层数，同 (side,mark) 单实例聚合）

### 2.3 求值器实现

```python
def _eval_enemy_mark(trig, bs, ai, rng):  # _eval_player_mark 同构
    """印记触发：读 marks_state[side]，按 mark/min/max/absent 判定。"""
    side = "enemy" if trig.get("type")=="enemy_mark" else "player"
    ms = (bs.get("marks_state") or {}).get(side) or []
    count = 0
    want = trig.get("mark")
    if want:
        for inst in ms:
            if inst.get("mark_id")==want or inst.get("name")==want:
                count = int(inst.get("count",0)); break
    if trig.get("absent"): return count == 0
    lo = trig.get("min"); hi = trig.get("max")
    if lo is not None and count < int(lo): return False
    if hi is not None and count > int(hi): return False
    return True
```

（实现时不动既有 13 类；纯新增 2 个 handler + TRIGGER_TYPES 追加 → 注册表/BUILTIN_HANDLERS 各加一行）

TRIGGER_TYPES 从 13 → 15：

## 三、功能二：技能效果条件化（effects 条件求值 + 数值改写）

### 3.1 目标形态（纯配置，效果条目级）

```jsonc
// 方式 A：效果条目内嵌条件（推荐，最小侵入）
{"id":"smite", "name":"制裁", "type":"damage", "power":120,
 "effects":[
    {"effect":"smite_bonus"},   // 无条件基线
 ]}
// 效果 id 指向 effects.json 条目，条目可带 condition
{"id":"smite_bonus", "type":"damage", "power":180,
 "condition": {"target_marks":{"vulnerable":{"min":1}}}}   // 对方有破绽→改用 180

// 方式 B：skill 级条件分支（若需要更复杂）
// （本设计先做 A，B 视需要二期）
```

### 3.2 condition schema（对齐 combo evaluate_condition 的既有子句，纯配置）

复用 combo.py evaluate_condition 已支持的子句（它读 battle_state + marks_lookup，battle 已接线）：
```
self_marks   {mark_id: {min/max}}   我方印记层数
target_marks {mark_id: {min/max}}   对方印记层数
marks_total / marks_set / marks_any
player_status / player_hp_below     我方状态/血量
（追加需要时）：
self_status  {status_id: ...}       我方 Buff/Debuff
target_status {status_id: ...}      对方 Buff/Debuff
self_stat    {atk: {min:100}}       我方属性阈值
target_stat  {hp_ratio: {max:30}}   对方属性/血量比
```

### 3.3 求值挂载点（effects 执行链）

- effects execute_action 入口（L1392）解析 effect id → 查 effects.json 条目 → **执行前先 evaluate condition**（用既有 evaluate_condition + 注入 marks_lookup/status/stat 读取器）→ 条件不满足 → 跳过该 effect（缺省无条件 = 恒执行，零行为变化）
- 需要 EffectRuntime 暴露：status_instances / combatant stats 读取（已有 status_instances；stats 需注入 combatant 快照或经 ctx）

### 3.4 复用 vs 新增

- 复用 combo.evaluate_condition 的条件语法（同一方言，内容包作者只学一套）
- 新增：effects 条目级 condition 求值入口 + self/target status/stat 子句（combo 侧已有 self_marks/target_marks 等——若 combo.evaluate_condition 已全支持则纯接；缺 status/stat 子句则补）

## 四、两者关系与统一抽象

两个功能本质同一：**"读 battle 状态（印记/状态/属性）→ 决定行为"**。
- 功能一：状态 → enemy 是否放某行动
- 功能二：状态 → 玩家技能效果是否生效/改数值

统一设计语言（内容包作者视角）：
- 印记：`enemy_mark` / `player_mark`（AI 触发）+ `self_marks` / `target_marks`（效果条件）——语义一致
- 状态/属性：功能二新增 self/target status/stat 子句（功能一 player_status 已有，是玩家状态非印记——两者并存）

**建议先做功能一（小、独立、veinborn 部位技直接卡），功能二（大、跨 effects）作为第二期**——或按用户节奏并行。功能一改动面：monster_conditions + 契约 + 测试 ≈ 150 行。功能二改动面：effects 执行链 + condition schema + 校验 + 契约 + 测试 ≈ 300+ 行。

## 六、风险与待拍板

| 项 | 说明 |
|---|---|
| 功能一先做还是并行 | 功能一独立可先落地；功能二改动 effects 执行链，风险略高，建议功能一验证后再上（或并行分路） |
| 效果条件 = 效果条目级 vs 技能级 | 条目级最小侵入（推荐）；技能级可表达"整技替换"但改动大 |
| self/target status/stat 子句 | 若 combo.evaluate_condition 已支持则纯接；缺则补（量小） |
| 印记 absent 语义 | 与既有"印记存在=层数≥1"对齐，absent=true 反向 |
| 与既有 player_status 区分 | player_status = 玩家身上状态(status)，player_mark = 玩家身上印记(mark)——两套并存不混 |

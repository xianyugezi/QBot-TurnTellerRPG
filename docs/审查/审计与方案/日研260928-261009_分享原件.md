## 3. 项目分析

## 3.1 主题一：事件定义不能等于事件派发

### FACT

批84建立了一个明确的事件点元数据结构：

```text
EventPoint(name, dispatched, note)
```

并把原先的 `EVENT_POINTS` 改为从更完整的事件表派生，而不是让事件名列表单独存在。这样可以区分：

- 事件是否被定义
- 事件是否已经接入运行时
- 事件是否属于二期未接入范围
- 事件为什么当前没有派发点

项目还对 `status_lose` 的过期路径进行了补派发，并使用修复前后对拍验证“无声明效果时行为不变，有声明效果时才产生预期变化”。

### OBSERVATION

这里实际上形成了一个比普通“事件枚举”更强的三段式模型：

```text
事件语义定义
    ↓
事件派发能力声明
    ↓
事件实际运行时入口
```

如果只有第一层，数据驱动系统很容易出现“伪支持”：

- 配置文件允许填入某个事件名；
- 编辑器能显示该字段；
- 校验器只检查事件名是否属于枚举；
- 但运行时没有任何组件发出该事件。

批84的 `dispatched=False` 相当于把“语义上存在、运行时尚未接入”显式化，避免把“未完成能力”伪装成“已支持能力”。

### HYPOTHESIS H-20260928-01

> 对于数据驱动游戏框架，事件系统至少需要同时记录“定义状态”和“可达状态”；仅维护一个事件枚举集合，长期一定会产生静默死配置。

当前证据：**SUPPORTED**  
理由：批84已经通过实际缺陷修复验证该问题存在，并通过 `trigger_event_no_dispatch` 将其暴露给内容作者。

### 对项目的启发

建议把事件目录进一步标准化为以下最小字段：

```text
event_id
display_name
domain
dispatched
dispatch_sources
payload_schema
phase
stability
introduced_in
```

其中最关键的是：

- `dispatch_sources`：这个事件由哪些系统、哪些生命周期节点发出
- `payload_schema`：事件附带哪些上下文
- `phase`：初始化、回合、行动后、状态结算、战斗结束等
- `stability`：稳定、实验性、二期未接、废弃

这样做的价值是，内容设计者看到的就不再只是“事件名”，而是一个可判断的“事件契约”。

## 3.2 主题二：配置验证应覆盖“可运行性”

### FACT

批84对无派发事件采用的是“黄提示、不红拦、零行为变化”的策略，而不是直接禁止保存配置。

这说明项目已经在区分两类问题：

- **配置非法**：字段类型、枚举值、引用等错误，应阻止或明确报错
- **配置当前不可运行**：语义合法，但所依赖的运行时入口还未接入，应提示但允许保留

Pydantic 官方文档将验证分为字段级验证与模型级验证，并支持对字段之间的关系进行检查。模型级验证适合处理“多个字段组合后是否合法”的约束，而不仅是单个字段的类型检查。citeturn155462search0turn155462search6

### OBSERVATION

项目现阶段已经从“字段是否合法”走向“配置是否能产生预期行为”，这是一个重要升级。

可以把配置校验分成四层：

| 层级 | 检查内容 | 例子 |
|---|---|---|
| L1 | 语法与类型 | 字符串、整数、布尔值 |
| L2 | 枚举与引用 | 事件名、技能 ID、目标类型 |
| L3 | 业务规则 | 数值范围、互斥字段、前置条件 |
| L4 | 运行时可达性 | 是否存在派发点、执行器、消费者、资源 |

批84至少已经覆盖了 L4 的一个关键子类：**事件值存在，但没有派发入口**。

### HYPOTHESIS H-20260928-02

> “配置合法性”不应只返回 pass/fail，而应返回“可执行性等级”，例如 READY、WARNING、BLOCKED、DEPRECATED。

当前证据：**SUPPORTED**  
理由：批84已经采用“只提示、不红拦”的处理方式，说明项目实际上已经需要分级结果，而不是单一布尔值。

### 推荐的校验结果模型

```text
ValidationIssue
- code
- severity
- path
- message
- reason
- runtime_impact
- suggested_fix
- introduced_by
```

其中 `severity` 可以定义为：

```text
INFO
WARNING
ERROR
BLOCKED
DEPRECATED
```

而 `runtime_impact` 可以进一步说明：

```text
NO_EFFECT
PARTIAL_EFFECT
MAY_FAIL_AT_RUNTIME
WILL_NOT_TRIGGER
BREAKS_LOAD
```

这比单纯给出“字段错误”更适合长期维护内容包与游戏规则。

## 4. 外部参考资料

## 4.1 OpenTelemetry：事件必须是有明确语义的结构化事件

OpenTelemetry 的事件语义约定指出，事件应表达一个有意义的发生时点，例如状态变化、生命周期节点、配置重载、异常或某个明确结果；事件名应稳定、唯一，并且事件属性应被文档化。citeturn155462search1

### 对项目可借鉴之处

适合借鉴以下思想：

- 每个事件必须有稳定的事件名
- 事件必须说明“何时发生”
- 事件应有结构化属性，而不是只传一段自由文本
- 事件定义应有文档和版本边界
- 事件名不应混入动态值，动态信息放到 payload 中

### 不宜照搬之处

OpenTelemetry 面向的是可观测性和跨系统追踪，不等于游戏业务事件总线。项目不需要为了“像标准”而引入复杂的 telemetry 层。

更适合的做法是只借用其**事件契约和命名规范**，不直接复制整套追踪模型。

---

## 4.2 Pydantic：字段验证与模型级业务验证分离

Pydantic 官方文档强调：

- 字段验证适合做单字段约束
- 模型验证适合做跨字段关系与业务一致性
- `before`、`after`、`wrap` 等不同阶段适合不同的数据验证时机。citeturn155462search0turn155462search6

### 对项目可借鉴之处

对于项目的内容包、技能、效果、事件、状态配置，可以采用：

```text
字段级验证
    ↓
对象级验证
    ↓
引用图验证
    ↓
运行时能力验证
```

例如：

- 字段级：`trigger` 必须是字符串
- 对象级：`on_lose` 与 `on_expire` 不得违反对象规则
- 引用图：引用的技能、状态、资源必须存在
- 运行时能力：绑定的事件必须有派发来源或被明确标记为二期

### 不宜照搬之处

不要把所有业务规则都堆进一个巨大的模型验证器。否则会形成新的“验证上帝模块”，导致：

- 错误难以定位
- 修改一个规则影响多个内容包
- 运行时规则和编辑器规则耦合
- 不同生命周期阶段无法独立测试

建议保持多个小型验证器，并统一输出同一种 `ValidationIssue`。

## 5. 最重要启发

### 今日核心结论

**对数据驱动 RPG 框架而言，最危险的不是“配置写错”，而是“配置写对了但永远不会发生”。**

批84的价值不只是修复 `status_lose`，更重要的是建立了一个可以继续扩展的判断框架：

```text
定义存在 ≠ 派发存在 ≠ 运行时可达 ≠ 内容效果生效
```

未来可以把这条链统一为：

```text
Config
  → Reference
  → Capability
  → Dispatch
  → Consumer
  → Observable Effect
```

其中任意一层断开，都应能被索引、验证或提示。

## 8. 反例与风险

### 反例一：把 `dispatched=True` 当作“功能一定正确”

事件已接入并不代表：

- payload 完整
- 派发时机正确
- 派发次数正确
- 订阅者一定存在
- 订阅者执行顺序正确

因此“有派发点”只能证明可达性，不能证明语义正确性。

### 反例二：所有未接入事件都直接红色阻止

这会压缩设计空间，尤其在项目存在“设计先行、实现分批接入”的情况下。批84采用黄色提示是更合理的兼容方式，但需要进一步区分：

- “允许保存、当前无效果”
- “允许保存、运行时可能产生部分效果”
- “禁止保存、会破坏加载”
- “已废弃、应迁移”

### 风险

1. `EVENT_POINT_TABLE` 可能继续膨胀，最后变成一个新的集中式大表。
2. 事件来源如果只写成文本，而不是可反查的代码引用，未来仍可能出现文档与实现漂移。
3. 只验证“有没有派发”，还不能发现重复派发、漏派发、错误阶段派发。
4. 事件提示如果只存在于编辑器，而缺少 CLI / CI 校验，批量内容包仍可能把问题带到运行时。

## 9. 未来实验

### 实验 1：事件派发来源自动索引

目标：为每个事件生成：

```text
event_id
dispatch_source
dispatch_phase
payload_keys
test_reference
```

验证方式：

- 静态扫描派发函数
- 与 `EVENT_POINT_TABLE` 对照
- 对没有来源的事件输出 warning
- 对表中声明有来源但代码找不到的事件输出 error

### 实验 2：事件“零消费者”检测

当前项目已经开始检查“事件有没有被派发”，下一步可检查：

```text
事件已派发
但没有任何订阅者/处理器
```

这类事件同样可能形成“静默死效果”。

### 实验 3：把配置校验结果统一为 ValidationIssue

将字段、引用、业务规则、运行时能力检查统一成同一输出结构，并让：

- 编辑器使用它
- CLI 使用它
- 测试使用它
- CI 使用它

以避免不同入口给出不一致的错误语义。

## 3. 项目分析

## 3.1 主题一：权限拒绝不是“没有输出”这么简单

### FACT

批84·C2 明确区分了两类行为：

- GM 指令对无权限者：**静默**
  - 不执行
  - 不报错
  - 不提示
  - 不写审计
- 被封玩家发送游玩指令：**人话提示**
  - 说明当前受限状态
  - 与 GM 指令的静默处理不同

同时，GM 指令被划分为不同权限档：

- 机主可下授
- GM 默认权限集
- 特定运维功能
- 只读测试与进程内调试

### OBSERVATION

这里实际上已经形成了一个“请求处理四元组”：

```text
请求者身份
+ 请求动作
+ 当前上下文
+ 失败可见性策略
```

很多系统只关注：

```text
allow / deny
```

但机器人游戏框架还必须决定：

```text
deny 后是否回复？
deny 后是否记录？
deny 后是否触发事件？
deny 后是否改变玩家状态？
```

这意味着“权限检查”本身已经不只是一个布尔函数，而是一个**带副作用策略的决策层**。

### HYPOTHESIS H-20260929-01

> 权限结果不应只返回 `True/False`，而应返回“授权结果 + 失败处理策略 + 审计策略 + 业务事件策略”。

当前状态：**SUPPORTED**

建议的最小结果模型：

```text
AuthorizationDecision
- allowed
- reason_code
- response_policy
- audit_policy
- event_policy
- effective_role
- matched_rule
```

例如：

```text
allowed = false
reason_code = "GM_PERMISSION_MISSING"
response_policy = "SILENT"
audit_policy = "NONE"
event_policy = "NONE"
```

或者：

```text
allowed = false
reason_code = "PLAYER_BANNED"
response_policy = "USER_MESSAGE"
audit_policy = "SECURITY_EVENT"
event_policy = "player_command_rejected"
```

### 对项目的价值

这能避免把以下逻辑散落在各个命令函数里：

```python
if not is_gm(user):
    return
```

更可维护的方式是：

```text
Command Request
    ↓
Authorization Policy
    ↓
AuthorizationDecision
    ↓
Response / Audit / Domain Event
```

这样在未来拆除 GM 模块时，核心命令处理器不需要知道所有角色、权限和提示细节。

---

## 3.2 主题二：静默拒绝是否应该完全不留痕

### FACT

批84·C2 的口径是：对无权限者调用 GM 指令，静默且不写审计。

这是一个明确的业务选择，而不是技术必然结果。

### EXTERNAL OPINION

OWASP 建议：

- 默认拒绝
- 最小权限
- 每次请求都执行访问控制
- 对授权事件建立测试
- 记录授权相关事件，便于事后分析。citeturn851942search0turn851942search6

### OBSERVATION

“对用户静默”与“系统内部完全不记录”其实可以分开：

```text
用户可见性 ≠ 系统可观测性
```

如果完全不记录，会产生以下盲区：

- 权限配置错误无法回溯
- 某个命令被误判为静默的原因难以定位
- 恶意或异常频繁尝试无法统计
- GM 权限变更后无法解释行为差异

但如果所有拒绝都写入公开日志，也可能：

- 泄漏管理员命令名称
- 暴露权限结构
- 让普通玩家通过反馈枚举系统权限
- 使日志被无意义的高频请求刷满

### HYPOTHESIS H-20260929-02

> “静默拒绝”最合理的实现不是“完全无记录”，而是将响应可见性与内部审计可见性分层。

当前状态：**UNCERTAIN**

需要区分至少三种层级：

| 层级 | 用户响应 | 内部记录 | 适用场景 |
|---|---|---|---|
| S0 | 静默 | 不记录 | 低风险、预期误触 |
| S1 | 静默 | 计数/采样 | 高频命令、抗刷 |
| S2 | 静默 | 完整审计 | 敏感命令、异常行为 |

这不意味着必须立刻改变当前口径。当前批84 的“不写审计”可以保留为业务默认，但框架层应允许将来针对不同命令配置不同级别。

## 3.3 主题三：权限检查本身也是状态机边界

### FACT

批84 文档区分了：

- 机主
- GM
- 普通玩家
- 被封玩家
- 无权限调用者
- 只读测试调用者
- 进程内调试调用者

### OBSERVATION

这些并不只是静态角色，更像是多个状态维度叠加：

```text
身份状态：OWNER / GM / PLAYER
账号状态：ACTIVE / BANNED
命令上下文：GAMEPLAY / OPS / DEBUG / READONLY
```

如果把它们揉成一个单一 `role`，后面会出现大量不自然的角色组合：

```text
BANNED_GM
READONLY_OWNER
DEBUG_PLAYER
```

更适合采用“状态维度分离”：

```text
Principal
- identity_role
- account_status
- command_context
- grant_source
```

然后用策略判断：

```text
can_execute(principal, command, context)
```

这和分层状态机目标一致：  
**将状态分类与行为许可分离，避免状态枚举爆炸。**

### SUGGESTION

建议把权限与业务状态分成两条线：

```text
身份/授权线：
Owner → GM → Player

业务状态线：
Active → Banned → Suspended → Deleted
```

最后由策略层组合决定：

```text
EffectivePermission =
    RolePolicy(identity_role)
    ∩ AccountPolicy(account_status)
    ∩ CommandPolicy(command_context)
```

这样：

- 封禁不是一个新的角色
- 只读调试不是一个新的角色
- 临时授权不需要添加新枚举
- 模块删除时，不会牵连整个玩家状态模型

## 5. 最重要启发

今天最值得纳入长期设计的一句话是：

> **权限系统不应只决定“能不能做”，还应决定“失败后谁能看到、系统是否记住、是否触发业务事件”。**

这与项目之前研究的“事件定义—派发—可达”形成了新的连接：

```text
命令请求
  → 授权决策
  → 业务执行
  → 用户响应
  → 审计事件
```

其中授权失败也可能是一种有意义的系统事件，但是否派发、是否记录、是否对用户可见，必须由策略决定，不能靠各个命令函数自行发挥。

## 8. 反例与风险

### 反例一：所有拒绝都写审计

可能导致：

- 高频垃圾请求污染日志
- 暴露权限模型
- 增加存储与查询成本
- 普通误触被误判为攻击

### 反例二：所有拒绝都完全不记录

可能导致：

- 权限配置错误无法排查
- 无法发现命令被错误屏蔽
- 无法分析异常请求模式
- 后续很难建立可观测性

### 反例三：把封禁直接实现成“没有任何权限”

这会混淆：

- 账号状态
- 身份角色
- 命令类型
- 回复策略

封禁玩家发送普通游玩指令需要人话提示，而 GM 命令可能要求静默，说明两者不能共用一个简单的 `if banned: return`。

### 风险

1. GM 权限规则若分散在命令实现中，会形成新的硬编码区域。
2. “静默”语义如果没有统一枚举，未来会出现不同模块各自解释。
3. 如果授权失败不进入任何统一事件或统计接口，诊断能力会越来越弱。
4. 如果把权限系统过度泛化为复杂策略引擎，可能违背“最小核心”。

> **当前游戏启用了什么。**

```text
enabled_modules:
  - battle
  - status
  - quest
  - craft
```

Registry 负责：

- 注册模块
- 检查 ID 冲突
- 检查依赖
- 检查 API 版本
- 检查能力冲突
- 建立启动顺序
- 暴露能力查询

而不是直接执行游戏逻辑。

---

## 第三层：Module Runtime

模块真正获得：

```text
ExtContext
Event Bus
Config
State
Storage
```

然后挂接：

```text
hooks
subscribers
commands
validators
serializers
```

这样就可以实现你一直要求的：

```text
新增模块
=
注册表加一项
+
挂若干 hook
```

而不是：

```text
新增模块
=
修改 Core
+
修改 Battle
+
修改 Command
+
修改 Context
+
修改多个 if/else
```

# 5. 最关键的问题：模块“可删除”比模块“可添加”更重要

这是今天最重要的架构观察。

### OBSERVATION

很多框架会宣传：

> “支持插件。”

但真正检验插件架构的其实不是：

> “我能不能安装插件？”

而是：

> **“我把插件删除以后，核心能不能正常运行？”**

这与你最初提出的：

> **拆除任意 L1 模块，内核照转，其余模块无感知**

完全一致。

因此建议把模块架构的验收标准改成：

```text
Add Test
Remove Test
Disable Test
Isolate Test
Upgrade Test
```

而不是只有：

```text
Load Test
```

# 6. 一个模块真正可删除，需要满足 5 个条件

## 条件 A：没有反向硬引用

例如：

```text
battle → quest
```

这种直接 import 就很危险。

更合理：

```text
battle
  ↓
Event Bus
  ↑
quest
```

这样：

```text
quest removed
```

battle 仍然可以运行。

---

## 条件 B：模块不能向 Core 注入专属字段

这是当前项目尤其值得关注的一点。

`ctx` 已经存在大量运行时键，而且 README 明确指出内部 `ctx` 并不是扩展契约。

这是一个正确方向。

### HYPOTHESIS H-20260930-01

> **真正稳定的插件边界不能依赖不断增长的全局 `ctx` 字段，而应该依赖能力接口 + 事件 + 模块私有状态。**

状态：

**SUPPORTED**

原因：

如果每新增模块都向：

```text
ctx["xxx"]
```

加入字段，那么最终：

```text
ctx
```

会变成隐式 Service Locator。

这会直接破坏：

- 模块删除
- 依赖分析
- 类型检查
- AI 阅读
- 自动化重构

# 7. Event Bus 应该成为模块间的“唯一横向通信面”

### OBSERVATION

项目已经明确希望：

> 同级模块禁止直接调用，一律通过事件总线广播/订阅。

如果这个原则继续强化，那么可以进一步规定：

```text
Module A
   │
   │ publish
   ▼
 Event Bus
   │
   ├── Module B
   ├── Module C
   └── Module D
```

而禁止：

```text
Module A → Module B
Module A → Module C
```

这样模块之间形成的是：

```text
事件契约依赖
```

而不是：

```text
实现依赖
```

# 8. 但 Event Bus 本身也不能成为“万能垃圾桶”

### 反例

如果所有东西都变成：

```text
event_bus.publish(...)
```

最终可能出现：

```text
event_a
event_b
event_c
event_d
event_e
...
```

任何人都不知道：

- 谁发送？
- 谁接收？
- 参数是什么？
- 顺序是什么？
- 是否允许取消？
- 是否同步？
- 是否保证一次？
- 是否允许多个消费者？

这会形成所谓的 **Event Spaghetti**。

### HYPOTHESIS H-20260930-02

> Event Bus 的核心不是“减少函数调用”，而是建立“稳定的跨模块契约”；因此每个跨模块事件都应该拥有明确的 payload schema、producer、consumer 和生命周期语义。

状态：

**SUPPORTED**

这与前几轮研究出的：

> “事件定义 ≠ 事件派发 ≠ 运行时可达”

可以直接合并。

# 10. 但当前阶段不建议直接使用 Python Entry Points

### SUGGESTION

目前项目没有必要马上把所有模块改成独立 Python distribution。



会明显增加普通作者的使用门槛。

> 换数据库 / 内容包，就能形成新的游戏。

因此游戏内容模块应该优先：

```text

```

而不是：


### 第三，真正需要插件包的是“新机制”

这一点反而和现有 Vibecoding 说明书高度一致：


# 11. 最值得采用的是“轻量 Registry”

建议最终形成：


```text

     ↓

     ↓
```

# 12. 最重要的启发：把“模块”变成能力提供者

这是今天最值得进入长期架构知识库的内容。

不要定义：

```text

```

而定义：

```text
模块 = 一组能力（Capabilities）的提供者
```

例如：

```text
Battle Module
 ├─ battle.start
 ├─ battle.execute_action
 ├─ battle.calculate_damage
 └─ battle.end
```

Craft：

```text

 ├─ craft.preview
 ├─ craft.execute
 └─ craft.salvage
```

Quest：

```text
Quest Module
 ├─ quest.accept
 ├─ quest.progress
 └─ quest.complete
```

于是“删除模块”就可以变成：

```text
remove Craft Module
       ↓
craft.* capabilities disappear
       ↓
依赖它们的配置获得明确提示
       ↓
其他模块继续运行
```

这比单纯的：

```text
enabled = false
```

强很多。

# 16. 反例与风险

### 风险 1：Registry 变成新的 God Object

如果所有东西都注册到：

```text
GlobalRegistry
```

最终 Registry 自己会变成新的核心黑洞。

**解决方向：**

按能力域拆分：

```text
ModuleRegistry
CapabilityRegistry
CommandRegistry
EventRegistry
```

但它们共享统一的注册协议。

---

### 风险 2：Capability 过度细化

如果出现：

```text
battle.calculate_damage
battle.get_attack
battle.get_defense
battle.get_target
battle.get_skill
...
```

模块边界会变得极其碎片化。

所以 Capability 应代表：

> **稳定的业务能力**

而不是：

> **每一个函数。**

---

### 风险 3：Event Bus + Registry 双重间接

如果：

```text
A
 ↓
Event Bus
 ↓
Registry
 ↓
B
```

所有调用都要经过两三层间接，会增加 AI 理解难度。

因此：

- **事件发生** → Event Bus
- **请求某项能力** → Capability Registry
- **读取共享数据** → 明确 Data/State API

不要三者混用。

### OBSERVATION

因此不要尝试把：

```text
EventSchema
```

写成：

```text
万能业务系统
```

例如：

```json
{
  "event": "status_lose",
  "damage": 10,
  "condition": "..."
}
```

Schema 可以告诉你：

- event 是字符串
- damage 是数字
- 某字段可选
- 某字段不能超过范围

但它不应该承担：

> “status_lose 必须在 tick 过期之后、状态移除完成之前触发。”

这种属于**运行时语义**。

所以项目需要保持：

```text id="schema004"
Schema
  = 声明“是什么”
  
Runtime
  = 决定“怎么发生”
  
Tests
  = 证明“确实这样发生”
```

而不是：

```text
Schema
  = 整个游戏引擎
```

# 8. 今天发现的一个重要架构边界

可以把项目中的信息分成四层：

| 层 | 作用 | 例子 |
|---|---|---|
| Schema | 定义允许什么 | `status_lose` 是合法事件 |
| Registry | 当前有什么 | 17 个事件、36 个模块 |
| Runtime | 怎么运行 | `_death_check_side()` 派发 |
| Evidence | 如何证明 | 单元测试、回归测试 |

因此：

```text id="schema005"
Schema ≠ Registry ≠ Runtime ≠ Test
```

但它们应该存在明确的依赖方向：

```text id="schema006"
Schema
 ↓
Registry
 ↓
Runtime
 ↓
Evidence
```

更准确地说，测试可以同时验证四层，而不是 Runtime 反向依赖测试。

# 9. 对项目“内核最小化”的直接意义

这是今天最值得连接到长期目标的地方。

如果采用：

```text id="schema007"

      ↓
派生 Validator / Editor / Docs
```

那么 Core 不需要知道：

```text

```

Core 只需要：

```text

```

这样能够避免一个非常常见的架构退化：

```text id="schema008"

 ├── Runtime
```

最终 Core 越来越胖。

# 6. 可以定义第一批 Architecture Invariants

## I-01：事件唯一源不漂移

必须满足：

```text
EVENT_POINTS
==
tuple(p.name for p in EVENT_POINT_TABLE)
```

不能出现：

```text
EVENT_POINT_TABLE
EVENT_POINTS
```

分别手工维护。

---

## I-02：事件索引完全派生

必须满足：

```text
EVENT_POINT_INDEX
==
{p.name: p for p in EVENT_POINT_TABLE}
```

否则：

```text
EVENT_POINT_TABLE
```

和：

```text
EVENT_POINT_INDEX
```

可能产生分叉。

---

## I-03：事件名称唯一

必须满足：

```text
len(EVENT_POINT_TABLE)
==
len(set(p.name for p in EVENT_POINT_TABLE))
```

这看起来简单，但非常重要。

因为重复 ID 会导致：

```text
EVENT_POINT_INDEX["xxx"]
```

静默覆盖前一个定义。

---

## I-04：合法事件只能处于两种状态

```text
dispatched=True
```

或者：

```text
dispatched=False
```

其中 `False` 必须明确表示：

> **合法，但当前没有生产派发点。**

而不能出现第三种隐式状态：

```text
“表里登记了，但不知道到底是什么状态。”
```

---

## I-05：Y-19 / Y-24 互斥

对于任意 trigger：

```text
unknown
→ Y-19

known + undispatched
→ Y-24

known + dispatched
→ no warning
```

这其实已经被批84中的几个测试表达出来了。

下一步可以把它提升为**参数化性质测试**，而不是只测试：

```text
"on_kil"
"on_hit"
```

两个例子。

> “某次测试到底产生了哪些具体对象。”

而是关注：

> **事件轨迹是否符合生命周期协议。**

# 11. Event Trace 会成为非常有价值的测试资产

建议未来测试统一记录：

```text
EventTrace
[
    battle_start,
    turn_start,
    action_start,
    status_gain,
    action_end,
    turn_end,
    battle_end
]
```

然后对 trace 做验证。

例如：

```text
assert before(trace, "battle_start", "action_start")
assert before(trace, "action_start", "action_end")
assert before(trace, "turn_start", "turn_end")
```

甚至：

```text
assert count("battle_start") == 1
assert count("battle_end") <= 1
```

这样一来，Event Bus 的正确性就不再依赖几十个散落测试。

# 12. 模块测试也可以采用同样思路

上一轮研究的：

> Module = Capability Provider

今天可以进一步得到：

```text
Module Contract
```

例如 Battle Module 对外承诺：

```text
provides:
    battle.start
    battle.execute
    battle.end

publishes:
    battle_start
    battle_end
    action_start
    action_end
```

测试不必测试 Battle Module 内部用了哪个函数。

只测试：

```text
给定输入
→ 提供哪些 Capability
→ 产生哪些 Event
→ 保证哪些 Invariant
```

这就是一个真正的**模块契约**。

# 13. 这比传统 Mock 更适合你的架构目标

### EXTERNAL OPINION

Martin Fowler 对契约测试的总结是：组件之间一旦形成接口依赖，就形成了契约；契约可以描述输入、输出、副作用以及性能/并发特征。契约测试的价值是验证这些边界，而不是深入测试提供者内部实现。citeturn1search4turn1search5

urlMartin Fowler — Contract Testhttps://martinfowler.com/bliki/ContractTest.html

### 对 QBot 的意义

例如：

```text
Battle
```

不应该被 Quest 测试：

```text
battle.py 第 4321 行调用了某函数
```

Quest 应该测试：

```text
Battle 提供 battle.execute
并产生 action_end
```

这就能保护：

> **接口稳定，而实现可以自由重构。**

这非常符合 Vibe Coding。

# 21. 反例与风险

## 风险 1：不变量过多

如果每个细节都变成 invariant：

```text
1000 条 invariant
```

那么开发速度会下降。

原则应该是：

> 只保护“未来重构时不能被破坏”的架构性质。

---

## 风险 2：Contract 过度具体

如果 Module Contract 写成：

```text
必须调用 function_x()
然后 function_y()
```

那其实不是 Contract，而是实现锁死。

正确的是：

```text
输入
→ 能力
→ 输出
→ 事件
→ 不变量
```

---

## 风险 3：Stateful Test 随机性导致难以复现

pytest 官方也指出，测试的非确定性或环境状态控制不足会产生 flaky tests，而 flaky tests 会削弱测试作为可靠反馈信号的价值。citeturn1search3

因此如果以后引入 Stateful Testing：

必须保留：

```text
seed
操作序列
失败状态快照
最小化后的 replay case
```

否则 AI 调试反而会变困难。

# 3. 项目分析：当前最容易被低估的风险不是“能不能加载”，而是“加载后语义是否仍然相同”

### FACT

- 平台无关核心包

- 设计层文档驱动

### OBSERVATION

```text
框架代码版本
内容 Schema 版本
数据库结构版本
具体游戏数据版本
```

如果只用一个版本号，会出现无法判断的问题：

```text
当前程序能否加载这个数据库？
能加载，但旧字段的含义是否改变？
能加载，但事件/状态/公式语义是否已经变化？
这个内容包是旧 Schema，还是旧游戏规则？
```

因此项目需要明确区分：

```text
Runtime Version
Schema Version
Storage Version
Content Pack Version
Rule Set Version
```

# 4. “数据库换了就是新游戏”不等于“数据库结构随意变化”

### HYPOTHESIS H-20261003-01

> “内容可替换”与“Schema 可任意变化”必须分离：内容数据可以高度替换，但数据结构、引用规则和运行时语义必须有独立的兼容策略。

状态：**SUPPORTED**

原因：

- 新游戏可以只换数值、文本、地图、掉落和配置；
- 也可能需要新增一种机制；
- 新增机制不应偷偷伪装成普通数据；
- 否则配置层会吸收过多代码责任，最终变成不可验证的动态脚本系统。

# 5. 建议建立五层版本模型

## 第一层：Framework Version

描述代码提供了哪些基础能力：

```text
framework_version = 0.8.0
```

例如：

- Event Bus 是否支持 `status_lose`
- 是否支持新的能力注册
- 是否存在某个模块
- 某个接口是否已经废弃

---

## 第二层：Schema Version

描述配置文件结构：

```text
schema_version = 3
```

例如：

- 字段改名
- 字段拆分
- 枚举变化
- 结构嵌套变化
- 引用格式变化

Schema Version 只描述：

> **数据长什么样。**

不要让它承载全部业务语义。

---

## 第三层：Storage Version

描述数据库内部结构：

```text
storage_version = 12
```

例如：

- 新增表
- 索引变化
- 字段迁移
- 状态快照格式变化
- 存档结构变化

它不应与内容 Schema Version 混为一谈。

---

## 第四层：Content Pack Version

描述某套内容包自身：

```text
content_pack = {
  "id": "demo_world",
  "version": "1.4.0"
}
```

例如：

- 新增怪物
- 调整技能公式
- 更新任务文本
- 修改掉落
- 增加区域

这类变化未必需要框架升级。

---

## 第五层：Rule Set Version

描述规则语义：

```text
rule_set_version = "turn-rpg-v2"
```

例如：

- 伤害公式变更
- 状态叠层规则变更
- 行动顺序规则变更
- 事件时机改变
- 战斗结果判定改变

这一层最容易被遗漏。

因为结构不变时，规则仍可能发生破坏性变化。

---

# 6. 为什么必须区分 Schema Version 与 Rule Set Version

### 例子

假设旧配置：

```json
{
  "damage_formula": "atk * 1.2",
  "critical_rate": 0.2
}
```

新版本仍然使用同样字段，因此：

```text
Schema Version 没变
```

但如果运行时把暴击改成：

```text
最终伤害 × 2
```

改为：

```text
基础伤害后再乘 1.5
```

那么：

```text
Rule Set Version 已变
```

如果没有 Rule Set Version，旧内容包会“正常加载”，但运行结果已经悄悄变了。

### HYPOTHESIS H-20261003-02

> 对 RPG 框架而言，真正需要兼容的不只是字段结构，还包括公式、事件时机、状态生命周期和行动顺序等规则语义。

状态：**SUPPORTED**

# 7. 外部参考资料一：SUEWS 的 Schema Versioning

SUEWS 的文档明确把 Schema Version 与软件版本分开：

- Schema 版本只追踪配置结构变化；
- 软件可以频繁迭代，但 Schema 不必每次都改变；
- 旧 Schema 若存在迁移处理器，可以继续兼容；
- 新于当前程序的 Schema 应被明确拒绝或提示；
- 迁移可以通过独立命令执行，并支持 dry-run。citeturn307683search4turn307683search5

urlSUEWS Schema Versioninghttps://docs.suews.io/latest/contributing/schema/schema_versioning.html

### 对 QBot 的可借鉴之处

最值得借鉴的不是具体命令，而是这几个原则：

```text
旧版本可识别
兼容路径可判断
迁移过程可预览
新版本不可静默加载
```

特别适合 QBot 的场景：

- 老数据库继续运行
- 老内容包加载时给出兼容性说明
- 旧配置在迁移前先做 dry-run
- 迁移失败不能破坏原始内容

### 不宜照搬之处

QBot 不需要一开始就构建复杂的通用迁移平台。当前更合适的是：

- 先定义版本元数据
- 先支持少量明确的迁移函数
- 先覆盖最容易变化的字段和引用
- 先建立兼容性报告

---

# 8. 外部参考资料二：OpenClaw 的数据库版本契约

OpenClaw 的文档采用了较严格的数据库版本契约：

- 数据库记录自身 Schema Version；
- 程序只向前迁移旧版本；
- 数据库版本高于当前运行时版本时拒绝启动；
- 启动前检查全部注册数据库是否兼容。citeturn307683search6

urlOpenClaw Versioning Contracthttps://docs.openclaw.ai/reference/database-schemas/versioning

### 对 QBot 的可借鉴之处

QBot 可以采用同样的边界：

```text
旧数据库
→ 可迁移
→ 迁移后加载

同版本数据库
→ 直接加载

新于当前程序的数据库
→ 拒绝加载并说明原因
```

这比：

```text
尽量加载
遇到未知字段就忽略
```

安全得多。

因为“忽略未知字段”会产生一种危险状态：

> 数据库看起来能运行，但部分游戏语义已经丢失。

### 不宜照搬之处

QBot 的内容包和游戏存档未必都需要“数据库级别全部阻断”。例如：

- 只读内容预览可以允许降级；
- 生产战斗存档应更严格；
- 测试数据库可以选择警告模式。

因此可以按用途定义兼容策略：

```text
Preview: WARNING
Development: WARNING + report
Production: BLOCK
```

# 10. 内容包迁移与数据库迁移不能混为一谈

### OBSERVATION

建议至少分成三种迁移：

## A. 结构迁移

字段、表、键、引用格式变化。

```text
schema 2 → schema 3
```

## B. 数据迁移

旧数据转成新数据。

```text
old_status_id → new_status_id
```

## C. 语义迁移

规则变化需要显式说明：

```text
旧状态“燃烧”每回合结算
→ 新版本改为行动后结算
```

语义迁移最危险，因为它可能不需要任何结构变化。

### HYPOTHESIS H-20261003-03

> 语义迁移必须生成“差异报告”，不能只执行转换函数。

状态：**UNCERTAIN**

建议报告至少包含：

```text
- 受影响规则
- 受影响内容对象
- 旧行为摘要
- 新行为摘要
- 是否可逆
- 是否需要玩家确认
- 是否影响存档公平性
```

# 11. 对“无硬编码化”的直接启发

迁移逻辑本身不能完全依赖分散的 `if old_version == ...`。

否则会形成：

```python
if version == 1:
    ...
elif version == 2:
    ...
elif version == 3:
    ...
```

最终迁移系统会变成新的硬编码中心。

更好的做法是：

```text
MigrationRegistry
- from_version
- to_version
- scope
- reversible
- handler
- risk_level
```

例如：

```text
schema 2 → schema 3
storage
reversible = false
risk = medium
```

再由迁移规划器寻找路径：

```text
2 → 3 → 4
```

这与前几轮研究的 Registry 思路保持一致，但这里的 Registry 只负责**迁移能力**，不负责运行时业务。

---

# 12. 对“内核最小化”的直接启发

Core 不应该知道每个内容包的迁移细节。

更合适的分层：

```text
Core
 ├─ 版本识别
 ├─ 兼容性判断
 ├─ 迁移规划
 └─ 迁移执行协议

Content / Storage Adapter
 └─ 提供具体迁移处理器
```

这样：

- 核心负责流程与契约；
- 内容包负责自己的数据升级；
- 数据库适配器负责存储迁移；
- 规则系统负责语义差异报告。

# 13. 反例：只记录 Content Pack Version 不够

假设：

```text
content_pack_version = 1.2.0
```

但内容包依赖：

```text
framework >= 0.9
rule_set = turn-rpg-v3
schema = 4
```

如果只保存一个内容包版本，运行时无法判断：

- 是不是缺少事件？
- 是否支持某个模块？
- 公式是否改变？
- 数据库是否需要升级？
- 旧存档是否还能继续使用？

因此内容包 manifest 至少要有：

```json
{
  "id": "demo_world",
  "version": "1.2.0",
  "requires": {
    "framework": ">=0.8,<1.0",
    "schema": 3,
    "storage": 7,
    "rule_set": "turn-rpg-v2"
  }
}
```

# 14. 最重要启发

今天最重要的结论是：

> **“更换数据库又是一个新游戏”必须建立在“版本契约清晰”的前提上，否则只是把不可预测的运行时差异转移到了数据层。**

建议把每个游戏实例都视为一个组合：

```text
Game Instance
=
Framework
+ Schema
+ Storage
+ Content Pack
+ Rule Set
+ Enabled Capabilities
```

然后由兼容性层检查：

```text
这个组合能否安全启动？
```

而不是只检查：

```text
数据库文件能不能打开？
```

# 17. 反例与风险

## 风险 1：版本号过多

如果每个对象都拥有独立版本：

```text
技能版本
状态版本
事件版本
模块版本
规则版本
存储版本
```

使用者会难以理解，AI 也会难以判断。

建议优先保留五类顶层版本，细节用迁移记录和变更日志补充。

## 风险 2：迁移器不可逆

对于玩家存档和生产数据，默认迁移前应备份或生成新副本，不能直接覆盖原始数据。

## 风险 3：新字段默认值改变游戏行为

即使结构迁移成功，新增字段的默认值也可能改变：

- 战斗结果
- 掉落
- 状态效果
- 任务进度

所以迁移测试不能只检查“文件能否打开”。

## 风险 4：把语义变化伪装成补丁版本

若规则语义发生破坏性改变，应在 Rule Set Version 或兼容性报告中明确体现，而不是只把内容包从 `1.0.1` 改到 `1.0.2`。

# 7. 外部参考资料

## 7.1 GitHub Status Checks：验证必须绑定到最新 Commit

GitHub 文档明确指出：

- 状态检查用于表示构建、测试、代码扫描、部署等验证结果；
- 如果分支启用了必需检查，检查必须在合并前通过；
- 必需检查必须对应**最新 Commit SHA**；
- 旧 Commit 上的通过结果不能替代最新提交上的检查。citeturn662177search0turn662177search1turn662177search11

### 对 QBot 的启发

项目的“批次通过”也应该绑定到：

```text
commit_sha
test_command
test_scope
execution_time
result
```

否则会出现这种危险情况：

```text
批84测试通过
但通过的是旧 Commit
当前文档和代码已发生变化
```

这与 GitHub 的“检查必须作用于最新 Commit”是同一个基本原则。

### 不宜照搬之处

QBot 当前未必需要立即启用复杂的分支保护规则。更优先的是先把**证据记录模型**建立起来，再决定哪些证据升级为真正的合并门禁。

## 7.2 pytest 自定义标记：让测试集合表达验证层次

pytest 官方支持注册自定义 marker，并用 `-m` 选择测试集；开启 `strict_markers` 后，未注册的标记会直接报错，而不是静默接受。citeturn662177search5turn662177search13

### 对 QBot 的启发

可以把现有测试按语义分层：

```python
@pytest.mark.unit
@pytest.mark.contract
@pytest.mark.invariant
@pytest.mark.integration
@pytest.mark.scenario
@pytest.mark.architecture_gate
```

再配合命令：

```text
pytest -m unit
pytest -m contract
pytest -m architecture_gate
pytest -m "not slow"
```

这样《Vibecoding 说明书》中的验收命令就不再只是“跑全部测试”，而可以精确对应某个验收目标。

### 不宜照搬之处

不要给每个测试都加很多标签。标签应该服务于：

- 运行分层；
- 证据统计；
- 关键门禁；
- 快速回归。

如果 marker 数量过多，反而会增加认知负担。

今天可以继续往前推进：

```text
Architecture Invariant
    ↓
Claim
    ↓
Evidence
    ↓
Gate
```

例如：

## 架构不变量

```text
模块删除后核心仍可启动
```

## Claim

```text
REMOVE-CORE-01
```

## Evidence

```text
STATIC_REVIEW：依赖图无反向 import
INTEGRATION_TEST：禁用模块后启动成功
CI_RUN：当前 Commit 测试通过
```

## Gate

```text
如果没有 Integration Test，则不得标记为 COMPLETE
```

这使“架构目标”从抽象口号变成可验收资产。

- M6/M7/M8；

# 11. 风险与反例

## 反例一：证据标签过于复杂

如果每个验收点要填 15 个字段，作者可能会直接跳过记录，回到自由文本。

**缓解办法：**

先用最小四字段：

```text
claim
evidence_type
result
commit_sha
```

其余字段按需要增加。

---

## 反例二：静态审查被低估

静态审查虽然不能替代动态测试，但它对以下问题很有价值：

- 依赖方向；
- 是否存在硬编码；
- 是否重复维护唯一源；
- 是否存在明显死分支；
- 是否缺少注册入口；
- 是否违反模块边界。

因此不能把静态证据改成“无效”，而应把它标为**适用范围不同**。

---

## 反例三：所有东西都升级为 CI 阻断门禁

如果每个黄色提示、文档差异、实验性能力都阻断合并，开发速度会明显下降。

建议按等级区分：

```text
P0 / 契约破坏 → 阻断
P1 / 核心行为未证实 → 通常阻断
P2 / 边界缺口 → 允许合并但必须登记
P3 / 文档与防御项 → 警告
```

# 3. Event Bus 的真正问题：隐藏依赖

假设有：

```text
Battle
  ↓ publish
battle.finished
```

然后：

```text
Reward
  ↓ subscribe
battle.finished
```

这很好。

但如果：

```text
Reward
  ↓ publish
reward.granted
```

又有：

```text
Quest
  ↓ subscribe
reward.granted
  ↓ publish
quest.progressed
```

最后：

```text
Battle
  ← subscribe
quest.progressed
```

就出现：

```text
Battle
 ↓
Reward
 ↓
Quest
 ↓
Battle
```

代码 import 图可能完全没有循环。

但运行时已经：

```text
A → B → C → A
```

### HYPOTHESIS

**Event Bus 会消除静态依赖，却可能隐藏运行时依赖。**

状态：`SUPPORTED`

# 4. 外部参考：OpenTelemetry 的 Event Semantic Conventions

OpenTelemetry 对 Event 的定义非常值得借鉴。

它要求事件具有明确的：

- event name；
- timestamp；
- severity；
- structured attributes；
- event definition；
- requirement level。

并明确强调：

> 一个事件名应该唯一对应一种事件结构。

citeturn0search0turn0search6

这对 QBot 很有启发。

目前很多 Event Bus 实现容易变成：

```python
bus.publish(
    "something_happened",
    {"foo": x, "bar": y}
)
```

这种方式的问题是：

```text
foo 是什么？
bar 是什么？
什么时候可以为空？
谁可以发布？
谁可以订阅？
这个事件发生前还是发生后？
这个事件是否允许重复？
```

都不明确。

```yaml
  - battle

  - reward

  - statistics

  actor_id:
    type: entity_id
    required: true

    type: enum

      - success
      - miss
```

重点不是 YAML 本身。

> **Event Bus 中传递的是“有契约的数据”，而不是任意 Python dict。**

# 7. QBot 应严格区分 Command / Event

这是今天非常值得加入架构规则的一点。

## Command

表达：

> **“请做某件事。”**

例如：

```text
StartBattle
EquipItem
UseSkill
MovePlayer
```

特点：

```text
有目标
有执行者
通常只有一个权威处理者
```

---

## Event

表达：

> **“某件事已经发生。”**

例如：

```text
BattleStarted
SkillUsed
DamageResolved
BattleFinished
ItemEquipped
```

特点：

```text
过去时
事实
可以有多个订阅者
订阅者原则上不应该改变过去发生的事实
```

# 8. 为什么这对你的“状态机分层”尤其重要

你的目标是：

```text
状态机分层
+
Event Bus
```

那么可以形成：

```text
Command
 ↓
State Machine
 ↓
State Transition
 ↓
Domain Event
 ↓
Other Modules
```

例如：

```text
UseSkillCommand
        ↓
BattleState
        ↓
ResolveSkill
        ↓
DamageResolved
        ↓
┌───────┼────────┐
↓       ↓        ↓
Quest  Reward  Statistics
```

这里有一个非常重要的边界：

> **状态机负责决定“发生了什么”，Event Bus 负责通知“发生过什么”。**

这样 Event Bus 就不会反过来成为新的状态机。

# 9. 不建议让 Event Handler 直接修改核心状态

危险模式：

```python

    player.exp += 100
```

因为这意味着：

```text
Event
 ↓
隐藏修改 State
```

久而久之谁修改玩家经验就无法追踪。

更好的模式：

```text
battle.finished
      ↓
Reward Module
      ↓
Reward Command
      ↓
State Mutation
```

或者：

```text
battle.finished
      ↓
Reward Policy
      ↓
State Transition
```

# 12. 一个重要的新模型：Event Dependency Graph

建议长期把架构依赖图从：

```text

```

升级为：

```text
Architecture Graph
```

包含至少三种边：

```text

A ──publish─→ Event-X
Event-X ──consume──→ B
```

于是：

```text

+
事件依赖
```

才是真正的系统依赖。


# 13. Event Bus 还需要一个非常重要的限制：方向

如果项目目标是：

> 单向依赖

那么事件也应该拥有方向。

例如：

```text
L1
 ↓
L2
 ↓
L3
```

允许：

```text
L1 → L2
L1 → L3
L2 → L3
```

但禁止：

```text
L3 → L2
L3 → L1
```

即使这个反向通信通过 Event Bus 完成，也应该禁止。

所以：

> **Event Bus 是通信媒介，不应该成为绕过架构层级规则的逃生通道。**

这个原则非常重要。

```text
                 │ Capability Registry  │
                 └──────────┬───────────┘

              │ Architecture Fitness     │

              └────────────┬─────────────┘
                           ↓

          │                                │
```

# 7. 更重要的是：文档不是同一种东西

应该先给文档分类。

建议：

```text
DESIGN
CONTRACT
IMPLEMENTATION
AUDIT
HISTORICAL
GUIDE
INDEX
GENERATED
```

例如：

### DESIGN

描述：

> 应该怎么设计。

它可以领先代码。

---

### CONTRACT

描述：

> 实现必须满足什么。

它不能悄悄过期。

---

### AUDIT

描述：

它天然允许过时，但必须带：

```text
snapshot_commit

```

---

### HISTORICAL

描述：

> 当时发生过什么。

不应该被要求跟随当前代码变化。

---

### INDEX

描述：

> 当前有哪些资产。

最好自动生成。

---

### GENERATED

完全由代码/Schema 自动生成。

不能人工修改。

# 2. 今日研究主题

## T-Event-Capability-Matrix

### Event Capability Matrix：事件能力矩阵

目标是回答：

> 一个事件键到底处于什么状态？

而不是只回答：

> 这个字符串是否存在？

---

# 3. 当前模型的问题

现在至少有以下几种状态：

| 状态 | 含义 |
|---|---|
| UNKNOWN | 事件键不存在 |
| REGISTERED | 事件键合法 |
| REGISTERED_NO_DISPATCH | 合法，但运行时没有派发点 |
| DISPATCHED | 运行时存在派发 |
| CONSUMED | 存在消费者 |
| EFFECTIVE | 已经产生业务效果 |

这些状态不能混成一个 Boolean。

例如：

```text
on_hit
```

可能：

```text
合法
↓
没有派发
↓
因此不会触发
```

而：

```text
status_lose
```

可能：

```text
合法
↓
有派发点
↓
resolver 找到声明
↓
消费者执行
↓
产生效果
```

---

# 4. 一个更完整的 Event Capability Matrix

建议未来把事件能力表示为：

```yaml
event:
  key: status_lose

  declared: true

  dispatch:
    available: true
    locations:
      - effects._dispatch_status_expire
      - effects._remove_status

  consumers:
    available: true

  runtime:
    reachable: true

  validation:
    legal: true

  phase:
    status: current
```

于是：

```text
合法性
≠
可派发性
≠
可消费性
≠
可达性
```

---

# 5. 这和 AsyncAPI 有一个很有价值的对应关系

AsyncAPI 将事件驱动 API 拆成：

```text
Channel
Message
Operation
```

其中 channel 描述消息通信位置，operation 描述应用对 channel 的发送/接收行为；文档本身可以作为机器可读的 Event-Driven API 定义，并进一步用于文档生成和消息验证。citeturn1search8turn1search10

尤其重要的是：

> **“消息存在”与“应用执行什么操作”是不同层次的信息。**

这和 QBot 当前批84的问题高度类似。

---

# 6. QBot 不应该照搬 AsyncAPI

### EXTERNAL OPINION

AsyncAPI 是面向消息 API 的通用规范，适合描述：

```text
producer
consumer
channel
message
operation
```

citeturn1search4turn1search8

### SUGGESTION

QBot 更适合借鉴其**分层思想**，而不是引入整个 AsyncAPI。

因为 QBot 的事件还有 RPG 特有语义：

```text
事件键
→ 派发时点
→ resolver
→ 条件
→ 状态
→ effect
```

如果直接套 AsyncAPI，很容易把运行时业务语义压扁成“消息 API”。

# 7. 今天最重要的启发

## Event Registry 应该逐渐升级为 Event Capability Registry

现在类似：

```text

```

可以进一步发展成：

```text
EVENT_CAPABILITY_TABLE
```

例如：

| Event | Registered | Dispatched | Consumed | Runtime Reachable |
|---|---:|---:|---:|---:|
| `turn_start` | ✓ | ✓ | ✓ | ✓ |
| `turn_end` | ✓ | ✓ | ✓ | ✓ |
| `status_lose` | ✓ | ✓ | ✓ | ✓ |
| `on_hit` | ✓ | ✗ | — | ✗ |
| `xxx` | ✗ | ✗ | — | ✗ |

这样就可以直接回答：

> 为什么这个事件虽然合法，却不会触发？

而不需要 AI 再自己 grep 整个项目。

# 10. 但是这里有一个非常重要的边界

### HYPOTHESIS

**不能把“静态分析发现没有消费者”直接等价为“运行时不会产生效果”。**

原因是：

```text
消费者可能动态注册
消费者可能通过配置出现
消费者可能由模块加载
消费者可能存在条件注册
```

所以：

```text
STATIC_NO_CONSUMER
```

应该只是：

> “静态扫描没有发现消费者。”

而不是：

> “系统绝对没有消费者。”

这是今天需要特别保留的反例。

这就是：

# 17. 反例与风险

### R1：动态注册

如果模块可以运行时注册消费者，静态扫描不能证明：

```text

```

只能证明：

```text

```

---

### R2：事件过度分层

如果 L0-L5 被强制用于所有内部事件，会产生大量维护成本。

因此应该先用于：

```text
配置事件
跨模块事件
玩家可配置触发器
```

而不是所有临时内部事件。

---

### R3：把 Event Bus 变成万能 RPC

如果所有东西都变成 Event：

```text

命令
通知
返回值
```

都会混在一起，最终反而损害架构。

# 二、研究主题一：静态扫描器能证明什么？

## T-TEST-ORACLE-01

### 2.1 研究对象

重点检查批84新增的事件派发状态测试：

urltest_batch84_event_dispatch_status.pyhttps://github.com/xianyugezi/QBot-TurnTellerRPG/blob/main/tests/unit/test_batch84_event_dispatch_status.py

该测试使用正则表达式扫描 `qbot_rpg/**/*.py`，查找形如：

```python
_dispatch_event("event_name", ...)
_dispatch_status_event("event_name", ...)
```

的调用，然后将发现的事件名与 `EVENT_POINT_TABLE` 中标记为 `dispatched=True` 的事件进行比较。

测试还维护了预期的已接入事件集合和二期未接入事件集合。

### 2.2 这套测试的优点

**FACT：** 当前测试不只是验证一个常量表是否符合预期，还会检查声明的派发状态是否与生产代码中扫描到的派发调用一致。

它可以发现以下问题：

- 新增了符合扫描规则的派发调用，却忘记更新事件登记表。
- 事件表错误地将已有事件标记为未接入。
- 原有事件被意外移除或顺序发生变化。
- 已接入事件和二期未接入事件的边界发生意外变化。

这比单纯检查：

```python
assert len(EVENT_POINTS) == 17
```

更有价值。

因为它将一部分架构约束转化成了可自动执行的检查。

### 2.3 但它存在一个明确的证明边界

**OBSERVATION：** 该测试实际证明的是：

> 在当前扫描范围内，符合指定正则表达式的事件派发调用，与事件表声明保持一致。

它不能自动证明：

> 所有运行时可能发生的事件派发，都已经被扫描器发现。

例如，以下写法就不一定能被当前扫描规则识别：

```python
event_name = resolve_event_name()
dispatch(event_name, payload)
```

其他可能造成漏检的情况还包括：

- 通过别名调用派发函数。
- 使用间接包装函数。
- 从配置中读取事件名。
- 在动态注册过程中构造派发路径。

这些只是说明扫描器的理论边界，并不意味着当前项目已经存在上述缺陷。

### 2.4 这对架构审计意味着什么？

**HYPOTHESIS：** 项目中的部分静态自检可能同时承担两种职责：

1. 检查当前代码是否遵守既定的编码约定。
2. 证明某项运行时能力确实存在。

前者通常可以通过有限的语法模式实现。

后者则需要更加严格的证据，因为运行时行为可能跨越多个函数、模块或数据配置。

如果不区分这两种职责，审计结果可能显得比实际证据更强。

### 2.5 建议

暂时不必删除现有扫描器。

建议先把它的能力边界写清楚：

| 检查类型 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| 常量表检查 | 登记内容符合预期 | 运行时行为正确 |
| 正则扫描 | 约定格式的调用保持一致 | 不存在其他间接调用 |
| AST 扫描 | 语法树中符合规则的调用保持一致 | 动态执行路径一定可达 |
| 单元测试 | 指定输入下产生预期结果 | 所有输入均正确 |
| 集成测试 | 指定集成场景能够工作 | 所有模块组合均正确 |
| 变异测试 | 某些代码变更能被现有测试发现 | 所有真实缺陷都能被发现 |

**最重要的区分：静态一致性、运行时可达性和业务行为正确性，是三个不同的证明目标。**

# 三、研究主题二：变异测试能否提高测试质量？

## T-MUTATION-TESTING-01

### 3.1 什么是变异测试？

变异测试会有意对代码进行小幅修改，然后运行原有测试，观察测试是否能够发现这些变化。

例如：

```python
if dispatched:
    emit_event()
```

可以构造一个用于实验的变异版本：

```python
if False:
    emit_event()
```

如果测试仍然全部通过，就说明至少在这个变异场景下，测试没有发现行为被改变。

其他常见变异包括：

- 修改比较运算符。
- 改变边界条件。
- 修改数值常量。
- 删除关键调用。
- 改变分支行为。

它与覆盖率的区别在于：

**覆盖率关注代码是否被执行，变异测试关注某些代码变化是否能够被测试发现。**

一个函数即使有很高的行覆盖率，也可能存在断言不足的问题。

### 3.2 为什么值得在 QBot 中研究？

QBot 已经具有较多测试和多层质量门禁。

继续增加测试数量，未必总是最有效的下一步。

对于关键业务路径，更值得回答：

> 如果 AI 在重构时不小心删除了一次派发、放宽了一个验证条件，或者改变了一个结算边界，现有测试究竟能不能发现？

这尤其适用于项目中需要长期维护的机制：

- 事件派发。
- 效果执行。
- 状态到期。
- 配置合法性检查。
- 战斗结算。
- 存档和恢复。
- 购买、奖励等需要保证业务不变量的流程。

这些模块发生回归时，影响可能跨越多个系统。

### 3.3 现有测试能否发现这些问题？

先以批84为例。

现有的 `test_batch84_status_expire_dispatch.py` 包含以下检查：

- 持续回合到期时触发预期效果。
- 衰减到期时触发预期效果。
- `on_lose` 与 `on_expire` 的相关行为。
- 没有声明触发器时保持既有行为。
- 分派器未注册时安全失败。

urltest_batch84_status_expire_dispatch.pyhttps://github.com/xianyugezi/QBot-TurnTellerRPG/blob/main/tests/unit/test_batch84_status_expire_dispatch.py

从测试内容来看，这些断言能够覆盖多个关键场景。

但是，仅阅读测试代码，无法知道所有有意义的代码变异是否都会被这些断言捕获。

例如：

| 实验变异 | 预期测试表现 | 实际结果 |
|---|---|---|
| 删除到期时的派发调用 | 相关效果测试应该失败 | 尚未实测 |
| 错误地将已接入事件标记为未接入 | 事件状态测试应该失败 | 尚未实测 |
| 将校验器警告改为错误 | 相关校验器测试应该失败 | 尚未实测 |
| 删除未声明触发器时的兼容性处理 | 对应回归测试应该发现变化 | 尚未实测 |

这里必须明确：**预期失败不等于已经实测失败。**

本轮没有运行变异测试，因此不报告虚构的变异得分。

# 五、最重要的综合结论

今天的研究不是要推翻 QBot 现有的测试体系。

恰恰相反，现有的测试分层、覆盖率门禁、故障注入和事件自检，为进一步提高测试质量提供了良好的基础。

真正需要补充的是一个新的问题：

> **现有测试能否发现我们最担心的那类回归？**

我建议将测试质量分成三个层次：

```text
第一层：结构一致性
    ↓
第二层：运行时行为正确性
    ↓
第三层：测试对缺陷的发现能力
```

对应的技术手段分别是：

```text
AST / 静态架构检查
    ↓
单元测试 / 契约测试 / 集成测试
    ↓
变异测试 / 针对性故障注入
```

这些技术不是互相替代的。

AST 扫描可以检查代码结构，但不能保证业务结果正确。

普通测试可以验证指定场景，但不能证明所有有意义的错误都能被发现。

变异测试可以检验一部分测试的敏感性，但也不能证明不存在其他类型的缺陷。

因此，合理的策略是组合使用，而不是寻找一个万能工具。

# 七、反例与风险

### R1：不应为了 AST 而 AST

如果项目明确禁止动态事件名，所有派发都必须使用固定字面量，那么当前正则扫描器可能已经足以承担它的职责。

**判断标准应当是能否减少真实漏检，而不是工具是否更高级。**

### R2：变异存活不一定代表测试存在缺陷

某些变异可能：

- 不会改变实际运行行为。
- 位于当前场景不可达的代码中。
- 只改变不重要的日志或格式。
- 需要更高层次的测试才能体现影响。

因此，不能要求每个变异都必须失败。

### R3：不要把测试数量当成质量得分

即使测试数量继续增长，如果大量测试只是重复检查同一个不变量，整体测试体系仍可能存在盲区。

更值得追踪的是关键不变量是否受到保护，以及已知类型的回归是否能够被发现。

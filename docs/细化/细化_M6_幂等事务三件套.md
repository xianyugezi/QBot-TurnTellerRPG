## 一、幂等键入指令入口（IDEM 件套 · 【总纲】ADR-05/ADR-12 ①）

### 1.1 机制说明

幂等判定发生在**指令处理入口**：指令到达（携带 message_id/group_id/player_qid 三元组）→ `idem_claim` 只读查重 → 未命中 → 入 per-player 队列（§三）→ 单事务【业务写 + write_idem_key】→ COMMIT → 发送；命中 → 直接幂等返回，业务零执行。发送出口只是崩溃注入点，不承担幂等键（【总纲】ADR-05；【4a】F4 L277）。

崩溃窗口语义（【4a】F4 L280-281）：COMMIT 前崩溃 → 幂等键未插入、业务未提交（单事务原子）→ 重试 = 全新处理，无半执行；COMMIT 后崩溃 → 幂等键已插入 → 重试直接幂等返回 → 不双结算不双扣。回复前崩溃用例（【规则】L319）的断言对象 = 「业务已提交 + 幂等键已落（IDEM-2）」，而非发送出口键（【批5B】P1-4 修正）。

### 1.2 数据模型（引用既有 schema，非新增）

`idempotency_keys` 表（schema.py L71-81，字段即 4a §1.3 已定义，本档仅登记接线用字段语义）：

| 字段 | 类型/约束 | 语义 | 依据 |
|---|---|---|---|
| F-IDEM-01 | message_id | TEXT，PK 组合第 1 列 | 幂等键本体（QQ 消息 id） | 【4a】L118；schema.py L73 |
| F-IDEM-02 | group_id | TEXT，PK 组合第 2 列 | 群号仅进幂等键，绝不参与存档键 | 【4a】SCHEMA-3；schema.py L74 |
| F-IDEM-03 | player_qid | TEXT，PK 组合第 3 列 | 发送者（组员+发送者参与复合键） | 【4a】IDEM-1；schema.py L75 |
| F-IDEM-04 | command | TEXT NOT NULL | 指令名（审计/幂等重放识别） | 【4a】L121；schema.py L76 |
| F-IDEM-05 | result_hash | TEXT NULL | 处理结果摘要（幂等重放直接返回） | 【4a】L122；schema.py L77 |
| F-IDEM-06 | created_at | TEXT NOT NULL | 7 天滚动清理判据（idx_idem_created） | 【4a】D-03/L172；schema.py L78 |

### 1.4 边界异常

- 键三元组任一缺失（如事件无 group_id 的私聊场景）→ 【工程补白】group_id 取 `"dm"` 哨兵值兜底，保证私聊同样落幂等键（【框架】L1609 语义精神延伸，不伪造行号）。
- 同 message_id 跨天重发 → 幂等键未过期则幂等返回；过期（>7 天）则按新处理执行，业务级幂等兜底由各引擎承担（【4a】IDEM-4，签到/限购天然幂等）。
- `idem_claim` 与事务内 `idem_exists` 的时序：入口查重是快速路径；**权威判定以事务内 `tx.idem_exists` 为准**（BEGIN IMMEDIATE 持锁后二次确认，防排队窗口内先到事务已写键）（【4a】F3 模板 L251 注释语义；connection.py L344）。
- 幂等键写入用 `INSERT OR IGNORE`（repository.py L755）——并发下二次写同键被忽略，不抛错（【4a】IDEM-2 同事务语义下的安全冗余）。

## 二、购买结算入 repo.tx()（SEG 件套 · 【总纲】ADR-12 ② / ADR-06）

### 2.1 机制说明

购买结算**整体搬入** `repo.tx()`（BEGIN IMMEDIATE）内完成：读余额/限购/库存 → 6 步校验链 → 扣减 → write_idem_key → COMMIT，任一步失败整单回滚（【总纲】ADR-12 ②；【批5B】P0-2）。BEGIN IMMEDIATE 在事务期间持有写锁 + 单写连接队列（connection.py L340）使**并发事务严格串行**：第二条购买的事务在第一条 COMMIT 后才开始，事务内重读的是第一条提交后的最新状态 → 消除「读-改-写」竞态（货币丢失更新/限购漏加）【批5B】1.2 的核心修复。引擎 `shop_buy` 的内存快照-回滚（shop.py L1114-1132）**保留为事务内校验层**——防单次调用异常中间态，不替代 SQLite 事务。购买并发防护**不依赖** wild_lock（【总纲】ADR-06；【批5B】P2-4）。

### 2.2 数据模型（无新增字段）

购买结算涉及既有表：`players`（currencies/inventory/persistent_state 列，schema.py L40-46）、`world_state`（world_stock 字段，data/world_state.py L27，CAS 写回 repository.py L451-494）。**本档不新增任何字段/表**；ctx 内 `personal_buys`（玩家存档）、`world_stock`（世界状态）的持久化路径沿用既有 player_to_row/row_to_player（repository.py L114-245）与 save_world_state。

### 2.4 边界异常

- 限购满 + 库存 0 + 货币不足同时成立 → 校验链③限购先拦（【2b3】TC-39），事务内提示原样发出（【2b3】D-01）。
- 数量超过上限（默认 99）→ ⑥「提示不拦截」先截断执行量再校验（【2b3】L162；shop.py L1046-1053）。
- global 库存并发同抢最后 1 件 → 事务串行 + 条件式扣减：仅 1 人成功，另一人收到「已售罄」（【2b3】D-03/TC-24）。
- 混合支付两币任一不足 → 整单拒绝、不部分扣款（【2b3】D-02）。
- 入包通道缺失 → 校验链前拒绝 storage_missing（shop.py L1110-1111），不进入结算。
- **事务内二次读 vs 事务外预读的一致性**：装配层不得把 `load_player`（60s 缓存，repository.py L368-391）的陈旧结果直接当结算读；结算读数必须走事务内 fetchone（【细化定型】落点：ctx 构建分「浏览读」与「结算读」两路，结算路在 tx 内重读）。

## 三、per-player 串行队列（POOL 件套 · 【总纲】ADR-12 ③）

### 3.1 机制说明

同玩家指令**按到达顺序处理**（【框架】L1606），粒度 = 玩家（player_qid）级：每玩家一条 FIFO 队列，单消费者顺序消费；不同玩家队列互不阻塞。队列在**事务外排队**（【4a】TX-4），同玩家指令必然串行 → 事务冲突面只在世界资源（全体限购/野图 BOSS）。幂等键查重在入队前（【4a】F4 L277）：命中 → 直接幂等返回不入队；未命中 → 入队 → 队列内单事务处理。

### 3.2 数据模型（队列条目，进程内存，【工程补白】）

定稿只定义语义（同玩家按序），条目结构为【工程补白】定型（命名可改）：

| 字段 | 类型 | 语义 | 标注 |
|---|---|---|---|
| F-POOL-01 | player_qid | str | 队列键（每玩家一队） | 【工程补白】 |
| F-POOL-02 | message_id | str | 幂等键本体（事务内写键用） | 【工程补白】 |
| F-POOL-03 | group_id | str | 幂等键三元组之二 | 【工程补白】 |
| F-POOL-04 | handler | Callable | 指令处理闭包（解析后命令 + 已构建 ctx） | 【工程补白】 |
| F-POOL-05 | enqueued_at | float | 入队时刻（调试/超时观测） | 【工程补白】 |

### 3.4 边界异常

- 同玩家队列堆积 → 【工程补白】不设队列长度上限（消息量小，排队即幂等安全的串行化），但观测 enqueued_at 差值，异常堆积打日志（【规则】L110 日志纪律精神）。
- 玩家在队列中重复 message_id → 幂等键查重（POOL-3）保证第二条不入队直接返回（【4a】F4 L276）。
- 队列任务内事务嵌套 → 被 connection.py `_tx_owner` 防嵌套拒绝（L335-339），禁止在 tx 内再开 tx（【4a】TX-1 单指令单事务）。
- 进程崩溃重启 → 队列为内存态，随进程丢失；幂等键在 DB（已落），重发靠幂等返回兜底（【4a】F4 L280-281；【规则】L319）。

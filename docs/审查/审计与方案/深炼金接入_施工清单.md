**最小改法**（比规格建议的更小）：规格说「入参加 `settings`」——**不需要**。

  把药剂强度塞进 `stats_bonus` 会：① 让消耗品带上装备语义；② 喝药时该字段仍无人读。
  **正确的承载位是 `inst.affinities`**（`data/item.py:69`，批42 已落、落档往返已通）。

**迁移**：✅ 零。

- **A-α 不是在复用既有消费点，而是在 `healing_done_pct` 上开第二个消费点**

**判定**：⚠️ **轴名声称成立；「零新数值口径」成立；但「复用既有消费者」不成立**——
需要实现批显式选择「A-α 开第二消费点」还是「把药剂强度折进 `heal_apply` 的口径」。

## 3. 风险与坑（≥3 条，均带证据）

### R1 · 使用路径读实例会牵动 6 处 `ItemInstance` 构造点（**若新增实例字段**）

```bash
$ grep -rn "ItemInstance(" --include=*.py qbot_rpg/ | grep -v __pycache__ | wc -l
6
$ grep -rn "ItemInstance(" --include=*.py tests/ | wc -l
47
```

6 处运行时构造点：`basic_commands.py:1577` / `shop_tx.py:181` / `runner.py:720` /
`equipment.py:909` / `equipment.py:915` / `repository.py:202`。
**A-α（现算）与 A-β-轻（只冻 `affinities`）都不需要动它们**——`affinities` 字段已存在
且 `runner`/`repository` 已透传。**只有 C5（新增 `scaled_effects`）才触发这个面**：
漏改任何一处 → 该路径产出的实例静默丢字段。另有 47 处测试构造点，
新增带默认值的字段不会破坏它们，但**若有测试用 `==` 做整体相等断言**，需逐个核对。

### R2 · 池条目 `weight` 的键常量不在 `affinity_keys`，且 `effect_ref` 零消费者

```bash
$ grep -rn "ENTRY_WEIGHT" --include=*.py qbot_rpg/ | grep -v __pycache__
qbot_rpg/core/deep_craft.py:546:ENTRY_WEIGHT: str = "weight"     ← 唯一定义
qbot_rpg/core/deep_craft.py:643:            w = _as_num(_as_map(r).get(ENTRY_WEIGHT))   ← 唯一消费
$ grep -rn "ENTRY_PAYLOAD_EFFECT_REF" --include=*.py . | grep -v __pycache__
（只有 affinity_keys.py 自身 3 行，无消费者）
```

两个坑：① 写池校验时若从 `data/affinity_keys.py` 找 `weight` 会找不到——
它在 `core/deep_craft.py`，**跨层引用需注意 `content -/-> core` 的依赖铁律**
（`affinity_keys.py:5-8` 的模块 docstring 明确要求共用常量落 data 层）；
② `effect_ref` 抽出来后**没有任何消费点**，实现批若以为「抽到就生效」会写出
静默无效的代码——必须在批 59-B 显式写消费（`resolve_affinity_effect` 或 `_use_consumable` 分派）。

### R3 · `healing_done_pct` 的第二消费点与「唯一收口」纪律冲突

```bash
$ grep -rn "HEAL_DONE_AXIS" --include=*.py qbot_rpg/ | grep -v __pycache__
qbot_rpg/core/effects.py:112   HEAL_DONE_AXIS: str = "healing_done_pct"
qbot_rpg/core/effects.py:1863  done = _axis_pct(source_c, HEAL_DONE_AXIS, cfg)
```

`data/gear_stats.py:211-231` 该轴的 `consumer_note` 明写「唯一收口 = `heal_apply` 的
**source（施疗侧）** 取值」。A-α 在 `use_commands` 里对该轴做乘法 = **第二个消费点**。
规格自列 R-A1 担心平方放大——实测**不会**（`cmd_use` 在 `use_commands.py:395-396`
战斗中直接返回 `use_in_battle`，非战斗才走 `_use_consumable`），真正的风险是
**同一药剂在战斗/非战斗两路径强度口径不一致**（战斗中走 `heal_apply` 读玩家 buff 轴，
非战斗走药剂自身相性）。实现批要么接受这个不一致，要么统一收口（§5 Q1）。

### R4 · `scaled_effects` 算出来但没人读，容易误判「已经通了」

`alchemy_settle.py:367-383` 的 `scaled_effects` 有完整的 `_scale_effects` 计算
（`:322-333`，实测 `{damage:80, heal:32}`），单测也断言它
（`tests/unit/test_alchemy_settle.py:267,278,290`）。**这会让「已有结算缩放」看起来像
功能已完成**，而实测 `add_item` 只收 `quality`/`traits`。实现批务必以
**「实例上读得到」**为验收，而不是「返回值里有」。

### R5 · `zz_craft_demo` 没有任何炼金配方，端到端验收无处落脚

见核验 6：`kind=alchemy` 配方在三包中均为 0 条。规格说「zz_craft_demo 已由批58 落数据」
是对的，但**落的全是 `kind=craft` 打造数据**。不加配方/药剂，B2 的 A-V1/V2/V5 无法执行。

### R6 · 批量炼金路径（`/炼金 *N`）会静默丢相性

```bash
$ awk 'NR>=1032 && NR<=1032 {print NR"| "$0}' qbot_rpg/commands/alchemy_commands.py
1032|    _add_item(ctx, output_id, qty, quality=bq["tier"])     ← 既无 traits 也无 affinities
```

规格 §3.4 已识别此点（「批量产出不带相性，与丢特性同列」），**但引用行号偏差**
（规格写 `:1024`，实际 `_add_item` 在 `:1032`；`:1024` 是能量消耗）。
**结论正确、行号需修正**，实现批按实际行号定位即可。此路径必须显式写进批报。

## 5. 待用户裁决（只列真正的玩法分歧）

### Q1 · `healing_done_pct` 要不要在非战斗 `/道具` 开第二消费点？（**最高优先级**）

- **选项 1（规格推荐 A-α）**：非战斗 `/道具` 直接读 `inst.affinities` 求
  `healing_done_pct` 并乘进 `heal_total`。优点：零迁移、改动最小。代价：该轴出现
  第二个消费点，非战斗与战斗中强度口径不一致（R3）。
- **选项 2（统一收口）**：把药剂相性折算成一次性的 `heal_apply` 调用
  （或把 `use_commands` 的 `heal_total` 也送进 `heal_apply`），保持单一消费点。
  优点：语义一致、无 R-A1/R3 类风险。代价：要给非战斗路径造 runtime/snapshot 上下文。
- **需要你定**：是要「改动最小先跑通」还是「口径一致优先」？

### Q2 · 疗效是「使用时复算」（T2）还是「结算时冻结」（T1）？

- **T2（A-α）**：改 `settings.alchemy.affinity_effects` 会**追溯**改变已持有旧药剂的实际疗效。
- **T1（A-β 完整）**：疗效在炼金结算时冻进实例（需新增 `ItemInstance.scaled_effects`，
  触发 R1 的 6 构造点 + 迁移）。旧药剂疗效永久固定。
- **需要你定**：能否接受「改包 = 旧药剂变强/变弱」？接受 → T2 省一大批工作量。

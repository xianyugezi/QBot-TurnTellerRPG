## 一、一句话说明

打造一次装备时：**固定项按图纸照抄**；**随机项条数由图纸/包声明**，**内容从相性池抽**
（池 = 通用池 ∪ 主相性专属池；主+副命中联动时专属池被特殊池覆盖）；**装备被动按相性
变体求值**；结果（相性值、属性、套装词条、被动）**打造时冻结进装备实例**，同模板多件互不
相同、以 `uid` 精确区分。

## 二、声明形状（内容包）

### 2.1 图纸（`items`/`equipment` 条目，图纸是物品的一种）

| 字段 | 类型 | 说明 |
|---|---|---|
| `blueprint_fixed_stats` | `list<obj>` | 固定属性，每行 `{stat, value, value_rule?}`；**`value` 照抄**（`value_rule` 缩放见 §六 待裁决） |
| `blueprint_random_stat_count` | `obj` | 随机属性条数 `{min, max}`，`0~2`（可配）；缺省回落 `settings.deep_craft.craft_rules.random_stat_count` |
| `blueprint_fixed_set_affix` | `str` | 固定套装词条 id（照抄） |
| `blueprint_random_set_affix_count` | `obj` | 随机套装词条条数 `{min, max}`，`0~2`；缺省回落 `craft_rules.random_set_affix_count` |
| `blueprint_random_set_affix_pool` | `str` | 可选的候选池收窄（空 = 用相性池解析结果；见 §四 边界 6） |
| `blueprint_passive` | `str` | 固定装备被动 id（引用 `traits.json`）；受相性影响时可变更为其他被动 |
| `affinities` | `obj` | 图纸相性 `{相性id: 数值}`（作为相性累计的**前置贡献**） |

### 2.2 相性四段（`settings` 顶层，打造与深度炼金共用的通用层）

```
settings.affinities[]        {id, name, desc, exclusive_pool}      相性定义 + 专属池引用
settings.affinity_pools[]    {id, kind, desc, entries[]}           kind ∈ common/exclusive/linkage
settings.affinity_linkage[]  {main, sub, override_pool}            主+副联动 → 专属池被覆盖
settings.affinity_reactions[] {kind, from, to, pair, value}        材料互动（冲突/增幅/反转）
```

**池词条行（`entries[]`）**——一个池同时服务随机属性 / 随机套装词条：

| 键 | 类型 | 作用 |
|---|---|---|
| `stat` | `str` | **随机属性候选**：命中该键即属性词条，属性键 = 该值 |
| `value` | `number` | 随机属性的数值（缺省 0；品质/等级缩放见 §六 待裁决） |
| `set_affix` | `str` | **随机套装词条候选**：值 = 套装词条 id |
| `weight` | `number ≥0` | 抽取权重（全 0/缺失 → 取候选首项） |
| `min_level` | `int ≥1` | 装备等级下限（低于则排除） |
| `requires_affinity` | `str`（单相性） | 该词条要求相性（**必须是 `{主, 副}` 的子集**，否则抽不出） |
| `effect_ref` / `value_rule` | `str` | 保留键（`effect_ref` 供后续被动/强化词条；本批消费 `stat`/`set_affix`） |

> `requires_affinity` 的**多相性列表**由引擎 `affinity.affinity_requires` 支持，但字段元数据
> 当前登记为 `str`（门禁更严，保持不变）→ 内容包请用「主专属池 + 联动覆盖池」表达
> 「主+副同时要求」，不要用列表（见 §六 待裁决）。

### 2.3 装备被动（复用 `traits.json`，不新建注册表）

```jsonc
// traits.json 条目（含相性变体的“部分被动”）
{ "id": "<被动id>", "name": "…", "effects": ["<effect id>"],
  "affinity_variants": { "<主相性id>": "<变体被动id>",
                         "<主相性id>|<副相性id>": "<变体被动id>" } }
```

- 有 `affinity_variants` = 可变更；无 = 固定被动（表达原案 §11「部分」）。
- 求值顺序：`"<main>|<sub>"` 优先 → 退 `"<main>"` → 无命中保留原被动（复用
  `affinity.resolve_affinity_effect`，不本地匹配）。

### 2.4 产物实例字段（`ItemInstance`）

| 字段 | 内容 |
|---|---|
| `stats_bonus` | 固定 + 随机属性合并后的 `{属性键: 数值}` |
| `set_affixes` | 套装词条 id（固定 1 + 随机 0~2，去重） |
| `passives` | 本次求值后的被动 id（固定 + 相性变更结果） |
| `affinities` | 本次相性结算值 `{相性id: 数值}`（主/副从中判定；供后续强化/附魔复用） |

> 随机属性的**逐条 provenance（`stat` / `value` / 来源池）**落在打造快照
> `persistent_state.deep_craft_last.random_stats`；实例本体只留合并后的 `stats_bonus`。

## 三、抽取顺序（一次打造内的确定性步骤）

```
1. 材料归一 → 等级 / 品质经验 / 品质等级
2. 品质抽取          ← 注入随机流第 1 个随机数（批41 语义不变）
3. cost 约束
4. 相性累计          图纸相性（前置）+ 材料相性（投入顺序）→ accumulate_affinity
5. 主/副判定         rank_affinities（最高=主、第二=副；并列按 affinities[] 声明序）
6. 池解析            resolve_available_entries(config, main, sub, level)
                     = 通用池 ∪ 主专属池；联动命中 → 主专属池被 override_pool 覆盖；
                       requires_affinity ⊆ {main,sub} 过滤；min_level 过滤
7. 条数抽取          随机属性条数（图纸声明优先，回落 craft_rules）→ 1 个随机数
                     随机套装词条条数（同上）→ 1 个随机数
8. 逐条抽取          按 weight **不放回**抽（同载荷键去重）；随机套装词条排除固定项
9. 被动求值          blueprint_passive → affinity_variants → resolve_affinity_effect
10. 冻结进实例       固定+随机属性 / 套装词条 / 被动 / 相性值
```

随机数消费顺序固定（品质 → 属性条数 → 套装条数 → 属性抽取 → 套装抽取），同种子必同结果。

## 四、边界行为（明确口径）

| # | 情形 | 行为 |
|---|---|---|
| 1 | **无相性**（`main=None`） | `requires_affinity` 非空的词条**全部抽不出**（原案 §12「本质一个池子，没有对应相性就抽不出来」）；通用池中不要求相性的词条仍可抽 |
| 2 | 主/副**并列** | 按内容包 `affinities[]` 声明顺序破平；无声明序则按 id 升序（确定性） |
| 3 | **副相性缺失** | `sub=None`；联动不命中 → 回主专属池；要求副相性的词条抽不出 |
| 4 | 联动命中 | 主专属池**整体被 `override_pool` 覆盖**（原案 §8「特殊联动池也是专属池的一种，触发会覆盖掉专属池」） |
| 5 | 候选不足声明条数 | 实际条数 = `min(声明条数, 候选数)`，**不补空**、不降级到其他池 |
| 6 | `blueprint_random_set_affix_pool` 声明 | 在**已解析候选**中再按 `_pool` 收窄；声明池不在「通用 ∪ 专属/联动」可达集内 → 无候选 = 抽不出（不外开第二条池查询） |
| 7 | 权重全 0/缺失 | 取候选首项（确定性；**不引入未声明概率**），仍逐项去重 |
| 8 | 固定套装词条 | 随机抽取时**排除**固定项，避免重复 |
| 9 | 无 `traits` 定义 / 被动无变体 | 被动 id 原样保留（框架不臆造） |
| 10 | 注入随机源缺失/非法 | 条数取 `min`、抽取退化取首项（确定性，不报错） |

## 五、与既有 `forge_sets`（套装档位/激活）的关系

**核查结论：产物上的套装词条目前无法被既有套装结算识别——如实登记为缺口。**

- 既有套装结算（`core/forge_sets.py` + `core/forge_set_skills.py`）的件数来源是
  **锻造节点 id**：`player["set_tracker"]`（族 id→件数）优先，否则从
  `equipped`/`equip_nodes`/`equip_snapshot` 取条目的 `node_id`/`id`（`forge_sets.py:116-118,687-713,730-739`），
  与 `forge.json sets[].pieces` 求交。
- 深度打造产物的身份是 `ItemInstance`（`item_id` + `slot` + `uid` + `set_affixes`），
  **没有锻造节点 id**；`EquipmentSlot` 只存 `item_id/name/slot_level/locked/gems/uid`，
  也不携带套装词条。因此「同名套装词条件数 → 激活」这条链**当前未接通**。
- 文档化的 `INS-07 set_tag` 消费方**未实现**（全仓 `grep set_tag` 仅命中注释）。
- **建议复用路径（待裁决后再接线）**：在唯一已穿戴件枚举点（`equip_mods._worn_defs`，
  与副手失活同源）按穿戴实例的 `set_affixes` 归并族件数写 `set_tracker`，即可让既有
  `set_lookup`/`resolve_set_skills` 零改动识别打造套装。**前置待裁决**：套装词条 id 与
  `forge.json` 套装族 id 的对应关系（原案未定义；是否要求同名，或需一处映射声明）。

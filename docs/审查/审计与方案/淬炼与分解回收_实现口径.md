## 2. 淬炼（原案 §10）

### 2.1 原案逐条拆解 → 可执行规则

原案 §10 全文（`打造系统_原案_20260919.md:41`，一段话）：

> 「装备根据**装备等级**会获得**淬炼上限值**；玩家可以通过消耗**装备精粹**对装备的**某一个属性**进行淬炼提升；除去**装备总体的淬炼总值**，**单项属性也有淬炼值上限**，玩家需要对淬炼属性有一定的规划。」

| # | 原文要素 | 可执行规则 | 参数（§2.3） | 落点 |
|---|---|---|---|---|
| R1 | 根据**装备等级**获得**淬炼上限值** | `total_cap = f(装备等级)`，等级越高上限越大；**上限是"总值"** | `temper.total_cap` / `cap_formula` | `enhance.json → temper` |
| R2 | 消耗**装备精粹**提升**某一个属性** | 单次操作 = 指定 `stat_key`；消耗 = 精粹（必）＋金币（可选）；**确定性消耗，无成功率**（原案未提失败） | `temper.cost_per_point`、`allowed_stats` | 同上 |
| R3 | **总体淬炼值上限** | `Σ temper_alloc.values() ≤ total_cap` | `total_cap` | 同上 |
| R4 | **单项属性也有上限** | `temper_alloc[stat] ≤ per_stat_cap(stat)`，且 **`per_stat_cap < total_cap`**（否则无规划空间） | `per_stat_cap` / `per_stat_cap_ratio` | 同上 |
| R5 | 玩家需**对淬炼属性有规划** | 由 R4 派生：**可淬炼属性数 ≥ 2** 且 `per_stat_cap/total_cap < 1` 时，必须取舍 | `allowed_stats` 长度、`per_stat_cap_ratio` | 同上 |
| R6（原案 §12 `:54`） | **装备精粹通过分解装备获得** | 精粹**只从分解出**（是否另有来源 → §5 D4） | `essence_rate`（§3.1） | `settings.forge` |

> **口径澄清（关键，需用户确认）**：R2 的"某一个属性"是指**该装备模板已提供的属性之一**（原案 §3：图纸固定 1~3 + 随机 0~2 条），还是**任意属性键**？本报告按前者设计（`allowed_stats` 必须全部取自该实例已有属性键，回退全局 `GEAR_NUMERIC_KEYS`）；后者会让"淬炼"变成"打词条"，与原案 §3/§4 的属性来源划分冲突。

### 2.2 数据模型草案

#### A. 落点三方案对比

| 方案 | 做法 | 优点 | 缺点 / 风险 | 判定 |
|---|---|---|---|---|
| **P1（建议）** | `ItemInstance` 新增 `temper_alloc: Dict[str,int]`（+ 派生 `temper_total`）；`EquipmentSlot` **不加**淬炼字段 | 与 `uid` 实例身份同层，天然跟随装配/卸下/寄存/交易（批 40 已把 uid 打通这些链路，`equipment.py:807-815`）；**单一事实源**，无双向同步 | 5 处重建点必须同改（§6 自证 ③）；`frozen=True` → 用 `dataclasses.replace` 更新（既有先例 `enhance_commands.py:626-628`） | ✅ |
| P2 | 挂 `EquipmentSlot.temper_*`（仿 `slot_level`） | 与强化显示同源 | **复制强化已有的双写痛点**（`enhance_commands.py:33-36` F-2 明确记录双向同步之累）；卸下/交易/寄存时状态会丢 | ✗ |
| P3 | 侧表（存档新表 `instance_temper`，uid 主键） | 不动 `ItemInstance` 重建点 | 新增持久化面 + 事务 + 清理；批 40 的"包声明状态格"（CHANGELOG `player_pack_state`）是玩家×包粒度，不适配实例粒度 | ✗（除非未来要跨装备的淬炼传承） |

#### B. 字段草案（**字段语义级，非代码**）

| 字段 | 类型 | 默认 | 语义 | 备注 |
|---|---|---|---|---|
| `temper_alloc` | map<stat_key,int> | `{}` | 各属性已投入淬炼点数；**只记分配，不记基数** | 上限判定、分解返还、规划展示的唯一事实源 |
| `temper_total` | int | `0` | `sum(temper_alloc.values())` 的**冗余缓存** | 可省（每次求和），但展示/排序高频 → 建议缓存并加**一致性校验** |
| `temper_seed` | int | — | 若淬炼为**随机加点**（原案未提）则需要 RNG 快照 | **默认不需要**（见 §2.3 假设 T-A1：淬炼是确定性投入，不是赌博） |
| **不新增** `temper_bonus` | — | — | 数值加值**物化进既有 `stats_bonus`** | 与强化同款；聚合/桥/展示零改 |

> **为什么不存"淬炼基数"**：`stats_bonus` 里已经是"模板词条 + 强化 + 淬炼"的混合结果。要区分"哪部分是淬炼"，只要**从 `temper_alloc` 按同一公式重算**即可（确定性公式），不必再存一份基数——**存两份必然漂移**。

#### C. 属性物化路径（复用既有全链路）

```
策划数据(enhance.json → temper)
ItemInstance.temper_alloc
   └─► temper 引擎算 Δ ─► 上限校验(total/per_stat)
          └─► stats_bonus[stat] += Δ（写回 ItemInstance）
stats_bonus ─► aggregate_bonus(:789) ─► route_bonus_into(:132)
   └─► attributes.bonus.flat/pct ─► pvp 战斗桥 / 展示 / 编辑器
```

- 聚合点：`equipment.py:789-850`（同层求和 → `attributes.bonus["flat"/"pct"]`）
- 键分层：`gear_stats.py:63-75`（flat/pct/combat 三档）＋ `:132 route_bonus_into`
- 先例：强化就是**物化进 `stats_bonus`**（`enhance_commands.py:561-632`；`data/item.py:63` 注释"实例级持久化；穿装同步 `EquipmentSlot.slot_level`"）

#### D. **双计/幂等风险（必须写进实现任务书）**

- 强化用 `level <= cur → 返回 0`（`enhance_commands.py:575-576`）防重复加；淬炼若用"每次 +Δ"累加，**重放/重连/重算会把 Δ 加两遍**。
- **建议口径**：淬炼写入用**幂等式重算**——`Δ(stat) = 公式(temper_alloc[stat])`，写回时**以"当前值是上次物化结果"为不变量**，或干脆**用 `temper` 引擎一次性重算整件**（base 词条保留在 `stats_bonus`、淬炼部分单独维护一个内部快照）。二选一必须显式，不能默认。→ 列入 §5 D9。

#### E. 迁移

- 仿 `migrations.py:92-135 backfill_instance_uids`：新增 `DB_SCHEMA_VERSION 3→4` + 纯函数 `backfill_instance_temper(inv, equip)`（缺失 → `{}`；**只增键，不删改**；幂等）；新库直具备（`ItemInstance` 默认 `{}`）。
- 因 `temper_alloc` 默认空 dict → **旧档零语义变化**（不淬炼 = 空分配）。

#### F. 装备等级从哪来（**依赖缺口**）

| 候选 | 现状 | 问题 |
|---|---|---|
| `items[].use_level` | 引擎已消费（`equipment.py:325-349`；字段登记 `field_meta.py:2282-2283`） | **veinborn `items.json` 0 条**（实测）；且打造装备是**实例**，`use_level` 是**定义**级 |
| 实例 `required_level` | **不存在**（`ItemInstance` 无此字段） | 需新字段 + 迁移（与本文件 `temper_alloc` 同一批做最省） |
| 打造节点 `node.level` | `forge.json` 有（1~6） | **是职业门槛，不是装备等级**（A 路 C11 `:512-513` 明确"绝不复用"） |

### 3.1 精粹产出公式与可调参数表

#### A. 公式（N5 口径展开；决策记录 `:32`）

```
精粹产出(件) = floor( 投入价值(V) × k1 × k2 × β^色序 ) + 淬炼返还
  k1   = 材料价值基准回收系数      （决策记录 0.30–0.40）
  k2   = 图纸档系数                （决策记录 0.40–0.60）
  β    = 品质色序衰减              （决策记录 0.50–0.70）
  色序 = 白0 / 绿1 / 蓝2 / 紫3 / 橙4 / 红5
  淬炼返还 = floor(该件已投入淬炼点数 × temper_refund)   （默认 temper_refund = 0 → 0）
```

#### B. `投入价值 V` 的三种定义（**必须先裁决，否则 k1 无量纲意义**）

| 方案 | 定义 | 可算性（现状） | 优点 | 缺点 |
|---|---|---|---|---|
| **V1 图纸固定材料价值**（建议） | `V = Σ(节点固定材料件数 × items.price)`；同一图纸的产品 V 相同 | ✅ 现在就能算（`forge.json` 节点 `materials[]` + `items.json` `price`；实测 §4 已算） | 实现最省；防"投 1 个便宜材料打造毕业装"；与 cost 上限（B 路 `:106`）同源 | 不含"自由选择材料"的投入差异（原案 §1 `:6` 有自由槽） |
| **V2 实际投入材料价值** | 实例档案里记录本次打造的实际投料 → 逐件求和 | ❌ **不存在**（`ItemInstance` 无打造档案） | 最公平：真·高投入高回收 | 需批 44 前先加"实例打造档案"（新字段 + 迁移 + 打造主流程写入） |

### 3.4 经济风险与闸门

#### A. 无限循环是否可能？（分两侧证明）

| 侧 | 循环 | 是否可能无限 | 证明 |
|---|---|---|---|
| **材料侧** | 打造 → 分解（返材料）→ 再打造 | ❌ **不可能**（但会被显著放大） | 回收率最大 0.65 **< 1**（`gem_wallet.py:91-93`）→ 每循环净损 ≥35% 材料；**收敛级数** = `1/(1−0.65) ≈ 2.86` → 材料可被"用 2.86 次"，**不是无限** |
| **精粹侧** | 分解（出精粹）→ 淬炼 → 分解（含返还） | ⚠️ **可能**，当且仅当 `temper_refund > cost_per_point.essence` | 单件循环：投入 `c = 点数 × p` 精粹，分解返还 `r = 点数 × refund`。若 `refund > p` → 净赚，**且可跨件套利**（分解 A 的精粹去淬炼 B，再分解 B）。`refund = 0`（建议默认）→ 精粹侧**严格单向**，无循环 |
| **装备侧** | 分解 → 得精粹 → 再打造 | ❌ 不可能闭环 | 分解**销毁装备**（`alchemy_commands.py:1669-1672` 扣物品）、打造**消耗材料**（材料回收 <100%）→ 需要外部材料输入 |
| **跨系统侧** | 装备分解 ↔ 炼金分解（宝石/材料）互转 | ⚠️ 需检查 | 若精粹能买材料或材料能换精粹 → 破闭环。当前无此兑换（`currencies` 只有 coins/zuanshi） |

**结论**：**只要 `temper_refund = 0` 且精粹不可逆（不能换回材料/装备）**，就不存在无限循环；风险不在"无限"，而在 **"精粹净产出远超淬炼消耗"造成的购买力通胀**（§4）。

#### B. `β^色序` 闸门为何**实际失效**（本报告新增发现）

- 设计意图（B 路 `:491-492`）：品质越高回收越少 → 防"打造→分解→再打造"套利。
- 实际行为：玩家分解的是**不要的**件。按 §13 概率表（原案 `:64-78`），铜图纸 1–3 级有 **75%/55%/45% 出白**，即使 10 级也有 40% 紫。→ **被分解件的色序集中在白/绿**，即 `β⁰ = 1.0`、`β¹ = 0.6` 的高回收区。
- 数值后果（β=0.6）：

| 色序 | β^色序 | 每单位投入精粹系数 (`k1·k2·β^i`) | 会被分解吗 |
|---|---|---|---|
| 白 0 | 1.000 | 0.1750 × V | **会（主要来源）** |
| 绿 1 | 0.600 | 0.1050 × V | **会** |
| 蓝 2 | 0.360 | 0.0630 × V | 有时 |
| 紫 3 | 0.216 | 0.0378 × V | 少（常保留） |
| 橙 4 | 0.130 | 0.0227 × V | 极少（保留） |
| 红 5 | 0.078 | 0.0136 × V | **几乎不会（毕业保留）** |

- **结论**：`β` 的衰减几乎全部作用在"不会被分解的件"上 → **对精粹供给不设闸**，反而让**垃圾装备成为最高效的精粹矿**。→ 若要保留 `β`，须同时加 M6 实测与 §3.4C 的 G2/G5 闸门；否则 `β` 是"看起来很聪明但不生效"的参数。

#### C. 建议的闸门（G1~G5）

| 闸门 | 内容 | 作用 | 参数 |
|---|---|---|---|
| **G1 装备消失（硬）** | 分解必然销毁该件（现有 `/分解` 已是扣物品语义，`alchemy_commands.py:1669-1672`） | 断"装备侧闭环" | 无（语义） |
| **G2 对象限定（硬）** | 只有**打造装备**可出精粹；炼金产出仍只走 `decompose_rate` | 防"从商店/掉落廉价装备刷精粹"（对齐既有防套利四轴 `gem_wallet.py:19` GEM-13/14） | `essence_rate.scope="crafted_equipment"` |
| **G3 精粹不可逆（硬）** | 精粹**不能**换回材料/装备/金币；只能淬炼 | 断跨系统闭环 | 无（语义；需 D4 载体决定） |
| **G4 递减（软）** | `cost_growth>0`：已投点越多，每点越贵 | 让"满淬"不是线性投入，抑制无限堆精粹 | `temper.cost_growth`（默认 0 = 原案口径） |
| **G5 产出上限（软，兜底）** | `cap_per_item` / `cap_per_period` | 防单件暴利/防 RMT 批量套利；**校准前的安全阀** | `essence_rate.cap_*`（默认 null） |
| **G6 返还率上限（硬）** | `temper_refund ≤ cost_per_point.essence` 由校验器红拦 | 直接禁止精粹侧循环 | `essence_rate.temper_refund` + V 校验 |

### 4.6 反解（校准锚点）

| 场景 | 条件 | 平衡点 `p` |

### 4.7 推演结论

1. **N5 的三档区间（k1/k2/β）不足以决定经济**——区间跨度只有 ~2 倍，而 `p` 需要跨 3 个数量级。
2. **必须新增"消耗侧"参数表**（本报告 §2.3 已给 `cost_per_point`/`cost_growth`/`stat_weight`），否则产出侧怎么调都失衡。
3. **`β^色序` 建议降级为"锦上添花"**，真正的闸门是 G2（对象限定）+ G3（不可逆）+ G5（上限）。理由见 §3.4B。
4. **`V` 的口径必须先定**（§3.1B）：若用 V3（price×系数），所有数字随 `price` 表漂移，回收率无法校准。
5. **淬炼上限必须与另三条通道同账重算**（§2.4B-5）：本报告的 `total_cap = 等级×6` 是**独立推演**，落地前须与**节点改造 / 客制 / 强化（H3 的 +18）/ 品质系数（N4）**四条通道合并到批 45 的装备总额度里复核（决策记录 `:44` 的"总额度参数上调配平"）。

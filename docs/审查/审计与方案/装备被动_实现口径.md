## 〇、一句话结论

**「装备被动」在框架内不需要新造机制**：被动**定义**复用既有 `traits.json`（命名被动注册表，`effects[]` 绑定行为，`content/veinborn/traits.json` 当前 0 条），被动**行为**复用 `effects.json` 运行期；装备模板上**新增一个引用字段 `passives`** 声明「模板固定被动」；「相性影响变更」写成被动定义上的 `affinity_variants` 映射，**直接调 `affinity.resolve_affinity_effect` 求值**（池化随机抽取则调 `affinity.resolve_available_entries`），不另算池。**打造时求值、冻进实例**（§12 独一无二），穿戴时只重算「当前生效集」（副手失活复用既有唯一枚举点）。最大工程缺口是 **`event_dispatcher` 无 owner 过滤**（触发式被动会全局误触发），以及 **`traits` 目前无任何战斗消费点**。

### 1.1 §11 两条要求拆成可核对条目

| 条目 | 原案原句（行号） | 拆解出的可核对要求 |

## 二、数据模型草案

> 原则：**被动身份**（叫什么、是不是可变更、变更成谁）与**被动行为**（干什么）分离；前者落注册表与模板声明，后者落 `effects.json`。**不新建第二套被动模块、不新建第二套相性池**。

### 2.1 装备被动的声明形状 —— 落在哪：`traits` / `effects` / 新段？

**结论：三层落点，各归其位。**

| 层 | 落点 | 复用/新增 | 理由（file:line） |
|---|---|---|---|
| **被动定义（身份 + 行为绑定 + 变更映射）** | **`traits.json`（复用，增量扩展 1 键）** | **复用（推荐）** | 现成语义恰好是"命名被动 + `effects[]` 绑定"：`field_meta.py:2388-2400`；kinds 已注册 `field_meta.py:84`；专项校验 `alchemy_models.py:1041`；`veinborn` 0 条零迁移（N-3）。**不新建 `passives.json`**（会与 `traits` 重复）。 |
| **被动行为（原子动作 / 触发容器）** | **`effects.json`（复用，不新增段）** | **复用** | `effects.execute_action`（`effects.py:1770`）+ `execute_proc_action`（`effects.py:2122`，`trigger`/`chance`/`cooldown`/次数上限现成）；`traits.effects[]` 已 ref `effect`（`field_meta.py:2391` = `F_EFFECTS`，`field_meta.py:136`）。 |

| 名称 | `name` | str | — | — | 否 | 复用 |
| 效果 | `effects` | list | ref 列表 | `effects` | 是 | **被动行为**，复用（`field_meta.py:2391`） |

**模板声明草案（`items`/`equipment` 定义）：**

```
"passives": ["passive_id_a", "passive_id_b"]     // list<ref trait>
```

- **「部分可变更」不需要额外的 per-entry 开关**：可变更性由被动定义是否有 `affinity_variants` 决定（有=可变更，无=固定）。
- 若希望同一被动在不同模板上表现不同（同一 `affinity_variants` 但模板可选择不启用变更），再加 per-entry 形态 `{"id": "...", "affinity_mutable": true}`——**默认不做**，进 §四 待裁决。

### 2.2 「相性影响变更为其他被动」的声明形状（**复用 `affinity.resolve_*`**）

**主形态（确定性替换，对应 §11「变更为」）——复用 `resolve_affinity_effect`：**

被动定义里：
```
"affinity_variants": {
  "<main_id>":        "<passive_id>",   // 仅主相性
  "<main_id>|<sub_id>": "<passive_id>"  // 主+副（= 联动/特殊组合）
}
```

求值（**唯一入口，不自建查表**）：
```
resolve_affinity_effect(passive["affinity_variants"], main, sub)
```
- 命中 `"main|sub"` 优先，再退回 `"main"`，否则 `None`（`affinity.py:351-377` 已实现该优先级）。
- **联动语义直接由 `"main|sub"` 键承载**，与 `settings.affinity_linkage`（`affinity.py:131-132, 280-290`）的 `{main, sub}` 概念同构；若用户要求"联动必须走 `override_pool`"，则改走下面的池形态。

**池形态（随机抽取，对应 §8「从池子抽取」+ §11「部分被动」）——复用 `resolve_available_entries`：**

池词条行已有文档化字段 `effect_ref`（`affinity.py:15`）：
```
settings.affinity_pools[].entries[] = {
  "effect_ref": "<effect_or_passive_id>",   // 目标被动/效果
  "requires_affinity": ["<aff>", ...],       // 必须是 {main,sub} 的子集（affinity.py:334-339）
  "weight": <number>,                        // 抽取权重（内容包声明）
  "min_level": <int>                         // 装备等级下限（affinity.py:340-343）
}
```
求值：`resolve_available_entries(cfg, main, sub, level)` → 候选行列表（通用池 加 主专属池；联动命中 → 专属池被覆盖）。**池的构造/联动/过滤全部由该函数承担，本设计不复制任何池逻辑。**

**两种形态的分工与边界（推荐）：**

| 形态 | 语义 | 适用 | 复用接口 |
|---|---|---|---|
| `affinity_variants`（主形态） | **确定性地**把某个固定被动替换为另一被动 | §11「部分被动受相性影响变更为其他被动」 | `resolve_affinity_effect` |
| 池 `effect_ref`（次形态） | 从相性池**随机**抽一个被动/效果 | §8「从对应池子抽取」；若用户希望被动也随机 | `resolve_available_entries` |

**必须避免的反模式（本设计明令禁止）**：在被动定义里自己写 `{main, sub, requires_affinity}` 列表再本地匹配——那会另造一套池/联动/子集判定，违反决策记录「不得在两处各写一套相性」（`docs/深度打造_决策记录.md:52`）与任务书「不得自己算池」。

### 2.3 与 `ItemInstance.uid`（批40）的关系 —— 定义级还是实例级？

**结论：被动 = 定义级声明 + 实例级解析结果。**

| 问题 | 结论 | 依据 |
|---|---|---|
| 被动声明在哪一级？ | **定义级**（图纸/装备模板定义 `passives`；被动本体在 `traits.json`） | 原案 §11「根据装备模板」；模板=物品（§12"图纸本身是物品" L55） |
| 变更结果在哪一级？ | **实例级**，且在**打造时**求出后冻结 | §12「每一次都是随机的……不重叠、独一无二」（L47）要求同模板多件结果不同；`ItemInstance` 为 `frozen=True`（`data/item.py:34-45`） |
| 用什么容器？ | **推荐新增 `ItemInstance.passives: Tuple[str, ...] = ()`**；备选复用既有 `ItemInstance.traits`（`data/item.py:61`） | 见下表对比 |
| 与 `uid` 的关系 | `uid` 是"哪一件"的精确键（`data/item.py:65`；回指 `EquipmentSlot.uid`，`docs/深度打造_决策记录.md:187`）；被动集是 per-uid 的属性。**被动集随 uid 精确定位，聚合/展示/战斗桥按 uid 取件（不得按 `item_id` 混堆）** | 批40 已解"同 item_id 多件随机词条混堆"问题（`data/item.py:34-45`） |
| 是否每次穿戴重算？ | **不重算变更结果**；穿戴只重算"当前生效集"（副手过滤） | 若穿戴时按定义+当前相性重算，同模板多件会得到相同被动 → 违背独一无二 |

**实例容器对比（推荐新增 `passives`）：**

### 3.2 「变更」在哪个时点求值（穿戴时 / 每次结算 / 缓存）

**推荐：打造时一次求值 + 实例冻结；穿戴时只重算生效集；结算时只读缓存。不每次结算重算。**

| 时点 | 是否求值「变更」 | 做什么 | 理由 |
|---|---|---|---|
| **打造结算** | **是（唯一求值点）** | 用该实例的 `(main, sub, level)` 调 `resolve_affinity_effect`（确定性变体）或 `resolve_available_entries`（池抽取），得到最终被动 id 元组，写入 `ItemInstance.passives` | §12 独一无二 + `frozen=True`；保证同模板多件结果不同 |
| **穿戴/卸下** | 否 | `recompute_equip_passives` 只做"哪些槽的被动当前生效"（副手过滤 + 去重/冲突） | 被动身份已冻结，穿戴不改结果 |
| **每次战斗结算** | 否（只读） | 直接读 `ctx["equip_passives"]`，触发式走 proc 计数 | 结算期重算会引入不确定性与性能开销；且相性在打造后不再变 |
| **缓存** | 落 `persistent_state` + `ctx` 镜像 | 与 `equip_skills`/`set_skills` 同模式（`context.py:1523-1530`） | 复用既有装配缓存口径 |

> 唯一例外：若用户希望"相性在装备成长后变化 → 被动跟着变"，则需要一个显式的**重铸/再打造**动作触发重新求值，而不是自动每结算重算——进 §四 待裁决。

### 3.3 触发式被动的归属过滤（工程缺口的具体建议）

现状：`dispatch_event` 无 owner 概念（N-5，`event_dispatcher.py:127-134`）。若不修，任何带 `trigger` 的被动效果会**对所有战斗单位/所有战斗**生效。

建议（择一，进 §四 确认）：
- **方案 A（推荐，改动最小）**：给 `dispatch_event` 增加 owner 作用域参数（如 `active_effect_ids: Optional[Sequence[str]]`），在 `_iter_candidates` 的"纯效果事件"分支按该集合过滤候选；调用方（battle）从 `ctx["equip_passives"]` 展开成 effect id 集合传入。
- **方案 B**：在 combatant 上挂"当前激活效果"列表，分派时按 `side` 取该列表过滤。
- **方案 C**：被动不落 `effects.trigger`，而由装备层在对应时点**主动调用** `execute_action`（像 α5 `resolve_attack_override` 那样显式触发）。

三种方案都**不改变 `effects.py` 的原子能力**，只补"归属"。
